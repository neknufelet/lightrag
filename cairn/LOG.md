## 2026-08-09（六）· 十二道閘門的 V1／V2 接上了，截斷不再靜靜通過

- **接的方式是共用一份實作，不是抄過去。** `vlm.py` 的十二道發現時整包零呼叫點，
  而 apply 那側**重寫**了其中三道 —— 抄一份就是這個坑本身的成因。所以把 V1／V2
  抽成 `vlm.truncation_failures()`，`judge()` 與 `eyes.look()` 都叫它，一份實作、
  兩個呼叫者。測試裡有一條專門斷言「沒有第二份抄本」。
- **斷點就在一行**：`vlm.transcribe` 正確回傳 `finish_reason`、`_store` 正確存進
  快取（21 筆全是 `stop`），但 `_cached` 只挑 `["html"]` 出來，訊號在快取這條路上
  被丟掉。改成回整包之後，**快取命中那條路也驗得到** —— 轉錄是會被長期沿用的。
- **真正會靜靜通過的形狀只有一種，先證明它是真的再補。** 三種截斷實測：單表截斷
  被 `gate_table_html` 擋（但訊息說「不是單一完整的 table」，看不出成因）；表後截斷
  無害；**兩表、第二表截斷會放行** —— `extract_html` 的非貪婪正則只取第一個完整的
  `<table>`，半張表被當成整張表採用，閘門看到的是結構完整的表。測試同時斷言
  舊路徑會放行、新路徑會擋，只斷言後者的話，判準被改回去也看不出損失了什麼。
- **實跑驗證（dker，真實資料）**：21 筆既有快取全部通過，`look()` 端到端呼叫 21 次
  零錯誤 —— 而且 `host` 故意設成 `unreachable.invalid`，真打出去就會回錯誤，
  所以**確定是零 API 呼叫**。拿真實轉錄砍掉尾巴 40 字元則正確擋下並印出該刪哪個
  快取檔。`canary` 27 份全綠（rc=0），基準一個數字都沒動 —— 這次沒碰規則。
- **⚠ 方程式那條路不能套同一個判準。** `eq-check.py` 把 `PROMPT` 換成方程式版，
  輸出是裸 LaTeX，V2 的「以 `</table>` 收尾」對它每一條都會誤判成截斷。三個呼叫點
  傳 `closing=None`（只跑 V1），`PROMPT` 與 `closing` 是同一個旋鈕的兩端。
  這條**NEXT 原本沒寫到**，是查呼叫點時才發現的。
- **被截斷的轉錄照樣寫進快取**（PO 裁決）：壞輸出留在磁碟上可 diff、可重看、
  restic 會備份，下次重跑直接從快取判失敗、不重複付費。代價是快取的鍵不含
  `max_out`，調大額度不會自動失效 —— 所以拒絕訊息直接印出該刪哪個檔、該調哪個鍵。
- 缺 `raw`／`finish_reason` 的快取當成**驗不了**（放行並 log 一行 warning），
  不當成截斷 —— 當成壞了會無端重付一輪轉錄費。實測現有 21 筆都有這兩欄。

## 2026-08-09（六）· 查詢這條路上唯一會抖的那一步，可以搬走

- **正式庫的查詢是不可重現的，而且是現在就有的行為。** 一個沒查過的問題連問三次
  拿回三組不同的段落。成因：`mode=mix` 要走圖譜就得先把問題變成關鍵詞，而那一步
  是 LLM 做的、查詢端溫度 1.0、**而且沒有快取**（`lightrag_llm_cache` 只有
  `extract` 與 `summary` 兩類）。查過的問題看起來穩定是被上層快取住了 ——
  **不穩定只咬「沒人問過的問題」，也就是正常使用的情況。**
- **解法：關鍵詞由外部 agent 給。** `/query/data` 收 `hl_keywords`／`ll_keywords`。
  自帶之後三題各問三次全部相同，分數一題更好、兩題持平、零題變差。
  數日誌證實：**自帶關鍵詞的查詢，llama.cpp 收到 0 次請求**（後端自己抽是 1 次）。
  ⇒ 後端變成零 LLM 的純運算。⚠ 但**不會變快** —— 那次呼叫只花 0.7–0.9 秒，
  5 秒的耗時在向量比對與圖譜查詢上。省的是不確定性不是時間。
- **圖譜值得留：mix 比 naive 好 10.2%，10 題裡 naive 一題都沒贏過。**
  對照之下「圖譜是誰建的」（DeepSeek vs llama.cpp，同 22 份文件）四次量測是
  +1.5%／+0.1%／+0.5%／−0.2%，正負都有。
  ⇒ **「用不用圖譜」比「誰建的」大一個量級。**
- **圖譜不必清到絕對乾淨。** 模型寫的實體描述從來不會到使用者手上（kbapi 只轉發
  chunk），所以垃圾節點最多讓它挑錯段落、不會污染答案。相對地**前端消音
  （參考文獻、標題頁）才是值錢的那一半** —— 那些文字本來會被撈回來佔掉 context。
- 完整的逐步拆解與數字：[cairn/retrieval-architecture.md](retrieval-architecture.md)。
- **這一輪我又踩了一次同一個坑，而且是在寫「不要踩這個坑」的工具時踩的。**
  評分跑完看到「10 題有 7 題分數到小數第四位完全相同」，差一點就當成「兩邊差不多」
  報出去。**那個異常才是真訊號** —— 追下去才發現量測本身不穩。

## 2026-08-09（六）· DeepSeek 試跑：可行、快、但照出比較組的盲點

- **「不思考」是必要條件不是選項。** DeepSeek 官方文件：思考預設**開著**且 effort
  是 high；關掉要送 `extra_body: {"thinking": {"type": "disabled"}}`。實測三次
  思考開著，其中一次 `finish_reason=length` —— 推理把 4,000 token 額度吃光、
  輸出被截斷、**不報錯**。關掉之後快一倍且穩定（3.8–5.9 秒對 7.5–21.0 秒）。
- **LightRAG 送得出去**（我先前判斷錯，以為送不出去）：
  `OPENAI_LLM_EXTRA_BODY` 與 `OPENAI_LLM_TEMPERATURE`，命名規則是
  `OPENAI_LLM_` ＋ 欄位名大寫。容器啟動日誌會印出實際送出的 options。
- **速度**：3 篇 82 秒（預設溫度）／163 秒（temp 0.2）；6 篇含 148 chunk 的
  教科書章節共 201 秒。對照本機 llama.cpp 每篇約 6 分鐘。
- **併發：`MAX_PARALLEL_INSERT` 是文件層閘門**（量到的：3 → 6 之後六份同時跑）。
  但**一份文件內部會平行抽 chunk**（教科書 148 chunk／138 秒，單次 8–10 秒
  ⇒ 約 8.6 條同時），所以 `MAX_ASYNC` 才是真正的旋鈕。
  ⇒ **我先前說「只調 MAX_ASYNC、文件層會擋住」是錯的。**
  16／6 之下：429 零次、重試零次、截斷零次，**天花板還沒摸到**。
- **不要設輸出 token 上限。** DeepSeek 上限 384K，LightRAG 預設不送 `max_tokens`，
  兩輪實跑 `finish_reason=length` 零次。設了才會製造「安靜被切掉」的風險。
  單價（官方）：輸入快取命中 ¥0.02/M、未命中 ¥1/M、輸出 ¥2/M。
- **品質**：對得回原文的比例與其他配置同級（可疑率 DS 1.0%、llama 0.7%、
  vLLM 1.3%），**捏造的關係三邊都是 0**。碎片化比率也同級（7.4–9.1%），
  但**碎法不同**：llama／vLLM 是單複數，DeepSeek 是自創縮寫（`(MPP)`、`(HR)`）。
- **最有價值的副產品：三篇的比較組測不到規則 2b。** `Region I`／`Zone II`／
  `Part 1` 這種標籤只出現在教科書章節，四個配置在三篇論文上全是 0。
  加了 C 那篇之後才量得到：DeepSeek 的 2b 遵守度是 **2／8**
  （做對的長這樣：`chamber (region II)`、`neck (region I)`）。
  ⇒ 而 2b 是**唯一沒有確定性工具能補的規則** —— `graph-clean` 只會刪或不刪，
  不會改名，而那些裸標籤正是 PO 裁決「先不刪」的那一族。
- **修好一支從 2026-08-08 起就跑不起來的檢查**：`extract-check.py` 把
  embedding 模型名直接拼進表名，換成 `BAAI/bge-m3` 之後斜線讓 psql 直接
  syntax error。它只在有人主動跑時才會炸，所以沒人發現。
- **我今天犯的三個錯**（形狀都一樣：拿沒驗的東西當結論）：
  ①「694 個實體名字全部找得到、0 個找不到」—— chunk id 前綴過濾錯了，
  那個 0 是**一次比對都沒做**。真實數字是 10.7%。我當天稍早才引用過
  「乾淨的 0 要先當成量錯」。
  ②「DeepSeek 碎片化比較嚴重」—— 只看一份文件的印象，量三份就不成立。
  ③ 為了測溫度設定跑了 `--force-recreate`，**洗掉第一輪的日誌**，
  於是「82 秒對 163 秒」的差異再也無法歸因。
