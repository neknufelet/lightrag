# 檢索架構：誰決定拿到哪幾段原文

**這份文件回答的問題**：使用者問一句話，到 agent 手上那幾段原文之間，發生了什麼、
哪幾步會抖、哪幾步能換人做。

2026-08-09 之前這件事沒有人完整量過，於是「換抽取模型會不會讓答案變好」這種問題
沒有辦法回答 —— 因為不知道抽取模型到底影響到哪一步。

---

## 一次查詢實際發生的事（實測，不是讀碼推的）

`kbapi` 的 `/kb/{ws}/search` 下傳給 LightRAG 的是：

```python
{"query": …, "mode": "mix", "top_k": 10, "chunk_top_k": 6, "only_need_context": True}
```

`only_need_context=True` 讓它在生成答案之前就停住 —— 回傳的欄位裡沒有任何
answer／response。**後端不寫結論**，這一點是設計，不是巧合。

一次查詢的外部呼叫次數（數 llama.cpp 與 Infinity 的日誌）：

| 步驟 | 誰做 | 次數 | 穩不穩 |
|---|---|---|---|
| 問題 → 關鍵詞 | 後端 LLM | **1** | ❌ 不穩，見下 |
| 關鍵詞／問題 → 向量 | Infinity embedding | 1 | ✅ |
| 向量比對 ＋ 走圖譜 → 候選段落 | 純運算 | — | ✅ |
| 候選段落重新排序 | Infinity rerank | 1 | ✅ |
| 砍成 `chunk_top_k` 段 | 純運算 | — | ✅ |
| 再砍到 `chars` 上限 | kbapi | — | ✅ |
| 段落 → 答案 | **外部 agent** | — | 由你控制 |

⇒ **決定「拿哪幾段」的是 rerank，不是外部 agent。** agent 只能決定問什麼、
以及（見下）給什麼關鍵詞。

---

## 唯一會抖的是「問題 → 關鍵詞」

`mode=mix` 要走圖譜，就得先把問題變成關鍵詞，而那一步是 LLM 做的。
**查詢端的 LLM 跑在溫度 1.0（沒有人壓下來），而且那一步沒有快取**
（`lightrag_llm_cache` 只有 `extract` 與 `summary` 兩類）。

實測：一個從沒查過的問題，在正式庫連問三次，拿回三組不同的段落。

```
第1次 [eb5a6d94, 72d06a65, 9773df92, 70eec7ad, 8a588bd3, 18673d80]
第2次 [eb5a6d94, 72d06a65, 9773df92, 70eec7ad, 8a588bd3, 6cf94c6d]
第3次 [72d06a65, 9773df92, 8a588bd3, 18673d80, 6cf94c6d, c2112bb0]
```

**這是正式庫現在就有的行為**：同一個問題問兩次，使用者可能拿到不同的答案，
而沒有任何訊號。查過的問題之所以看起來穩定，是因為結果被上層快取了 ——
不穩定只咬「沒人問過的問題」，也就是正常使用的情況。

---

## 解法：關鍵詞由外部 agent 給

`/query/data` 接受 `hl_keywords` 與 `ll_keywords`。自己給的話，後端那一步就不做了。

實測（同一題各問三次）：

```
題 1（英文）
  後端抽關鍵詞    ❌ 三次不同   分數 0.7624   4.8–4.9s
  自帶關鍵詞      ✅ 三次相同   分數 0.8507   5.6–5.7s
  naive（不走圖譜） —          分數 0.6177   0.7s

題 2（英文）    後端 ❌ 0.9265 ／ 自帶 ✅ 0.9265 ／ naive 0.7394
題 3（中文）    後端 ❌ 0.3597 ／ 自帶 ✅ 0.3597 ／ naive 0.2411
```

而且數過日誌：**自帶關鍵詞的查詢，llama.cpp 收到 0 次請求**（後端自己抽時是 1 次）。

⇒ 後端在這條路上變成**零 LLM 的純運算**：向量比對、查表、rerank。

⚠ **不會變快。** 那 1 次 LLM 呼叫只花 0.7–0.9 秒（50–65 token），5 秒的耗時在
向量比對與圖譜查詢上。省下的是不確定性，不是時間。

---

## 圖譜值不值得（mix vs naive）

同一個庫、同一組 10 題，只差走不走圖譜：

```
        mix      naive
全部  0.6492   0.5827   -10.2%
中文  0.4347   0.3853   -11.4%
逐題：mix 勝 7、平手 3、naive 勝 0
```

**naive 一題都沒贏過。** 圖譜對「挑段落」有實效，而且方向一致沒有反例。

對照組：**圖譜是誰建的**（DeepSeek vs llama.cpp，同樣 22 份文件）四次量測是
`+1.5% / +0.1% / +0.5% / -0.2%` —— 正負都有，是雜訊。

⇒ **「用不用圖譜」的影響（10%）比「圖譜是誰建的」（雜訊）大一個量級。**

---

## 中文問題的洞，這條路解決不了

自帶英文關鍵詞配中文問題，分數 0.3597；同一個意思寫成英文是 0.7624。

原因：關鍵詞只用在圖譜那一段，而**段落的向量比對用的是問題原文**。中文問題對
英文段落，那一步就對不上。

⇒ 要翻的是**整個問題**，不只是關鍵詞。這與 `retrieval-tuning.md` 記的
「中文問英文論文差 63–86%」是同一件事的兩個切面。

---

## 這對「圖譜要多乾淨」的意義

因為模型寫的實體描述**從來不會到使用者手上**（kbapi 只轉發 chunk，程式碼註解
寫明 entities/relationships 對這種用法是雜訊），所以：

| | 拿掉什麼 | 價值 |
|---|---|---|
| 前端消音（參考文獻、標題頁） | 那段文字不進索引 | **直接** —— 它本來會被撈回來佔掉 context |
| 圖譜清除（`graph-clean.py`） | `equation 22` 那種節點 | **間接** —— 只影響挑段落，內容不會外流 |

⇒ 前端消音是比較值錢的那一半（參考文獻消音實測 262 條一條都沒進索引）。
⇒ 圖譜不需要清到絕對乾淨：留著的垃圾節點最多讓它挑錯段落，不會污染答案。

---

## 還沒量的

- 圖譜清除（`graph-clean`）對檢索有沒有幫助 —— 沒量過
- `chunk_top_k=6` 是不是最佳值。第 7、8 段才是答案時**不會有任何訊號**
- 把 6 放大讓外部 agent 自己篩，值不值得（代價是 context，skill 記著每次查詢
  回傳 14,000–21,000 token）
