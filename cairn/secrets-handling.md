# 秘密怎麼放、怎麼讀

## 形成背景

2026-08-08 同一個 session 內把 `.env` 的秘密印進對話紀錄**兩次**——
`LIGHTRAG_API_KEY` 與 `MINERU_API_TOKEN`。

兩次的位置控制都是對的：`.env` 在 `/opt/stacks/lightrag/`（不在 repo）、
已 gitignore、chmod 600、不進備份。**該做的位置控制全做了，而值還是漏了。**

原因不是有人去偷檔案，是 `grep` 讀了它、輸出被貼出來。第一次之後我改了腳本裡的
遮蔽，第二次是在命令列上臨時打的 grep——**同一個錯誤換個位置**。

## 當前結論

### 位置擋不住洩漏，通道才擋得住

規則要分兩層寫。**第一層是必要的，第二層才是真正在防的那層。**

**第一層：值住哪**

- 值只活在**部署機的部署目錄**：`/opt/stacks/<stack>/.env`，chmod 600
- **不在 repo、不在備份、不在任何會同步的地方**
- repo 裡只有 `.env.example`：**名字＋這個值去哪裡拿＋為什麼是這個值，沒有值本身**

**第二層：值怎麼被讀**

- 要**列名字**：一律 `cut -d= -f1` 或 `grep -oE '^[A-Za-z_][A-Za-z0-9_]*'`，
  **永遠不要讓 `=` 右邊進入輸出**
- 要**用值**：在部署機上 `set -a; . .env; set +a`，讓它留在環境變數裡
- **不得帶上指令列**（`ps` 看得到；`4a54ed7` 已經對 `oracle.py` 做過這件事）

### 「先取出再遮蔽」的設計本身就是錯的

這是這則的核心。兩次外洩我都**打算**遮蔽，兩次都是正規式寫錯：

```bash
# 第二次的實際寫法，看起來很合理
grep -nE "TOKEN|RERANK|TOP_K" .env | sed -E "s/(KEY|TOKEN_[A-Z]*|PASSWORD)=.*/\1=<redacted>/"
# MINERU_API_TOKEN= 不符合 TOKEN_[A-Z]* （TOKEN 後面沒有底線），於是原樣印出
```

只要「值曾經進入輸出管線」，防線就只剩一個**容易寫錯的字串比對**。

⇒ 規則的重點不是「記得遮蔽」，是**讓值根本不進入輸出**。
`cut -d= -f1` 與 `source` 這兩種寫法**沒有可以寫錯的地方**——
不是靠小心，是靠沒有機會出錯。

### 執行者

| 規則 | 誰守 | 綠燈條件 |
|---|---|---|
| `.env` 不進版控 | `.gitignore` ＋ pre-commit | 已有 |
| live 與 example 的設定項目名單一致 | `daily-check.sh`（NEXT.md 上，未做） | diff 只有預期差異 |
| 秘密不上指令列 | pre-commit 掃 `--key=` 樣式（未做） | 無命中 |
| **值不進輸出** | **沒有人** | —— |

**最後一列是這則存在的理由。** 那條規則沒有執行者，只能靠寫的人記得——
而已經證明「記得」會失效兩次。

## 教訓

- **位置控制與通道控制是兩件事，做對前者不代表後者。** 這則的整個背景就是
  「位置全對、值照樣外洩」。
- **同一個錯誤修一次不夠。** 第一次之後只改了腳本，沒改「我自己在命令列上臨時
  打的指令」——而後者才是真正的發生地。修的時候要問「這個錯誤還能從哪裡出現」。
- **設計比紀律可靠。** 可以寫錯的防線就會被寫錯；沒有參數可以填錯的做法才擋得住。
