### cold workload 判斷

你的判斷**只對一半**：

- `cache_prompt=false` 能消除同題重播造成的巨大污染，作為「完整 cold prefill 壓力測試」與 MTP 公平 A/B 控制是合理的。
- 但「每個 chunk prompt 不同，所以正式負載 cache hit 接近零」不能直接成立。llama.cpp 重用的是共同前綴，不要求整份 prompt 完全相同；`cache_n` 也是重用的 prompt token 數。[llama.cpp server 文件](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) [共同前綴示例](https://github.com/ggml-org/llama.cpp/discussions/15530)
- LightRAG 的抽取 prompt 將大量固定指令放在 `input_text` 前，因此不同 chunk 仍可能共享很長前綴；這是從上游 prompt 結構作出的推論，釘死的 v1.5.5 映像仍應以真實 fixture 驗證。[LightRAG prompt source](https://github.com/HKUDS/LightRAG/blob/main/lightrag/prompt.py)

最低解鎖仍需：

1. 用最大併發量做成功的 synthetic warm-up，確保每個 slot 被觸及；或丟棄一個完整 calibration round。
2. 不要以 `max != min` 宣告「有順序效應」；至少增加獨立重複並報可解讀的變異。
3. 補多題 cache 加總與多輪 report 的整路徑測試。
4. 若要把 cold 數字稱為正式抽取的代表，另以「互不相同的 fixture prompts、只打一次」量一次 cache-on 的 `cache_n/prompt_tokens` 分布。

因此目前數字仍不應直接決定 `MAX_ASYNC` 2→4，也還不能作為正式 MTP 換檔基準線。工作樹保持原狀，仍只有原本兩個 untracked 檔。
