# 第二意見：gleaning（補抓那輪）該不該砍

你是 codex luna，本專案的**第二意見**席。**唯讀，不要改任何檔。**

我剛得出一個負面結論，準備寫進 `NEXT.md` 擋掉一個未來的優化提議。
**如果我算錯了，這個錯會留很久**，所以先請你找碴。

## 背景

LightRAG 抽取每個 chunk 時會呼叫 LLM **兩次**：
① 初次抽取 ② 「補抓遺漏或描述錯誤的實體」（gleaning，prompt 以
`---Task---\nBased on the last extraction task...` 開頭）。

390 份文件的抽取估計約 60 小時（本機 llama.cpp，解碼是瓶頸）。
我原本的假設是：**補抓那輪可能大量重工或只撈到低價值的東西，砍掉可省一半時間。**

## 我量到的（dker 實跑，母體＝`lightrag_llm_cache` 的 1,019 筆 `extract` 快取）

**第一層——成本與產出**
```
            呼叫數   輸出字元佔比   抽出實體   每次實體
initial      510      60.3%        6,372      12.5
gleaning     509      39.7%        3,912       7.7
```
⚠ 63 筆 `return_value` 不是合法 JSON（initial 41、gleaning 22），
它們的實體數被算成 0，會低估。

**第二層——補抓是不是主要在撈符號型垃圾**
（符號型＝`extract-check.py --dump-symbolic` 的 1,482 個，名字實質就是符號、檢索價值低）
```
            可解析呼叫   抽出實體   其中符號型   佔比
initial        469       4,935        729     14.8%
gleaning       487       3,808        950     24.9%     ← 1.69 倍
```

**第三層——邊際價值：補抓撈到的有多少是第一輪沒有的**
（同一 chunk 內比對名字，大小寫不敏感；458/510 個 chunk 兩輪都可解析）
```
補抓抽出 3,439 個名字
  第一輪已有   227（6.6%）
  真正新增   3,212（93.4%）
    符號型     878（佔新增 27.3%）
    非符號型 2,334   ← 我認為這是它真正買到的
```

## 我的結論（請你攻擊它）

**不要砍 gleaning。** 用 40% 的抽取時間換 2,334 個全新的非符號型實體；
第一輪產出約 4,206 個非符號型，所以是「多花 40% 時間換多 36% 有用實體」——
大致成比例，不是浪費。原本「省 24–30 小時」的想法不成立。

## 請你判的

1. **這個推論有沒有漏洞？** 特別是：
   - 我用「非符號型」當「有用」的代理指標，這個代理站得住嗎？
   - 「輸出字元佔比 ≈ 時間佔比」這個換算（解碼是瓶頸）合理嗎？
     prompt 的 prefill 成本我沒有分開算——initial 與 gleaning 的 prompt 長度不同
     （母體平均 15,742 字元，但兩組我沒分開量），這會不會翻轉結論？
   - 我比對「新增」用的是**同一個 chunk 內**的名字集合。但 LightRAG 之後會跨 chunk
     合併實體（原始抽取約 10,280 個 → 最終索引 7,211 個，三成被併掉）。
     用 chunk 內去重會不會**高估**補抓的新增量？
2. **那 63 筆解析不了的 return_value** 是不是一個獨立的問題？
   6% 的抽取輸出不是合法 JSON——這些內容有沒有可能整批掉了？
   （我不知道 LightRAG 的解析器有多寬容，這點沒查。）
