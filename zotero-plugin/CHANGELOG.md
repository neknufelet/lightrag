# 版本紀錄

每一條都記**為什麼改**，不只記改了什麼 —— 半年後回來看，「改了什麼」從 diff
就讀得出來，「為什麼」讀不出來。

裝法一律是：Zotero → 工具 → 附加元件 → 齒輪 → Install Add-on From File，
**然後完整重開 Zotero**。⚠ 2026-08-15 踩過：管理員顯示新版號，但記憶體裡跑的
還是舊的 `bootstrap.js`，花了好幾輪才發現。

## 0.3.6 — 2026-08-19

**點附件那一列送出，終於也會過選片規則了（`KI-016`）。**

在條目清單裡展開一筆文獻、對底下某一份 PDF 那一列按送出時，`sendOne()` 走的是
另一支：

```javascript
if (item.isPDFAttachment && item.isPDFAttachment()) {
    attachment = item;                       // ← 直接用，choose() 整段不跑
```

⇒ 過濾中文翻譯本的規則**全部沒執行**。點到哪一份就送哪一份，而且**沒有任何
訊號** —— 中文會安安靜靜進庫，然後被公式跨來源比對當成一個獨立來源。
PO 2026-08-15 口頭提過，08-16 才寫進 `KNOWN_ISSUES`，今天修。

**判準刻意不是「照 `choose()` 再挑一次」。** 人明確點了某一份，那是意圖 ——
他可能就是要送那一份補充資料、那一章。拿規則蓋掉他的選擇，等於按了送出卻送出
別的東西，那是另一種安靜的錯，不比原來的洞好。

⇒ 只擋一件事：**他點到的那一份本身就是翻譯本**（在 Zotero 裡原文與翻譯上下
相鄰，誤點很容易）。擋下來時說得出為什麼：

    這一份看起來是中文翻譯本，沒有送出。要送原文請改點文獻那一列

**判斷搬進 `lib/pickpdf.js` 的 `acceptDirect()`** —— 留在 `bootstrap.js` 裡就
測不到，而這個 bug 的本體正是「規則存在但那條路徑沒呼叫它」。所以
`tests/pickpdf.test.js` 除了測判斷，還有一條**盯著呼叫點**的測試：純函式測得到
判斷，測不到有沒有被呼叫。

⚠ 修之前那 6 條測試全是紅的（`# pass 15 # fail 6`），修完 `# pass 56 # fail 0`。
**這一點很重要**：08-18 第二雙眼睛在 bug 還在的情況下實跑，50 條測試全綠 ——
舊的判準（「測試全綠」）證明不了任何事。

## 0.3.5 — 2026-08-15

**選片時連檔名一起看，並認得 `mono`／連字號版的 `dual`。**

PO 問「排除規則有沒有 deepseek、mono 這兩個字」。查下去發現兩件事：

1. **外掛只看附件標題，不看檔名。** 掃全庫 2241 個附件，有 6 個標題看不出是
   翻譯（`deepseek-mono`、`電子書`），證據只在檔名裡（`….zh-TW.mono.pdf`）
   —— 那些**會被當成原文送出去，而且不會有任何訊號**。
2. **規則只認底線版的 `_dual`**，而 BabelDOC 也產 `.mono.pdf`，
   工具鏈另外會產 `-mono` / `-dual`（連字號）。

修法：標題與檔名一起比對，樣式加上 `[-_.]mono\b` 與 `[-_.]dual\b`。

⚠ `mono`／`dual` 前面**一定要有分隔號**。沒這個限制的話
`… Digital Monogr.pdf`（專著）會被誤判成翻譯本而拒送。測試裡有一條守著。

`deepseek` 這個字**沒有加進規則** —— 那 5 筆靠 `mono`／`dual` 就抓得到，
而把工具名寫進規則等於賭下一個工具也叫這個名字。

## 0.3.2 — 2026-08-15

**對帳從「用檔名查」改成「用 Zotero 的 key 查」。**

記在「其他」欄位的檔名是伺服器當時回的那一個。它一改名（同名加序號、重新命名、
遷移），對帳就查不到 —— 而「查不到」的處置是 `missing`，跟「被刪掉」「被重置」
落在同一格。**於是檔名漂移會偽裝成資料不見，沒有人分得出這兩件事。**
key 是 Zotero 給的，伺服器那邊做什麼都不會變。

順帶解決拆書：一本七章的書七個檔案共用一個 key，
**七章全進去才算 done**（進六章不是「進去了」——那一章查詢時找不到，
而標籤會說它在）。

## 0.3.1 — 2026-08-15

**自己決定送哪個 PDF，不用 `getBestAttachment()`。**

實測 PO 的庫（179 筆在知識庫裡的文獻）：**155 筆有兩個 PDF，其中 96 筆是
「原文 + 中文翻譯」**。挑錯就是把中文餵進英文語料，而且它會一路解析、抽取、
進圖譜，看起來一切正常；更糟的是中英兩份會被公式跨來源比對當成兩個獨立來源，
製造出大量看起來很像真的假發現。

翻譯本怎麼認（量出來的）：

```
名字像翻譯   有 BabelDOC 標籤    幾個
   否            否              205   ← 原文
   是            是              178   ← 翻譯，兩邊都認得
   是            否               10   ← 早期翻的，那時還沒打標籤
   否            是                0   ← 一個都沒有
```

`BabelDOC_translated`（翻譯工具自己打的）**從不誤標**但會漏 10 個；
名字樣式反過來。所以兩個都用、取聯集。

**分不出來就不送**（實測 2/179，那兩筆是庫裡真的有重複附件）。
送錯比不送嚴重得多。

## 0.3.0 — 2026-08-15

**檔名帶上 Zotero 的 item key。**

同一篇文獻在三個系統裡沒有共同的名字：Zotero 有 item key、知識庫有檔名、
Obsidian 有筆記名，互不攜帶對方的識別碼。於是「這三個是不是同一篇」只能拿標題
去猜，而 2026-08-14 一天內這個猜法被八種情形各打敗一次（拆書、縮寫、截斷、
空白不一致、標點黏字、上下集、短吃長、前綴相同）—— **每修好一種，下一批文件
就長出新的一種**。

檔名是唯一已經天然流過每一站的東西（進料台 → 解析快取的鍵 → LightRAG 的
`file_path` → 檢索回傳的 `doc` → kbapi 的圖片別名），所以身分放這裡等於零改管線。

```
APLAMD5P 2021 - Room acoustic modeling with the TD-DG method.pdf
```

⚠ **key 放最前面**，因為實測 Zotero 自己重新命名附件時會把名字砍在 110–111 字，
而且**一律砍尾巴**（翻譯本是先砍到 110 再接 `_zh-TW_dual`，證明頭部沒被動）。

⚠ key 取**父層文獻**的，不是附件的 —— 同一筆的原文、翻譯、章節共用同一個身分，
那正是「這幾個檔案是同一部作品」的依據。

⚠ key 不合格一律退回無前綴的舊格式，**不擋送出**：擋住會讓工作流當場停掉。

## 0.2.1 — 2026-08-14

**標籤從 `_RAGED` 改成 `_Raged`。**

外掛寫大寫、PO 手打小寫，同一件事兩個標籤名。合併時踩到更大的坑：
**Zotero 的 `DELETE /tags?tag=X` 不分大小寫**，刪大寫那個把 163 筆的小寫也
一起帶走，靠事先存的備份逐筆 PATCH 才救回來。所以源頭要對齊，不要再分岔。
