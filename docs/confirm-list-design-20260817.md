## 量：這個數字要不要算、怎麼算、誰算（PO 2026-08-17 追問）

> 第一個數字很重要嗎。都要建新庫了。還不如確認這個數字要不要算。
> 怎麼算 誰算。固定算的是怎樣。要不然散落在哪有屁用

**這一節先前是一格死數字（`631 項散在 165 份`），而它就是 PO 這句話的反例。**
同一個量在四個地方出現過四個版本：

```
631 項散在 165 份     這份文件 8/16 寫的那一版
1015 項散在 203 份    8/17 傍晚的交接
1232 項散在 218 份    scripts/pp/confirm.py 開頭的說明
1342 項散在 246 份    8/17 深夜重跑（指令見下）
```

⇒ **散落的數字沒有用。要留的是「怎麼量」，不是量出來的值。**

### 要不要算：要 —— 但只有「動手之前」量的才算數

理由不是好奇，是**它決定人要坐多久**：1342 項一項十秒就是 3.7 小時。它也是
「規則先幫你勾好」有沒有省到力的唯一證據（省下來的是「規則直接丟」那一格）。

⚠ **基準錯了這個數字就沒有意義。** 2026-08-17 深夜實測：

```
$ ssh florian-dker 'ls -d /data/lightrag/work/crops/*/backup | wc -l'
317
$ ssh florian-dker 'ls -d /data/lightrag/work/crops/*/ | wc -l'
317
```

317 份**每一份都有 `backup/`** —— 那是 `pp/apply.py` 動手之前存的備份，代表消音
早就真的執行過了。在這種文件上再算一次計畫，`noise.mute` 全是 0：

```
noise.held 1050   noise.mute   0
title.held  292   title.mute  71
refs.held     0   refs.mute  382
```

⇒ **等於在已經掃過的地板上數灰塵。** apply 之後量，「規則直接丟」永遠偏小、
「要人看」永遠偏大。**唯一有意義的時機是 apply 之前** —— 新庫重抽時每一份都會
經過那個狀態。

### 怎麼算：一支指令，零件都是現成的

```
scripts/postprocess.py plan --json     # 算出計畫，只讀不寫
pp/confirm.py items_from_plan()        # 要人看的項目
pp/confirm.py muted_count()            # 規則有把握直接丟的項數
```

實測整批 317 份跑完 **6.27 秒**（dker，2026-08-17）—— 便宜到不需要為它做快取。

### 固定算哪幾格：四格，缺一格就會誤導

| 格 | 少了它會怎樣 |
|---|---|
| 母體幾份 | 其餘三格不知道分母是誰 |
| 要人看幾項 | 不知道人要坐多久 |
| 散在幾份 | 不知道「確認一份放行一份」的批次多大 |
| 規則直接丟幾項 | 分不出「這批很乾淨」與「規則把半份文件丟了」（藍桶第 2 條） |

⚠ 每次報這四格都要附**什麼時候量的、母體是什麼、在 apply 之前還是之後**。
少了最後一項，兩次量出來的數字就不能比。

### 誰算：機器，跟每日體檢一起跑

**建議（PO 未裁）：**

1. **`scripts/daily-check.sh` 加一格**，每天把四格寫進 `checks/`。趨勢看得到，
   就不會再有人憑印象引用三天前的數字。**成本 6.27 秒**，相對於現在的 8 分鐘可忽略。
2. **文件與程式說明裡不再寫死這個數字，改寫量它的指令。**
   ⚠ `scripts/pp/confirm.py` 開頭現在寫著 `1,232` 與 `7,586`，今天照著跑重現不出來
   —— 那正是鐵則第 9 條在罵的事（附了來源卻給了對不上的數字），要拿掉。

## PO 2026-08-17 裁的四條

### 一、打勾 ＝ 不要

打勾代表「這段不要進知識庫」。**要丟掉的比較多**，所以這樣人動手的次數少。

### 二、一份一份，但不用做完才能往下；**確認一份、放行一份**

- 每做完一份**存一次**，關掉瀏覽器不會丟；回來從那一份接著。
- **確認完的積起來，湊成一批就去抽取。** 不用等 165 份全部做完。
- **沒確認的等著，不會被抽取。**

⚠ **這一條是 2026-08-17 稍晚更正的。** 模擬畫面第一版我寫了
「沒做完不擋新庫，文件照樣進得去」—— **那是我自己加的，沒想清楚成本，是錯的。**
PO 問「是做完全部才抽，還是決定多少抽多少」時才發現。

**為什麼「先抽再確認」是錯的**：消音會改變送去抽取的文字（`pp/apply.py` 的註解
寫著消音會讓 `is_bundle_valid = False`、快取失效）。先抽了之後才改消音，
那一份就得**重抽一次** —— 而抽取是整條線最貴的一步（審核台自己的字：
「先花小錢解析看清楚，再花十幾分鐘抽取的大錢」）。

⇒ 先抽再確認 ＝ 花兩次錢，165 份全改就是全部重來。

⚠ PO 明確否決了「按型別整批決定」那個版本（那會把 631 個決定壓成 5 個，
但他要一份一份）。**那個選項留在這裡備查，不要當成沒提過**：
如果哪天覺得太慢，改成按型別是現成的加速路。

### 三、不確定的預設不勾（＝留著）

寧可多留垃圾，不要誤刪正文。與 `docs/hard-rules.md` 一貫。

### 四、⭐ 每一項都要有一句白話說明「為什麼」

**PO 2026-08-17 看過模擬之後主動指名要保留這個。** 例如：

```
參考書目    機器有把握，先幫你勾了
期刊封面頁  整頁只有刊名與投稿日期
不確定      像頁首，但裡面有數字
致謝        不敢消，有些致謝裡寫著資料來源
```

**為什麼這條值得單獨記**：沒有這句話的話，畫面只剩「一堆勾選框加一堆文字」，
人得自己重新判斷每一項 —— 那就等於規則沒幫上忙。
這句話是「規則先幫你勾好」這個設計**能不能省下人力的關鍵**，不是裝飾。

⚠ 說明文字要說**理由**不是說**分類**。「參考書目」是分類，
「機器有把握，先幫你勾了」才是理由 —— 兩個都要，因為人要判斷的是
「機器憑什麼這樣勾」。

### 五、清單是**獨立一頁**，不塞進審核台現有的頁

PO 2026-08-17 稍晚：「清單應該是跳另一個頁面吧」。**我同意，三個理由：**

1. 審核台現有的頁是**看狀態**，這一頁是**做事情**。做到一半關掉要能回來，
   狀態頁沒有「做到哪裡」這種概念。
2. 一份文件平均 5～6 項（8/17 實測 1342 項散在 246 份），多的一份幾十項，
   塞進現有頁會把狀態擠掉。
3. 「確認一份、放行一份」需要一條「下一份」的動線 —— 那是一整頁的事。

⚠ **但入口要在審核台上**：一個連結，寫著「還有 N 份要確認」。沒有那個入口，
這一頁等於不存在。

### 六、兩隻眼睛先幫你勾好 —— 要做，排在人工那條路之後

PO 2026-08-17 稍晚：「然後其他幫忙看過也不錯」。

⚠ **這一項會花錢**（每一項要送去給模型看），所以 PO 只說了方向，**還沒裁時機**。

**建議：先把純人工那條路走通並上線，兩隻眼睛當第二版加上去。** 理由是沒有它
系統照樣能用（只是慢）；反過來如果先做它、人工那條沒走通，它出錯時沒有退路。

⚠ 要花多少錢還沒量。等第一批人工確認跑完、知道「人要坐多久」的真實數字之後，
PO 再裁值不值得。**這是花錢的決定，我不執行。**

| 欄位 | 例 | 為什麼要 |

**比對過了：拆章勾選已經解過一模一樣的題目，直接抄形狀。**

| | 拆章勾選（已上線） | 確認清單（提案） |
|---|---|---|
| 真的在用的檔 | `/data/lightrag/records/chapter-splits/` | `/data/lightrag/records/confirm-lists/` |
| 版控副本 | `verdicts/records/chapter-splits/` | `verdicts/records/confirm-lists/` |
| 誰搬過去 | `scripts/pull-verdicts.py` | 同一支，`PAIRS` 加第三個項目 |

⚠ **不要直接寫進 dker 上的 repo。** 那台是唯讀只 `git pull`，寫進去的檔會躺在
那裡永遠上不了 GitHub。體檢表踩過這個坑（一度 dker 318 份、git 只有 20 份，
備份只做到 6%）。這條寫在 `scripts/chapters/split_record.py` 的註解裡。

**三條照抄的規則**（理由見 `docs/chapter-selection-record-20260817.md`）：

1. **存整份清單，不是只存改了哪幾列。** 規則之後會改，而放行要照**當時**的決定，
   不是照新規則重算。
2. **每確認一份存一次。** 關掉瀏覽器不會丟，回來從下一份接著（第二條裁決）。
3. **改勾選可以留一句為什麼，但不強迫。**

**一項要存哪些欄位，`scripts/pp/confirm.py` 的 `ConfirmItem` 已經定好了**：
`key`（`section:index`，穩定識別）、`suppress`（要不要丟）、
`decided_by`（規則勾的還是人改的）、`note`（人改的理由，選填）。

### ⚠ 一個還沒量的問題：重抽之後 `index` 對得上嗎

`index` 是「解析結果裡第幾項」。新庫要重抽，**解析結果換了一份，同一個 index
會不會指到別的段落？** 拆章那邊的對應問題是「書被換掉、頁碼可能對不上就停下來
問人，不照舊頁碼硬切」。

這裡要不要照抄那個處置，**得先量過才知道** —— 還沒量。
⚠ 這條沒解之前，「存整份清單」只擋得住規則改變，擋不住重新解析。
