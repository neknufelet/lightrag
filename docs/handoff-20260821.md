# 二、真正的發現：警報機制本身

**PO 的原話**：「從一開始就在那邊沒人守要不就沒亮燈，你到底要怎樣才能亮燈有人守
做一些有用的事情」。

## 2.1 共同形狀：「沒在守」與「守了沒事」長得一樣

| 實例 | 表面 | 實際 |
|---|---|---|
| `canary` | 每天「金絲雀通過」 | 基準是 `{}`，**守著 0 份** |
| `test_stack_matches_repo` | 報告寫 `passed` | skipif 路徑過期，dker 上也跳過 |
| 體檢表五個閘門 | 一整欄 `-` | 172 份全部從沒量過（860/1376 格） |
| `compat` 的 `ok=None` | 燈號綠 | 那幾條斷言其實驗不了 |

這個專案**本來就有三態**（通過／失敗／驗不了）。問題是實作一路塌回兩態。

## 2.2 最嚴重的一盞：金絲雀下線中

```
$ cat tests/canary-baseline.json
{}
$ ssh florian-dker '…/postprocess.py canary'
金絲雀通過：0 份基準文件的數字都沒變（另有 172 份新文件尚未納入基準）
canary rc=0
```

清空基準（commit `4a6e533`）是對的——裡面 319 份全是已刪的舊庫。**沒做後半步
才是問題**：那個 commit 自己寫著「灌完第一批要記得跑 `canary --update`」，
而沒有任何機制在提醒。

⇒ **現在改任何規則都不會有人知道有沒有改壞。** 這也是為什麼工單 A 排第一。

## 2.3 檢索完全沒有探針

```
$ grep -rn "retrieval-check" scripts/ deploy/

```

`kb-health-check` 技能文件寫著「`retrieval.smoke` 放每日檢查」——**那句是錯的**，
它從來沒被排程叫過。2026-08-08「知識庫有料卻答查無資料、零紅燈」那族事故，
