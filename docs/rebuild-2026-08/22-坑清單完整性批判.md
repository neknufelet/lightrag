清單挖得很深，但它有一個系統性偏差：**agent 讀的是「被文件指到的檔」，沒讀「沒有人指到的檔」**。結果整個 LLM 伺服器的部署（`deploy/llama-qwen36-moe/`）、一條被否決的第三隻眼選型（mathpix）、跨機查詢工具（askrag）、通知管道（notify.sh）、以及 177 個 commit 裡最大的那 20 個訊息，**從頭到尾沒有任何 agent 打開過**。裡面至少 20 條坑，其中一條是「金鑰變數名打錯不會報錯，伺服器會以全部放行啟動」——安全等級的靜默失敗，這個專案最擅長的形狀，而清單裡一個字都沒有。

## 3. 整類被漏掉的坑

### (a) 環境／基礎設施 — **最大的空洞**

清單裡「環境」只有 bind mount inode（PIT-108）與目錄權限（PIT-109）兩條。實際上：

- **整個 LLM 伺服器的部署層完全沒有**（見 Q1 第 1–9 條）。這是唯一一台有 GPU 的機器、唯一一個沒有 compose／systemd 管的服務、唯一一個有 API key 直接暴露在 `ps` 的地方。
- **restic 密碼經 `ps` 外洩**（`54f86f7`「順修密碼經 ps 外洩」，`backup-cold.sh:86`）——清單的 BACKUP 線（PIT-021）只收了三段式與指紋，沒收這條。
- **`POSTGRES_USER` 至今仍預設 `"deeptutor"`**（實跑 grep：`compat-check.py:37`、`extract-check.py:75`、`compare-ws.py:61`、`archive-ledger.py:60`、`llm-bench.py:163`）。搬離 DeepTutor 之後 DB 使用者名沒改，所以 `grep deeptutor` 永遠有 5 個命中——**「已修」與「沒修」在 grep 結果上長得一樣**，正是這個專案自己在防的形狀。
- **Neo4j 搬遷的隔離驗證程序**（`54f86f7`）：「動手前照例先驗隔離：acoustics_v2 的 7,211 節點只有一個 label、跨界關係 0」、「刪 177,142 節點，全部發生在**複本**上，原實例一個位元沒動」。不可逆操作的前置驗證範式，清單沒有。
- **為什麼共用實例做不到選擇性備份**（`54f86f7`）：Postgres 的 `base/<oid>` 一庫一目錄，但 `global`／`pg_xact`／`pg_wal` 全叢集共用——「沒有 global 就不知道那個目錄是哪個庫，pg_xact 對不上會讓資料列被判成『交易沒成功』」。PIT-025 只說「搬出來了」，沒說**為什麼分不開**。

### (b) 工具本身的坑 — 收了 CLI 那半，漏了語言／執行期那半

清單有 PIT-089~094（codex／zsh／curl）。缺：
- **dataclass 的 eager 求值**（`a76a731`）：「把 `DEFAULT_CONTAINER` 從 module 層 eager 求值改成 `field(default_factory=...)` 延遲求值——否則 .env 缺 WORKSPACE 時會在 **import 時**就炸，連明確傳容器名的呼叫端都被拖下水」。這是 PIT-095（argparse eager default）的**孿生兄弟且早於它**，同一個病在兩個不同語言機制上各發作一次——這個 pattern 本身才是可遷移的知識。清單只有一半，且 `a76a731` 未被任何 anchor 引用。
- **deepseek/opencode 大題目逾時回 0 位元組**（`c94d2fe`）。

31 條契約假設涵蓋充分。唯一補充：`ecc7b78` 記載「向量表名寫死 `text_embedding_3_small_1536d` 導致 entities/relations 兩列恆空」這個歷史 bug 已由 compare-ws 改從 `lightrag_full_*.count` 取數解掉——又一個「恆空」實例。

### 標 `yes` 但實際零程式載體（實跑驗證，四條全錯）

- **PIT-055**（`MINERU_IS_OCR` 必須 true）標 `yes`，錨到 `oracle.py:190-199`——但 `grep -rn "mineru_options" --include='*.py' .` 只回**定義本身**（`oracle.py:190`），零呼叫端。唯一載體是 `.env.example` 的註解。

**`.env.example` 是即將被「文件層重寫」的檔，且 repo 內零程式讀取它**（三份體檢已各自 grep 確認）。這四條是清單裡**最危險的四個標記**——標 `yes` 等於告訴重建者「不用管它，它會活下來」。

### 標 `yes` 但擋板根本不存在

## 5. 拿這份清單當唯一依據，最先撞的牆

**情境：重建第三天，第一份 PDF 進新庫，一切綠燈，但知識庫是空殼。**

逐步：

1. 重建者照 Cairn 流程重寫 `.env.example`（「文件層重寫」的字面意思）。他手上的清單告訴他 PIT-055/056/057/144 是 `survives_teardown: yes`——**不需要特別搬**。
2. 新 `.env` 於是缺 `MINERU_IS_OCR=true`（或設 false）、缺 `MINERU_MODEL_VERSION=pipeline`、缺 `ENTITY_EXTRACTION_USE_JSON=true`、缺 `EMBEDDING_SEND_DIM`。
3. **四個都不報錯**：
   - `is_ocr=false` → 文字層路徑靜默吃掉 x-height 字母（實測 27.6% 的 chunk、1,660 個掉字片段）
   - `model_version=vlm`（MinerU 預設）→ 16/57 表格區域完全空白，連圖片備份都沒有
   - `USE_JSON` 未開 → 本機 4-bit 模型的關係記錄只吐 4/5 欄，**LightRAG 100% 拒收 ⇒ 關係 0 條**
   - 缺 `SEND_DIM` → 索引寫入炸，錯誤訊息是 `Vector count mismatch: expected 10 but got 20`，**完全不指向根因**
4. **既有的閘門一條都不會響**：`A-11` 只比對 manifest 的 `options_signature` 與現行設定是否**相同**，不判斷值對不對（`compat-check.py:405-412`）——整批重解析後兩邊一致，A-11 **重新變綠**。`A-22` 只驗向量表與索引存在，表名由 `EMBEDDING_DIM` 組出，與 `SEND_DIM` 無關。`extract-check.py` 是唯一能看到「關係 0 條」的工具，而它**不在 `daily-check.sh` 的五支裡**（三份體檢各自 grep 確認），且它自己**沒有零值守衛**（PIT-007 給的錨點 `extract-check.py:133-138` 我實讀過，那是 workspace 註解不是零值守衛）。
5. 第一個訊號會是幾週後的「檢索答得怪怪的」——那時候母體已經是新的，**沒有舊母體可以重現歷史數字**（PIT-123 的驗證方法在 v155 退役後已無法執行）。

第 3 步的四條**全部是 `survives_teardown: yes`**。這面牆不是「清單漏了」造成的，是**清單把它們標成安全**造成的——比漏掉更糟。

次要候補兩個（同樣有具體路徑）：① 新 LLM 伺服器 compose 寫成 `LLAMA_ARG_API_KEY` → 埠對整個 Tailnet 敞開，`/health` 綠、dker 通、監控全綠；② 有人 `docker compose -f deploy/llama-qwen36-moe/compose.yaml up` 想「把它納管」——檔頭明寫尚未啟動過、屬重票，而清單沒有這條。

## 一句話收尾

這份清單挖到的 173 條裡，**規則層挖得很徹底，載體層系統性偏差**：它相信文件指到的東西，而這個專案最貴的知識恰好都在沒有人指的地方——一個沒有 compose 的容器、一段被判為死碼的模組、一塊看起來像垃圾的行尾註解、以及 147 個沒有人打開過的 commit 訊息。拆之前最該做的一件不可逆的事：**把 `git log --format='%B'` 全文倒出來存成檔進 repo**，成本五分鐘，而它是唯一一個清完就回不去的載體。
