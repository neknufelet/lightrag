# 制度與節奏：裁決後的營運規則

> 本文是三份獨立設計的裁決結果，不是投票。**勝出骨架＝設計 C「編譯制」**，嫁接設計 A「Probe-or-Drop」與設計 B「工單 ledger 制」的更好部分，每處嫁接都標明來源與採納理由。
> 本輪唯讀，未動任何檔案（`git status --porcelain` 全程為空）。所有斷言附 coder 上可重跑的指令輸出；需要 dker 才驗得了的一律標 `(未驗,推測)`。

**三份設計的代號**

| 代號 | 名稱 | 核心主張 |
|---|---|---|
| **A** | Probe-or-Drop | 先砍規則，留下的全部換成探針；配不出探針的規則不准存在 |
| **B** | 工單 ledger 制 | 不發明新東西，把專案自己的兩個物件（ledger 三態表、canary 基準比對）套到「工作」上 |
| **C** | 編譯制 | 制度只以「資產＋消費者＋排程」三件套存在；缺一就退化成文件 |

**為什麼 C 當骨架**：它是唯一從專案**現有能跑的機制**歸納出通用公式的設計，而那個公式可以直接檢驗任何一條規則是不是真的。A 的診斷最狠但砍過頭；B 的落地細節最實但缺一個能一句話說完的判準。C 的三件套同時是診斷工具、設計約束、和驗收標準——這是骨架該有的性質。

## 一、現制診斷（人話）

### 1. 機器守資料守得很緊，守制度完全沒有

`scripts/daily-check.sh` 全文只呼叫五支：`compat-check`（第 30 行）、`canary`（39）、`scan-partial`（46）、`systemd-units verify`（59）、`run-tests.sh`（73）。這五支每天 08:30 由 systemd timer 逼著跑，紅燈打 ntfy，腳本自己掛掉還有獨立備援單元。資料層的免疫系統是完整的。

制度層是零。`ls .git/hooks/ | grep -v sample` 無輸出、`.github/` 不存在、`.pre-commit-config.yaml` 不存在——**藍桶第 8 條「無測試不得合入主線」在這個 repo 沒有任何機器擋門**，全靠 commit 訊息自報。而沒有任何東西阻止一次測試沒過、訊息照樣寫「全綠」的 commit 被提交。這正好落在鐵則 9（驗證再斷言）要治理、自己卻沒工具兜底的同一個洞裡。

### 3. 寫得最精細的那幾條把關動作，剛好是空的

- **終審雙軌的 opus-cold 席**：`CLAUDE.md:125,146,158` 定義得極具體（冷啟動分身、雙軌 BLOCK 不可推翻、指揮不得推翻）。實測 `git log --all --format='%B' | grep -ic 'opus-cold'` = **0**，母體是全庫 **177** 個 commit。它從定義以來一次都沒被叫過。**原因不是紀律鬆，是設計跟額度打架**：`CLAUDE.md:167` 自己寫「重活優先擺 OpenAI／DeepSeek 池」，而終審雙軌本身就是重活，卻被要求動用最吃緊的池。
- **重票觸發清單「不由指揮心證」**：判定手段本身仍是心證。唯一留下紀錄的判錯（`docs/log_20260803.md:237`「實際 diff 416 行命中觸發清單 #7，本來就該是重票」）是靠人事後重算 diff 才發現的。
- **「推出去之後不得 `--amend`」**：這條規則是踩雷之後才補的。`CLAUDE.md:82` 記載的事故裡自承「這次 git 有報錯是運氣」——擋下它的是 git 的 fast-forward 保護，不是本專案的任何制度。
- **`AGENTS.md:76`「每有實質進展記 LOG 一則」**：最近 8 個 commit 裡 `e017a8a`（「定案：只用一個庫」，一個真決策）、`ddeb279`、`c9ebc69`、`23312c5` 四個對 `cairn/` 零改動。而 `cairn/LOG.md` 最新標頭是 `## 2026-08-05`，但 `git log -- cairn/LOG.md` 顯示那段內容由 `cfba960`（08-06 21:30:46）與 `3e4b9fe`（08-06 21:33:38）寫入，且 `git log --format=%ad --date=short | sort | uniq -c` 顯示 **2026-08-05 全天 0 個 commit**。日期標頭是回溯的。

### 4. 專案已經發明了正確答案，只是把它當成一次性補丁

五個**同構**的機制已經在跑，而且形狀完全一致：

| 機制 | 資產 | 消費者 | 排程 |
|---|---|---|---|
| 已查證紀錄 | `tests/verified-findings.json`（3 筆） | `scripts/pp/findings.py` → `extract-check.py`，且 `_DRIFT = 0.5` 時自動改說「要重查」 | 手動（缺這一腳） |
| 模型易腐觀察 | `tests/model-observations.json` | `compat-check.py` A-23，不一致就 hard FAIL | daily-check |
| 規則退休訊號 | `compat-check.py:181-182` note 直接寫「chart 已被 LightRAG 認得，轉換規則可以退休」 | A-24 斷言自己 | daily-check |
| 規則漂移 | `tests/canary-baseline.json` | `postprocess.py canary` | daily-check |
| 探針的探針 | `deploy/systemd/*` | `systemd-units.py verify` 比對 /etc 與 repo | daily-check |

**公式是：知識 → 機器可讀資產；資產 → 一支在對的時機讀它的消費者；消費者 → 掛在會自己跑的排程上。三者缺一，就退化成文件。**（來自設計 C，這是它勝出的理由。）

制度層目前一條規則都沒套用這個公式。而專案裡已經有一個活生生的反證：`tests/symbol2-results.json` **沒有任何消費者**（逐檔 grep：`canary-baseline`→`postprocess.py`、`model-observations`→`latex_fix.py`+`compat-check.py`、`scan-partial-baseline`→`scan-partial.py`、`symbol1-answer-key`→`symbol-hits.py`、`verified-findings`→`findings.py`+`extract-check.py`、`symbol2-results`→**無**）。寫了、進版控了、沒有任何東西會讀它。

## 二、要砍掉的

判準只有一句（設計 A 的入場閘門，我採納為全案的第一條規則）：**一條規則若沒有「資產＋消費者＋排程」三件套，它就不是規則，是願望。願望可以留在文件裡當歷史，但不得被引用為「這件事有人在守」。**

### 砍：opus-cold 常設席（降級為 PO 可指定的逃生門）

- **沒被執行的證據**：`grep -ic 'opus-cold'` = 0 / 177 個 commit。同期 `fable`、`deepseek`、`sol`、`terra` 都找得到實際引用。
- **裁決來源**：診斷取設計 C（結構性矛盾：終審雙軌本身是重活，卻要求最貴的池）；結論取設計 A（廢除常設席）；逃生門取設計 B（保留為 PO 可指定的升級選項）。
- **不採納設計 C「把 opus-cold 職責砍到只剩親跑貼輸出」的理由**：那個職責與 dker 實跑完全重疊，留著只會讓兩個東西看起來像兩道關。設計 A 的論證更根本——`pp/eyes.py` 擋「兩雙眼睛是同一個模型」，因為同模型的系統性誤讀會原樣重現；同池同模型的冷啟動分身在流程層違反了本專案在資料層已經懂的原理。**真正獨立的第二來源是 dker 的實跑輸出：機器不會為了讓流程過而說謊。**
- **廢除後的風險**：真出現一張需要 Anthropic 長推理視角的重票時沒有現成席位。緩解：sol（OpenAI 池，讀 diff 與長推理擺這裡）＋ deepseek（不同家族對抗）＋ 機器席（`verify-debt` 帳本＋`ticket-class` 重跑）。**殘餘風險誠實標示：審查的「深度」確實下降；但對照組不是「opus-cold 認真審過」，是「它一次都沒被叫過」，淨值為正。**
- **保留的逃生門**：`碰資料`（觸發清單 #6）時 PO 可指定啟用。理由見下一條。

### 砍：`CLAUDE.md` 前綴註冊表的「狀態」欄

- **證據**：`CLAUDE.md:237-245` 自 `1ad2224`（2026-08-03 11:13）建立後逐字未改；四條線的狀態與 `NEXT.md:266-272` 全部矛盾；範圍欄寫 `REBUILD-0…REBUILD-5` 而 `REBUILD-6/-9` 活在 `scripts/daily-check.sh:12` 與 `tests/test_archive_ledger.py:1`。
- **廢除後的風險**：低。前綴→工作線的對照（穩定資訊）留著，只砍狀態欄，改指向唯一 SSOT。
- **來源**：三案一致。

### 砍：手寫維護的「工作線狀態總表」（改機器生成）

- **證據**：`NEXT.md` 狀態總表有**兩列 `REBUILD`**（`:264` 標完成、`:273` 標進行中）；`REBUILD-10` 在 `:273` 標完成而在 `:179`、`:402` 未打勾，且其驗收條件（清掉 `/data/rag/lightrag`）實測未達成。
- **廢除後的風險**：中。狀態改由 `worklog.py` 從機器檔生成之後，人不能再隨手改一格——這既是好處也是摩擦。緩解：生成器要能保住人手寫的備註欄（藍桶第 2 條 No silent drops）。
- **來源**：三案一致；schema 取設計 C（`OPEN.jsonl` append-only），開線／收線的檢查取設計 A（`line.py` 拒絕無收線指令的開線、拒絕無證據檔的收線）。

### 砍：`AGENTS.md:76`「每有實質進展，在 LOG 加一則」（降級為觸發式）

- **證據**：最近 8 個 commit 有 4 個對 `cairn/` 零痕跡；LOG 標頭 `## 2026-08-05` 由 08-06 的兩個 commit 寫入，而 08-05 全天 0 commit。
- **根因（設計 A 的診斷，我採納）**：這條規則的產出與 `git log` 高度重疊，而 git log 是自動的、LOG 是靠記得的。**兩份重複紀錄裡，靠記得的那份一定先腐爛。**
- **降級後怎麼做**：只在**收線**時記一則，且只記 git log 記不到的東西——為什麼這樣決定、否決了哪個選項、依據。
- **不採納設計 C「每個有 commit 的日曆日都要有標頭」**：08-01～08-04 的密度是 39/38/52/42 commit／日，逐日儀式性條目會把 LOG 灌成第二份 git log。但**採納設計 C 的日期倒掛檢查**——條目日期標頭不得晚於寫入它的 commit 日期。

### 砍：`ledger.py summary`（VERIFY-3）的現行狀態，停用到資料歸檔完成

- **證據**：`NEXT.md:188`「`archive-ledger.py` 寫好了但還沒在 dker 上跑過（舊 20 張體檢表還在…）」；`grep -c 'ledger' scripts/daily-check.sh` = 0（從來不在排程裡）。語料已於 2026-08-04 整批換成 18 份，跑起來會對已不存在的文件狂報 fail。
- **理由（設計 C 的排序原則，我採納為全案優先序第二鍵）**：**假警報比漏報更貴，因為它訓練人忽略警報**——而這個專案的全部防線都建立在「紅燈會被當一回事」上。
- **廢除後的風險**：VERIFY-3 這段時間完全沒人守。可接受，因為它現在也沒在守，只是在製造雜訊。

### 砍：文件裡所有「可計算的計數」

- **證據**：`CLAUDE.md:226` 寫 26 條，實際 21。
- **新規則**：可機讀的事實只准有一份 SSOT，文件只准放指標（「見 `assertions-baseline.json`」），不准寫字面數字；要抄第二份就必須同時交出比對探針。

### 砍不下手的三條，以及為什麼

| 不砍的 | 為什麼砍不下手 | 改法 |
|---|---|---|
| **觸發清單第 6 條「碰資料」** | 它從沒咬過人——但**對不可逆操作而言，「沒出事」不是證據，是尚未到期的運氣**（硬約束 4：資料操作不可逆、沒有備份時代的教訓還新） | **不砍，換層級。** 從流程層搬到寫入點（設計 A 的 `data-write-gate`）。理由：票級判定實測會被判錯（416 行那次）、會被 PO 叫停、會被繞過；寫入點繞不過。本專案已有成功先例——`postprocess.py` 的 `gate_table_html` 掛在寫入點，自動採用與人工裁定走同一道 |
| **重票／一般票二分制** | 設計 A 主張廢除，但它自己也承認會流失「這是一次重要改動」的心理重量感 | **不砍，換判定手段。** 2:1 保留（B、C 皆保留），改由 `ticket-class.py` 讀 diff 機械判定並印出命中條款；`#6`（碰資料）diff 看不出來，改成 CLI 必填宣告，**未宣告＝視為命中**（偏差方向與「只能升檔不得降檔」同向） |
| **鐵則「只增不刪」** | `CLAUDE.md:283` 的字面不可持續（只增不刪的清單會膨脹到沒人讀得完），但**它的用意是對的**，且用意就是藍桶第 2 條 No silent drops | **不砍，拆兩層**：條文只增不刪（歷史層），效力可以停止（執行層）。詳見第七節 |

**另外兩格不是廢除，是「不要求平時維護」**：cairn 的 topic note 與 `Cited.md`（`find cairn .cairn -type f` 只有 `cairn/LOG.md` 與 `.cairn/config.yaml`，自 `65a151a` init 至今零產出）。topic note 保留為**畢業前置**，只在真的要畢業時才建；`Cited.md` 保留為 lazy create（cairn 規格本來就是首次使用才建）。理由：一個從未被使用的層級不是緩衝，是空殼——但把它整個砍掉會讓畢業流程沒有落點（`a23a71a` 直接從鐵則畢業七條、規格要求的「記在 project topic note」那一半結構性做不到）。

## 三、工作生命週期

**三種強制力，分清楚才看得見殘餘風險在哪**（這是本裁決的組織裝置，三份設計都有但都沒明說）：

- **【機器擋】** 沒做就過不去（hook 拒絕、CLI 拒絕）
- **【機器抓】** 動作靠人做，但**遺漏會被帳本或探針事後抓到並每天印一次**
- **【靠人記得】** 沒有任何東西會發現——這一格必須少，且每一項都要說明為什麼工具化不了

| # | 階段 | 觸發 | 誰／哪台機器 | 產出寫進哪 | 離開條件（可驗證） | 誰逼它發生 |
|---|---|---|---|---|---|---|
| 1 | **訊號** | daily-check 紅燈／做事時的實測輸出／PO 指定 | 探針（dker）／執行中的 agent／PO | 收件區一行：一句可證偽的陳述＋`source_ref`（file:line、commit hash、或落地檔路徑） | `source_ref` 打得開（CLI 實際檢查檔案／hash 存在） | 探針那一路【機器擋】；量測與 PO 那兩路**【靠人記得】敲一行 CLI**——沒辦法工具化，因為「我剛剛撞到一件事」這個事件本身在機器上沒有訊號 |
| 2 | **分流** | 收件區有東西 | 指揮（opus） | 四選一寫回：丟棄／掛既有線／開新線／這是知識不是工作（跳到 9） | 決定被寫下且帶理由；判「不做」時必須產生一筆帶 `revisit_when` 的決策紀錄 | **【靠人記得】做這個動作，【機器抓】做錯**：新前綴未註冊→測試紅；收件區項目超過門檻未分流→週報印出 |

**「靠人記得」只剩兩格**（第 1 階段的量測／PO 來源、第 2 階段的分流動作）。兩格都無法工具化的理由相同：**它們的觸發事件在機器上沒有訊號**——「我剛剛撞到一件事」與「這件事值不值得做」都不是系統狀態。降低成本的做法是把它們壓成一行 CLI，並讓漏掉的後果被第 2 階段的機器抓到。

**開工的固定動作也是靠人記得**：跑 `next.py` 看排序後的清單。緩解是把它放進 `NEXT.md:10-13` 那段**本來就每次都要貼**的開場白第一行（設計 B 的做法，成本接近零），並掛 Claude Code 的 SessionStart hook。**明確限制**：SessionStart hook 對 codex／opencode worker 不生效，人自己開終端機也不會跑到——這是真缺口，沒有更好的辦法。

## 五、知識路由

**六問序列。照順序問，第一個 yes 就停，不再往下。**

判準是「下次誰會在什麼情境下需要它」——**時機不會吵，分類會吵**（`AGENTS.md` 已定）。序列的排序原則是**送達時機最精準的排在最前面**（設計 C 的排序法，我採納，因為它讓「同時屬於多類」在結構上不可能發生）。

```
Q1  它是「跑某支檢查、看到某個數字時才需要」的結論？
    → 已查證紀錄類資產（工具超標時自己印出來，不要求任何人記得去找）

Q2  它是「某個外部東西必須保持某個樣子」的假設？
    → 契約斷言類（新增一條 A-##，消費者＝每日排程）

Q3  它綁特定模型／build／版本，換掉會靜靜失效？
    → 易腐觀察類資產（消費者＝A-23 式比對斷言，不一致就 hard FAIL）
       ※ 這類一律不得寫成流程中的自動裁決規則

Q4  它會改變某個可量的數字，或它本身是文件裡宣稱的一個事實？
    → 基準／事實類資產（消費者＝canary、scan-partial、docs-check）

Q5  它決定「下一步做什麼」或「刻意不做什麼」？
    → 待辦／決策類（工作線機器檔；「不做」的條目強制帶 revisit_when）

Q6  它換個領域、換個專案仍然成立？
    → 畢業候選（先寫成專題筆記，再走畢業流程）

以上皆非 → 那天發生了什麼 → 時序流水帳類（只記為什麼、否決了什麼）
真的都不是 → 不記。不記是合法答案，而且是最常見的正確答案。
```

**同時屬於多類的答案，明確而不是「看情況」：序列在前的那格贏，沒有例外、不需要權衡。** 因為序列本身就是按「最早會在什麼場合被需要」排的。

**其餘位置只准放一行指標（路徑＋一句話），不得複製結論正文。** 這一條有機器在守（`docs-check` 的跨檔一致性子功能）。依據是實測過的事故：`chart` 那條規則在三處講法不一致（`docs/precedents-inventory-20260804.md`），以及「20,873 關係」的雙倍計數在 `extract-check.py` 補了 workspace 條件之後仍留在文件裡活著。

**三條硬性限制**

1. **可機讀的事實只准有一份 SSOT。抄第二份就要同時交出比對探針；交不出就不准抄，只能放指標。**（設計 A 的核心規則第 5 條，我採納為全案最重要的一條路由規則。）現存三個違反實例全部已驗：線的狀態（`CLAUDE.md:237-245` vs `NEXT.md:264-272`）、資料根路徑（`CLAUDE.md:25,261,570` vs `paths.py:14`）、斷言條數（`CLAUDE.md:226` 寫 26、實際 21）。
2. **沒有消費者的格不得使用。** 一份不會被任何工具在對的時機印出來的知識資產等於沒寫。實測反例已存在：`tests/symbol2-results.json` 無消費者。
3. **想往鐵則區加一條，必須同時交出「哪支探針會在沒人問的時候喊它」。** 答不出來就進待辦區當觀察，滿一個月沒有第二次事故就刪掉。（設計 A 的入場閘門＋設計 B 的落點元探針，兩者合併：A 提供規則、B 提供守這條規則的探針。）**這一條連本裁決自己都適用**——第六節任何一支探針做不出來，對應的規則就不准寫進鐵則區。

**與文件結構那一組的介面**：本節只規定「這類知識去哪類**容器**」，不指定檔名與版面。所有探針把路徑集中在一個常數（`scripts/pp/paths.py` 已有這個慣例），另一組要搬只需改一處。已存在的工程資產（`tests/*.json`、`compat-check.py` 的斷言）不歸文件結構管——`AGENTS.md` 已定「工程資產不進 cairn」。

**「這個要記到哪」問到第二次就是規則壞了**（`AGENTS.md:83-86`）。落點是工單的沉澱格：commit 時該格不得是 `pending`，被 pre-commit 擋（設計 B 的做法，我採納——**這是唯一能把「記得沉澱」變成 commit 閘門的機制**）。判不出來就填 `unclassified: <一句話>`，週報撿出來。**允許判不準，不允許沉默**——與 `ledger.py` 的三態設計同一條原理。

## 六、要新增的探針

## 七、規則退休機制

### 先拆矛盾

`CLAUDE.md:283` 寫「這一組只會增加，不會刪」。這句話字面上不可持續——只增不刪的清單會膨脹到沒人讀得完，而讀不完的清單等於全部失效。但**它的用意是對的**，而且用意就寫在藍桶第 2 條裡：No silent drops，刪除必須明確說明。

**解法是把「條文」與「效力」分開**（設計 C，三案裡最完整的一個）：

> **條文只增不刪**（歷史層）。**效力可以停止**（執行層）。
> 一條規則退休 ＝ 條文留著、加退休註記、狀態改 `retired`、`superseded_by` 指向取代它的東西（或明寫「前提消失」）。
> **沒有任何一行字被刪掉，所以「只增不刪」逐字成立**；同時「已經不對的規則還在照舊裁決」這個真正的危險被解掉。

### 機器化載體：鐵則的機器鏡像

```
{id, one_line, status: active|observing|provisional|retired,
 evidence_count, evidence: [file:line | commit],
 落點: "程式路徑" | "靠人記得（理由）",
 retire_when, retired_on, retired_because, superseded_by}
```

並由一條測試斷言**「文件裡數得出的鐵則條數 == 鏡像裡 status 非 retired 的條數」**。這正好治 `CLAUDE.md:285` 自己嘲諷過又自己重演的病——本輪實測：`awk` 數出鐵則段共 **8** 條；而鐵則 7 的事故次數 `CLAUDE.md:316` 寫「三次」、`docs/log_20260803.md:42` 寫「踩了四次」。**數字互不相同這件事，本來就是機器一秒能抓的。**

### 退休三步，每步留機器痕跡

1. **喊** — 退休評估腳本判定 `retire_when` 成立，或人提出。進週報。
2. **降級（observing）** — 填 `retire_candidate_since`。**observing 期間規則仍然完全生效**，只是每週被問一次。這一步是刻意的緩衝：本專案的規則多半沒有第二個母體可以驗證「拿掉它會怎樣」。
3. **退休（retired）** — 填 `retired_on`＋`retired_because`＋`superseded_by`，條文加註記。**退休本身是重票**（動閘門判準），走終審。

### 合法的退休理由只有三種

1. **它守的東西已經不存在。** 現成範本：`compat-check.py:181-182`——「chart 已被 LightRAG 認得，轉換規則可以退休」。**退休訊號由探針自己喊，不靠人回頭想**，也不必去追 LightRAG 的 changelog。這是所有規則退休的理想形式（三案一致援引）。
2. **它被一支探針取代。** 規則降級成該探針的說明文字。留會響的那個。本案裡「碰資料要走重票」→ 寫入點閘門、「斷言不准亂刪」→ 只增不減探針，都是這種退休。
3. **它從未被執行、沒出事、觀察期滿。** ——**有硬性排除，見下。**

### 兩條排除條款

- **第 3 種不適用於任何涉及不可逆操作的規則**（碰資料、刪除、reindex、`apply --commit`、寫 DB）。理由：**對不可逆操作而言，「沒出事」不是證據，是尚未到期的運氣**（設計 A，硬約束 4）。這類規則只能走理由 1 或 2 退休——**只有在有東西接手守著它的時候才准退休**。
- **探針不因為「一直沒響」而退休。** 一支從沒響過的探針看起來像廢物，實際上可能正是唯一守著某個從未失效的東西的人。實測反例：A-16「沒有未知的項目型別」本來就抓得到 `chart`，但被 `if a.doc:` 關著，「從專案開始到發現為止一次都沒被喊過」——當時看起來就像一支沒用的探針，而它守的東西正在失效（184 個 chart 分散 11 份文件）。**探針沒響有兩種原因：沒事，或它壞了。分不出來就不准退休。**（設計 A。）
  - 配套：`zero_for_days` 型的退休判準必須同時標 `zero_is_expected: true|false`。canary 的 `latex_vetoed` 現在是 0 而且**本來就該是 0**——這一格分不清楚就會建議退休一條正在正確工作的規則（設計 C）。

### 證據強度也要退休：本專案目前最大的雙重標準

`CLAUDE.md` day-1 就對後處理規則訂了明文門檻——「只有 1 份的很可能是那份文件的巧合」——但**這把尺從未套用到鐵則本身**。逐條核對：鐵則 6 有 184 個 chart 散布 11 份文件的規模、鐵則 5 有 5 個症狀的可核對清單；鐵則 3（用 oracle 問不要推測）與鐵則 8（重解析不是同一份東西）各只有 1 次單一事件、1 份文件。

**規則**：`evidence_count == 1` 的條目自動標 `provisional`，每月問一次「還是只有一份證據嗎？升格、維持、或降回易腐觀察」。**不刪任何東西、不降任何一條的效力，只是讓證據強度變成一個可見的數字。** `provisional` 的條目**不得被引用來否決別人的提案**——這是它與 `active` 唯一的效力差別。

**新規則的晉升門檻**：≥ 2 次獨立事故，**或** 1 次事故＋一支會響的探針。兩者都沒有的，先進觀察區。已在清單裡而不滿足的**不追溯降級**（追溯會製造第二次爭論），但下次被引用或修改時要補齊落點——由落點元探針的「靠人記得」計數施壓。

## 九、刻意不做

1. **不設計任何需要「兩個人互相檢查」的環節。** 硬約束 1：只有一個人。所有審查席位一律是 AI worker，且必須留機器痕跡——因為 AI 席位唯一的失效方式就是「根本沒被叫」，而那件事只有留痕才看得見（實測：`grep -ic opus-cold` = 0 / 177）。
2. **不新增任何「靠人記得去讀」的文件段落作為執行機制。** 三件套齊了才進執行層；缺的留在文件裡當歷史，但不得被引用為「這件事有人在守」。
3. **不設計會常態消耗 Anthropic 額度的制度。** 讀 diff 與長推理全歸 sol（OpenAI 池），對抗找碴歸 deepseek。這不是妥協，是修掉一個結構性矛盾——現行規則同時要求「終審雙軌」與「重活優先擺 OpenAI／DeepSeek 池」，而終審雙軌就是重活。
4. **不碰檔案結構。** 哪個結論該住哪個檔、`CLAUDE.md` 怎麼瘦身，是平行 workflow 的題目。本文只規定容器類型、資產 schema 與消費者；所有探針的路徑集中在一個常數，另一組要搬只需改一處。
5. **不做會產生假警報的探針。** 每支上線前先跑現況、把既有存量設成 baseline 起點（驗證債的 `baseline_from` 就是這條的實作）。**寧可探針第一天綠，也不要它第一天滿江紅然後被關掉**——`ledger.py summary` 是活生生的反例。
   - **與「紅著上線」不衝突**：紅著上線指的是**探針必須能抓到一個具體的、已知的現存漂移**（證明它會響）；設 baseline 指的是**不把歷史存量債一次倒出來**（避免噪聲淹沒訊號）。前者證明有效，後者控制音量。
6. **不做只在指定目標時才跑的檢查**（鐵則 6）。所有新探針預設全母體；收合輸出時必須報「幾項通過未列出」。
7. **不把制度層探針做成依賴 `.env` 或資料庫。** 除了文件層 `--live` 與畢業回指這兩支本質上需要現值的，其餘全部要在 coder 上完整跑得起來且完整可測——**制度的健康不該取決於能不能連上 dker**。coder 上跑到 dker-only 的部分時回「驗不了」而不是「通過」。
8. **不憑空定門檻。** 所有數字標成猜測值並寫進 `derived_from`，一個月後用實測分佈重定。**本輪明確分開哪些是量的、哪些是推的**：commit 密度 39/38/52/42/6、`grep -ic opus-cold` = 0、A-## 唯一數 21、「dker 實跑」9/177、寬鬆比對 66/102 都是量的；14 天過期門檻是從密度推導的；容差與 `zero_for_days` 是拍的。
9. **不在這一輪動任何檔案。** 本輪是規則設計（硬約束 7）。實作本身要走它自己設計的流程——**第一張單會命中觸發清單 #5（動測試語義）與新增的 #8（動探針），因此是重票。**
10. **不承諾這套制度不會腐爛。** 它自己就是一堆規則，所以它自己也走第七節的退休機制：每支探針帶 `retire_when`，每個門檻一個月後重定，落點元探針守「規則必須有落點」。**誠實標示一個沒堵住的洞**：落點元探針只驗落點**存在**，不驗落點**有效**——一支永遠回 True 的測試也能通過它。唯一的部分緩解是「紅著上線」原則。
