# 重抽前的檢討

重抽會刪掉現有圖譜再重建，約兩個半小時，期間查詢查不到東西。**動手前把兩件事
列清楚**：還沒做完的，以及這一段自己踩過的線。

---

## 一、抽取之前還要做什麼

按「不做會怎樣」排序，不是按工作量。

| # | 事項 | 不做會怎樣 |
|---|---|---|
| 1 | **`postprocess.py apply` 對 6 份實跑** | 消音規則只算過 `plan`、沒真的套用。不跑就等於參考文獻照樣進索引，**這次重抽白費** |
| 2 | **重新載入 `acoustics.yml`** | 規則 2（兩級標籤）與 3（命名）是套用之後才改的，容器裡跑的還是只有兩條的舊版 |
| 3 | **pg_dump 備份** | 沒有退路。8/8 換 embedding 時有做 142 MB 的 dump，這次規模更大（規則全換） |
| 4 | **決定 2017 那篇放不放行** | 頁面尺寸容差改好之後它 preflight 已通過。要進就趁這次一起抽，否則之後單獨抽一次又是一輪 |
| 5 | **記錄「這批是用哪版規則抽的」** | 目前**沒有任何東西記錄**。解析那側有 `options_signature`（A-11 在守），抽取這側沒有對應物 ⇒ 之後新進的文件用新規則、舊的用舊規則，圖譜混著兩代而**沒有紅燈** |
| 6 | 更新 canary 基準 | 每天紅燈。但**必須在重抽之後**做，否則要更新兩次 |

第 5 項是這份清單裡唯一「現在不做、之後補不回來」的：重抽當下才知道用的是哪個
版本的規則檔，事後只能靠推測。

## 二、這一段踩過的線

26 個 commit。下面每一條都是**實際發生過**的，不是假想的風險。
分成「同一個病重複犯」與「單次」兩組——前者才需要寫成規範。

### A. 秘密進了輸出　—— 第三次，而且正解早就寫下來了

**發生什麼**：`docker inspect llama-qwen36-moe --format '{{join .Config.Cmd " "}}'`
把整條命令列印出來，裡面含 `--api-key <值>`。後來我寫比對腳本時加了遮蔽函式，
但它只遮「含 `api-key` 字樣的那一格」，而值在**下一格**，於是又印了一次。

**為什麼這是第三次**：`cairn/secrets-handling.md` 已經寫過結論——
> 「先取出再遮蔽」的設計本身就是錯的，正確做法是列名用 `cut -d= -f1`，
> 用值就讓值沒有機會進入輸出。

我讀過那份文件，然後用同一個錯的形狀又做了一次。**知道規則不等於套用規則。**

**規範**（可執行）：

```
凡是會吐出「整包設定」或「整條命令列」的指令，一律先過濾再印，不要印完再遮：
  ✘ docker inspect --format '{{join .Config.Cmd " "}}'
  ✘ env | grep -v KEY                      ← 漏一個樣式就全洩
  ✔ docker inspect --format '{{index .Config.Cmd 13}}'      只取要的那一格
  ✔ grep -E '^KEY=' .env | cut -d= -f2-     只取指定的鍵
比較兩個秘密是否相同，用雜湊不用值：sha256(v)[:8]
```

### B. 離開碼抓錯地方　—— 兩次

**發生什麼**：`cmd --json | python3 -c '…'; echo "rc=$?"` 抓到的是**管線最後
那支**的離開碼。因此我報過「compat-check 整支 rc=0」，實際是 2；後來又報過
「freshness rc=0」，實際是 2。兩次都因此漏掉真的紅燈。

第二次發生時，第一次的教訓已經寫進當天的 commit 訊息了。

**規範**（可執行）：

```
管線後面接 $? 一律無效。要離開碼就先存：
  ✘ cmd | tail -5; echo $?
  ✔ cmd > /tmp/out 2>&1; rc=$?; tail -5 /tmp/out; echo "rc=$rc"
```

### C. 自己算「應該是多少」，而不是問做決定的那一方　—— 三次

| 我算的 | 事實 | 錯在哪 |
|---|---|---|
| 容器啟動時間 vs commit 時間 ⇒ 誰要重建 | compose 自己說的 | 四台答錯兩台，含一個**漏報** |
| `compose config --hash` vs 容器標籤 | `up --dry-run` 說的 | `config --hash` **不把 `env_file` 算進去** |
| 每段 chunk 約 600 token | tokenizer 數的 1,818 | 錯 3 倍，結論因此完全相反 |

三次都是同一個形狀：**有權威來源，但我自己重算了一份**。而自己算的那份永遠會
跟真正的決策者漂移——差別只在什麼時候被發現。

**規範**：

```
要問「系統會怎麼做」，就問做決定的那個東西，不要自己重算它的邏輯：
  要不要重建容器  → docker compose up -d --dry-run
  伺服器開幾個 slot → 啟動 log 的 n_slots，不是設定檔
  這段多少 token   → 該系統自己的 tokenizer
  這份文件的結構   → 解析器給的 content_headings / sub_type
自己算的版本只能當「交叉驗證」，不能當答案。
```

### D. 統計數錯欄位，報出看起來合理的假數字

**發生什麼**：參考文獻消音第一版報「0.05%」。查下去發現參考清單的型別是 `list`、
內容在 **`list_items` 陣列**裡而 `text` 是空的，我只數了 `text`。實際是 **8–23%**。

危險的不是數字錯，是 **0.05% 看起來像「這條規則沒必要做」**——差一點就據此放棄。

**規範**：報比例之前，先確認分子與分母都涵蓋了「內容實際存在的欄位」。
對陌生的資料結構，先把一筆完整印出來看欄位，不要假設內容在 `text`。

### E. 啟發式的結果直接當數字用

**發生什麼**：用「年份密度」估參考文獻佔比，得到 40%，並且已經對外說出口。
改用解析器給的 `content_headings` 重數是 **10%**——方程式編號被誤判成年份。

**規範**：啟發式可以用來**找**，不能用來**報**。要報數字，先用權威訊號覆驗。

### F. 已經有規矩、我沒遵守（各一次）

- **寫死 `localhost`**：`.env.example` 明寫「服務綁定位址，腳本一律從這裡讀，
  不要寫死 localhost」，而我新寫的 `context-budget.py` 就寫死了，第一次跑
  Connection refused。
- **寫死會過期的數字**：把語料寫成「9 篇」，實際 5 份——**而第 2 批正在做的就是
  根治這個病**。
- **引用不存在的腳本**：註解裡指向已刪除的 `scripts/llm-bench.py`。

三條都已經有規矩，缺的是**執行者**。第三條被 pre-commit 擋下了（`test_no_dead_script_refs`），
前兩條沒有——所以它們過了。
