# 備份設計

## 兩份備份，各防一種災難

```
每日 04:00        完整冷備份 → 本機複本 + restic 上傳 Google Drive
按下「全部開始」   還原點     → 只有本機複本，不上傳
```

**它們防的東西不同，所以做法不同：**

| | 防什麼 | 要多久 | 上傳嗎 |
|---|---|---|---|
| 每日 | 硬碟掛了、機器沒了 | 停機十幾秒 + 上傳很久 | 要 |
| 還原點 | 這一批放錯檔案了 | 停機十幾秒 | **不要** |

還原點不上傳是刻意的：你要退回去用的是**本機那份**，不會去 Google Drive 拉。
而 2026-08-10 量到上傳 4.3G 要約 87 分鐘 —— 等它等於讓人按下按鈕後盯著
「還原點建立中」一個半小時，而那段時間買到的東西對這個用途一點用都沒有。

⚠ **還原點只保留最新一份。** 下一批會 `rm -rf` 再重建，上一批的就沒了。
它保護的是「這一批」，不是歷史。

## 為什麼都要停機

`backup-cold.sh` 的檔頭寫著理由，這裡不重複，只留結論：

> 跑著的資料庫，資料目錄裡的檔案是不同時間點的碎片，抄回來可能起不來、或起得來
> 但資料是壞的。停掉之後檔案就一致，**而且還原只是「停掉、換回目錄、啟動」**——
> 不需要任何特殊工具，也不需要一支沒人測過的還原腳本。

**停機是為了讓還原路徑保持簡單。** 熱備份省下的十幾秒，代價是還原時要一套沒人
驗過的工具。

上傳是服務啟回來之後才做的，不影響使用。停機窗只有「停容器 → 複製 → 起回來」
那一段，**2026-08-10 實測 77 秒**：

```
19:19:57  停服務
19:20:58  複製到 /data/lightrag-coldstage（排除 models/）
19:21:13  複製完成，14 秒
19:21:14  服務已恢復
```

⚠ **複製只佔 14 秒，其餘 61 秒是容器停下來的時間。** 只看「複製完成，14 秒」那一行
會低估五倍 —— 使用者感受到的是 77 秒查詢打不到。

那 61 秒還可以再指得更準。同日 20:35 那次：

```
20:35:14  停服務
20:36:14    停 kbapi-acoustics_v2      ← 整整 60 秒
20:36:15    停 lightrag-acoustics_v2   ← 1 秒
20:36:15    停 lightrag-postgres       ← 0 秒
20:36:19  複製完成，4 秒
20:36:20  服務已恢復                    ← 全程 66 秒
```

`docker stop -t 60` 的 60 秒是**寬限期**，容器自己收到 SIGTERM 就結束的話不會用滿。
kbapi 每次都用滿 ⇒ **它沒有處理 SIGTERM，是被 SIGKILL 砍掉的**。

⇒ 停機窗的 90% 是這一個容器，而且它每次都是被硬砍的。修它比修任何其他一段都划算
（見 NEXT）。

## 排除 `models/`

`models/hub` 是 HuggingFace 的權重快取（BGE-M3 與 reranker），2026-08-10 佔
11G 裡的 6.4G，而 **Infinity 啟動時會自己重新下載**。

⚠ **還原時不能整個目錄換掉**，否則權重會一起不見。用覆蓋的方式，或先把
`models/` 留著。這一條也印在 `--stage-only` 的輸出裡。

## 還原怎麼做

```
1. 停掉容器      kbapi → lightrag → postgres（順序：先停用它們的）
2. 把複本覆蓋回 /data/lightrag     ⚠ 覆蓋，不是整個換掉（models/ 不在複本裡）
3. 啟動          postgres → 等 pg_isready → kbapi、lightrag
4. 確認          份數、compat-check、審核台打得開
```

複本在哪：

```
每批的還原點   /data/lightrag-restorepoint
每日的暫存     /data/lightrag-coldstage      （上傳成功後會被清掉）
異地           restic repo：rclone:gdrive_LIH:restic_rag_db
```

## ✅ 本機還原點：2026-08-19 實走驗過

**這條路從 2026-08-10 起就標著「從來沒有人走過」，今天走了。** PO 要求在新庫
只有 3 份文件時測 —— 那是代價最低的時刻（丟了重解析只要幾分鐘）。

```
                還原前      還原後
文件              3           0
段落             48           0
實體            943           0
關係            925           0
收件匣            0           3      ← 三個檔跟著回來
work/parsed       3           0      ← 解析成果也回到還原點的狀態
models        49 檔 6.4G   49 檔 6.4G ← 一個檔都沒少
審核台          200         200
kbapi                {"workspace": "rag_acoustic", "documents": []}
```

四步完全照上面那張表走，指令是：

```
docker stop -t 60 kbapi-… lightrag-… postgres-…
sudo rsync -a --delete --exclude='models/' --exclude='lost+found' \
     /data/lightrag-restorepoint/ /data/lightrag/
docker start postgres-… ; 等 pg_isready ; docker start lightrag-… kbapi-…
```

⚠ **`--exclude='models/'` 是整條指令裡最重要的一段。** 還原點裡沒有 models，
少了那個排除、又帶著 `--delete`，6.4 GB 權重會一起消失。上面「還原時不能整個
目錄換掉」那句警告是真的，實測時特別確認過 49 個檔一個沒少。

⚠ **異地那份（restic → Google Drive）仍然沒有人驗過。** 這次驗的是本機還原點。
兩者防的災難不同：本機那份防「這批放錯檔案」，異地那份防「機器沒了」。
**不要因為這次驗過就以為兩個都通了。**

## 兩個戳記，不能共用

```
/data/lightrag/.backup-cold.stamp        「這個狀態已經上傳到 restic 了」
/data/lightrag-restorepoint.stamp        「本機現在有一份這個狀態的複本」
```

指紋沒變就跳過、不停機 —— 但**兩種模式問的是不同的問題**，所以看不同的戳記。
還原點那條除了比指紋，還要確認**目錄真的還在**：戳記是複本的收據，不是複本。

⚠ 2026-08-10 這兩件事共用一個戳記，結果是**還原點永遠建不出來**：

```
04:00  備份 → 上傳成功 → 寫戳記 → rm -rf 掉本機複本
10:00  放 PDF、按全部開始 → 指紋沒變（中間沒抽過東西）→ 跳過
       ⇒ 本機還原點不存在，唯一的安全網在 Google Drive
```

這不是邊角案例，**是每天的常態**。當天實測：戳記與現在的指紋逐字相同，
而 `/data/lightrag-restorepoint` 不存在 —— 這個功能從加上去起一次都沒有運作過。

判斷失誤的形狀值得記下來：當時的推理是「上一份備份本來就已經是這一批的還原點了」，
這句話單獨看是對的，**錯在沒有把「上傳成功會刪掉本機複本」接上去**。兩個各自正確
的事實中間少了一步。

`tests/test_backup_restore_point.py` 用假的 docker／sudo 把腳本真的跑起來 ——
這是控制流程的錯，讀原始碼比對字串抓不到它。

## 互斥鎖

兩支備份不能同時跑：一支在複製、另一支把服務停掉，複製出來的東西是不是一致的
沒有人知道，而且**不會有錯誤訊息**。`backup-cold.sh` 用 flock 擋，第二支直接
退出（exit 6）。

2026-08-10 當天就用上了：每日排程的上傳還在跑，而進料的還原點正要觸發第二支。

## 2026-08-10 的血淚：目的地從來不存在

**`backrest` 設定裡的 `rag-db` 倉庫從來沒有被 `restic init` 過。**

```
Google Drive 根目錄   只有 Learning_DB，沒有 restic_rag_db
```

那兩個 rag 相關的排程每 4／6 小時跑一次，**從設定的那天起一次都沒有成功過** ——
而沒有人發現，因為沒有人去看過目的地。

它造成的假象：

```
上傳 62 分鐘不結束     → 以為是「檔案太大」，差點拿它當調 timeout 的依據
指紋沒寫、暫存沒清     → 腳本其實是對的，它驗證了、發現快照不在、所以拒絕宣稱成功
```

⇒ **腳本的驗證步驟救了這件事。** 如果它上傳完就寫指紋、就清暫存，這個洞會一直
存在而且看起來一切正常 —— 那正是「先驗證才收尾」這個順序存在的理由。

⇒ 另一半的教訓是**檢查目的地本身**。所有的訊號（有排程、有容器、有設定、
有在跑）都指向「備份正常」，唯一沒被問過的問題是「東西真的到了嗎」。

## 量到的數字（2026-08-10）

第一次成功的完整備份（19:19:56 → 20:23:44，共 63 分 48 秒）：

```
資料量        11G → 4.207 GiB（排除 models）
停機窗        77 秒（其中複製 14 秒，停容器 61 秒）
上傳          1:01:41，實際約 9.3 Mbps
repo 增量     3.162 GiB（壓縮後存 1.850 GiB）
快照          98a2e61f，tag ts:20260810T191956
上限          TimeoutStartSec=7200（120 分鐘，留約 47% 餘裕）
```

⚠ 上傳前用「6.6 Mbps → 87 分鐘」估過，實測 62 分鐘 —— **估的那個數字是拿失敗中的
那次算的**（它在對一個不存在的 repo 空轉）。當時拿它當調 timeout 的依據是巧合對了，
不是推理對了。

⚠ **上限不能拿掉**：一支永遠不結束的備份會讓 timer 停在那裡不再觸發
（當天實測過那個症狀 —— `systemctl list-timers` 的 NEXT 是空白）。

**第一次要傳全量，之後 restic 只傳差異**（內容去重），所以上限大只影響第一次。
