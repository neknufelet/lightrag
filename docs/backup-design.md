# 備份設計

## 兩份備份，各防一種災難

```
每日 04:00        完整冷備份 → 本機複本 + restic 上傳 Google Drive
按下「全部開始」   還原點     → 只有本機複本，不上傳
```

**它們防的東西不同，所以做法不同：**

| | 防什麼 | 要多久 | 上傳嗎 |
|---|---|---|---|
| 每日 | 硬碟掛了、機器沒了 | 停機十幾秒 + 上傳很久 | 要 |
| 還原點 | 這一批放錯檔案了 | 停機十幾秒 | **不要** |

還原點不上傳是刻意的：你要退回去用的是**本機那份**，不會去 Google Drive 拉。
而 2026-08-10 量到上傳 4.3G 要約 87 分鐘 —— 等它等於讓人按下按鈕後盯著
「還原點建立中」一個半小時，而那段時間買到的東西對這個用途一點用都沒有。

⚠ **還原點只保留最新一份。** 下一批會 `rm -rf` 再重建，上一批的就沒了。
它保護的是「這一批」，不是歷史。

## 為什麼都要停機

`backup-cold.sh` 的檔頭寫著理由，這裡不重複，只留結論：

> 跑著的資料庫，資料目錄裡的檔案是不同時間點的碎片，抄回來可能起不來、或起得來
> 但資料是壞的。停掉之後檔案就一致，**而且還原只是「停掉、換回目錄、啟動」**——
> 不需要任何特殊工具，也不需要一支沒人測過的還原腳本。

**停機是為了讓還原路徑保持簡單。** 熱備份省下的十幾秒，代價是還原時要一套沒人
驗過的工具。

停機窗只有本機複製那一段：**2026-08-10 實測 14 秒**（排除 models 之後）。
上傳是服務啟回來之後才做的，不影響使用。

## 排除 `models/`

`models/hub` 是 HuggingFace 的權重快取（BGE-M3 與 reranker），2026-08-10 佔
11G 裡的 6.4G，而 **Infinity 啟動時會自己重新下載**。

⚠ **還原時不能整個目錄換掉**，否則權重會一起不見。用覆蓋的方式，或先把
`models/` 留著。這一條也印在 `--stage-only` 的輸出裡。

## 還原怎麼做

```
1. 停掉容器      kbapi → lightrag → postgres（順序：先停用它們的）
2. 把複本覆蓋回 /data/lightrag     ⚠ 覆蓋，不是整個換掉（models/ 不在複本裡）
3. 啟動          postgres → 等 pg_isready → kbapi、lightrag
4. 確認          份數、compat-check、審核台打得開
```

複本在哪：

```
每批的還原點   /data/lightrag-restorepoint
每日的暫存     /data/lightrag-coldstage      （上傳成功後會被清掉）
異地           restic repo：rclone:gdrive_LIH:restic_rag_db
```

⚠⚠ **這條路從來沒有人走過。** `backup-cold.sh` 自己寫著「**沒驗過的還原路徑等於
沒有備份**」，而截至 2026-08-10 它仍然成立。要驗必須停服務、動資料根，
風險比備份本身高 —— 挑一個有人在旁邊的時間做，不要在進料途中。

## 互斥鎖

兩支備份不能同時跑：一支在複製、另一支把服務停掉，複製出來的東西是不是一致的
沒有人知道，而且**不會有錯誤訊息**。`backup-cold.sh` 用 flock 擋，第二支直接
退出（exit 6）。

2026-08-10 當天就用上了：每日排程的上傳還在跑，而進料的還原點正要觸發第二支。

## 2026-08-10 的血淚：目的地從來不存在

**`backrest` 設定裡的 `rag-db` 倉庫從來沒有被 `restic init` 過。**

```
Google Drive 根目錄   只有 Learning_DB，沒有 restic_rag_db
```

那兩個 rag 相關的排程每 4／6 小時跑一次，**從設定的那天起一次都沒有成功過** ——
而沒有人發現，因為沒有人去看過目的地。

它造成的假象：

```
上傳 62 分鐘不結束     → 以為是「檔案太大」，差點拿它當調 timeout 的依據
指紋沒寫、暫存沒清     → 腳本其實是對的，它驗證了、發現快照不在、所以拒絕宣稱成功
```

⇒ **腳本的驗證步驟救了這件事。** 如果它上傳完就寫指紋、就清暫存，這個洞會一直
存在而且看起來一切正常 —— 那正是「先驗證才收尾」這個順序存在的理由。

⇒ 另一半的教訓是**檢查目的地本身**。所有的訊號（有排程、有容器、有設定、
有在跑）都指向「備份正常」，唯一沒被問過的問題是「東西真的到了嗎」。

## 量到的數字（2026-08-10）

```
資料量        11G → 4.3G（排除 models）
停機窗        30 秒 → 14 秒
上傳速度      約 6.6 Mbps（0.8 MB/s）
4.3G 預估     約 87 分鐘
上限          TimeoutStartSec=7200（120 分鐘，留約 38% 餘裕）
```

⚠ **上限不能拿掉**：一支永遠不結束的備份會讓 timer 停在那裡不再觸發
（當天實測過那個症狀 —— `systemctl list-timers` 的 NEXT 是空白）。

**第一次要傳全量，之後 restic 只傳差異**（內容去重），所以上限大只影響第一次。
