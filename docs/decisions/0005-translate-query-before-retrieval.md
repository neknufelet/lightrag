# ADR-0005: 中文查詢在檢索前轉成英文

* **Status**: Accepted
* **Date**: 2026-08-08
* **Deciders**: PO

---

## Context

語料全是英文論文，而 PO 平常用中文提問。2026-08-08 第一次量這件事：同一個問題
寫成中英兩版，同一份語料、同一個 embedding，用 cross-encoder 對取回的前 10 段
打分取平均——

| 問題 | 中文 | 英文 | 英文高出 |
|---|---|---|---|
| 微穿孔板的聲阻是由什麼機制產生的 | 0.0935 | 0.2528 | +63% |
| 盤繞式通道如何不增加厚度降低共振頻率 | 0.0785 | 0.3145 | +75% |
| 等效網路的阻抗概念跟超材料吸聲體的共通處 | 0.0408 | 0.2662 | +85% |

三件事同時排除掉了其他解釋：

1. **不是題目寫得爛**——中英兩版問的是同一件事，措辭差異不會造成 63–86%。
2. **不是模型選錯**——`text-embedding-3-large@3072` 與 `BAAI/bge-m3@1024` 的落差
   幾乎一樣（63–85% vs 64–86%）。換 embedding 救不了。
3. **不是「認不出來」**——rerank 用的 cross-encoder 跨語言完全沒問題：中文問題
   對英文正確答案打 `0.9134`，對無關雜訊打 `0.0000`。

症狀是**到得了對的房間、找不到對的抽屜**：中文題撈得到正確的論文（問「等效網路」
會回 `C Equivalent Networks`），但撈不到回答問題的那一段。

而**沒有任何東西會發現這件事**。回來的答案有引用、有出處、看起來完全正常，
只是引錯了段落。這是本專案反覆記載的那個形狀：不是壞掉，是安靜地做得比較差。

## Decision

**走向量檢索的查詢一律用英文送出，即使使用者是用中文問的。**
轉換由 agent 在 skill 層做，**不做在 kbapi**。

適用範圍（判準是「這條路徑有沒有 embedding 參與」）：

| 端點 | 走向量檢索 | 要翻譯 |
|---|---|---|
| `/kb/{ws}/search?query=` | ✅ | ✅ |
| `/kb/{ws}/figures?query=` | ✅（底下是 `mix` 查詢） | ✅ |
| `/kb/{ws}/doc/{檔名}`、`/kb/{ws}/docs` | ❌ 照檔名取 | ❌ |

## Rationale

**為什麼是翻譯而不是換 embedding**：換 embedding 的兩個候選落差一樣大，
證明這是向量檢索這一層的性質，不是選型問題。而翻譯把中文題拉到英文題的檔次
（0.05–0.13 → 0.25–0.39，三倍以上），**且完全不用重新進料**——是所有候選裡
成本最低、效益最大的一個。

**為什麼放 skill 不放 kbapi**（原本的建議是 kbapi，PO 質疑後推翻）：

1. **agent 本身就是 LLM，翻譯不用另接服務。** kbapi 要翻譯就得叫 LLM。
2. **kbapi 刻意只用標準函式庫**（`compose.yaml` 明寫「不需要自己建映像」）。
   加 LLM 呼叫會拉進金鑰、逾時、重試，並**逼它自己 build 映像**——違反本專案
   「不 fork、不 build 自己的映像」那條。
3. **agent 能用領域術語轉，機器翻譯不能。** 盤繞式通道是 `coiled-up channel`
   不是 `coiled channel`；聲阻是 `acoustic resistance` 不是 `sound resistance`。
   **術語對不對就是檢索準不準**，這正好是 LLM 強過翻譯 API 的地方。

原本反對放 skill 的理由是「其他呼叫端拿不到好處」，但實際上會查這個庫的就是
agent 走 skill；WebUI 是人在打字，他自己知道要打英文。

## Consequences

- **必須講出實際送出去的英文字串。** 使用者問中文、系統查英文，那是一個轉換；
  不講就是安靜地做了別的事，而引用回來的又是英文段落，看的人無從判斷是「沒撈到」
  還是「查了別的東西」。這一條寫進 skill 的做法區。
- **新的失敗模式：翻錯術語。** 症狀是「查不到而且不知道為什麼」。緩解方式是
  不確定術語時中英各查一次再合併——檢索很便宜（embedding 一個短句）。
- **實作不在本 repo。** 落在 `AI_TOOLS/skills/common/lightrag-search` 與
  `lightrag-images`（commit `6fc7b9a`）。依 `docs/knowledge-routing.md` 的判準
  「誰用它」，那三個 skill 是 Obsidian 的 agent 在叫，不搬回本 repo。
- **本 repo 沒有任何東西會檢查 skill 有沒有照做。** 跨 repo 的規則沒有執行者——
  這是已知缺口，不是疏忽。
