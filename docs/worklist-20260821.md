# 三塊工單（2026-08-21）

PO 的原話：**「從一開始就在那邊沒人守要不就沒亮燈，你到底要怎樣才能亮燈有人守
做一些有用的事情」**。

## 為什麼是這三塊，為什麼是這個順序

**今天一整天的問題是同一個形狀：「沒在守」與「守了沒事」在報告上長得一樣。**

| 當天實例 | 表面 | 實際 |
|---|---|---|
| `test_stack_matches_repo` | 報告寫 `passed` | skipif 路徑過期，在 dker 上也跳過 |
| `canary` | 每天「金絲雀通過」 | 基準是 `{}`，守著 0 份 |
| 體檢表五個閘門 | 一整欄 `-` | 172 份全部從沒量過 |
| `compat` 的 `ok=None` | 燈號是綠 | 那幾條斷言其實驗不了 |

這個專案**本來就有三態**（通過／失敗／驗不了，鐵則 7 那一族），規則寫在文件裡。
問題是實作上一路塌回兩態——遇到不確定就回綠。

⇒ **A 排第一不是因為它最大，是因為沒有它，B 與 C 的改動都是盲改。** 金絲雀是
「改了規則有沒有改壞」的唯一防線，而它現在下線。在它立起來之前動任何判準，
沒有任何東西會告訴你動壞了。

⚠ **量與判可以並行，改判準不行。** 改動都會碰同一套規則與同一個知識庫。

---

## A. 立基準 — 讓「改壞了」會被發現

**要回答的問題**：現在 172 份的處理結果長什麼樣？之後改規則，哪一份的哪個數字變了？

**怎麼知道做完了**：`postprocess.py canary` 的離開碼**不再是「守著 0 份的 0」**，
而且刻意改壞一條規則時它會紅。

### 現況（2026-08-21 實測）

```
$ cat tests/canary-baseline.json
{}
$ ssh florian-dker '…/postprocess.py canary'
金絲雀通過：0 份基準文件的數字都沒變（另有 172 份新文件尚未納入基準）
canary rc=0
```

### 已經知道的坑

- ⚠ **清空基準是對的，沒做後半步才是問題。** commit `4a6e533` 清空舊庫那 319 份
  幽靈是正確處置，訊息裡也寫著「灌完第一批**要記得跑 `canary --update`**」——
  **但沒有任何機制在提醒**。這就是本工單存在的理由。
- `canary --update` **拒絕在空母體上寫**（那道守衛是對的）。現在 172 份 bundle 都在，
  跑得起來。
- ⚠ **`--update` 是「認可現況為正確」，不是「重新整理」。** 172 份只能抽查，
  抽查什麼要先講清楚——至少涵蓋今天已知有問題的那幾份（`HMJ6IDEG_10`、
  `F9FBE9QK`、`ZX35VPDU`），否則等於把已知的壞當成基準。
- 立完之後**離開碼要能區分三態**：基準 0 份、沒有任何 bundle 這兩個分支現在都
  `return 0`（`postprocess.py` `cmd_canary()`），要改成非零的「驗不了」。
  不改的話，下次基準又被清空還是安靜。

### 做完之後要能說出

```
基準份數     172（或抽查後決定的子集，要寫明為什麼）
抽查了哪幾份 以及為什麼是那幾份
空基準行為   實測改成 rc=? 、check-levels 標成哪一態
反向驗證     刻意改一條規則 → canary 真的紅了（附原文輸出）
```

## B. 沒量過要亮燈 — 三個塌成兩態的地方

**要回答的問題**：現在哪些燈號其實是「不知道」在冒充「沒事」？

**怎麼知道做完了**：把今天這四個實例逐一改掉，而且每個都有「改壞它會紅」的證明。

### B-1 體檢表整欄沒量過（860/1376 格）

```
$ ssh florian-dker '…/ledger.py summary --problems'
共 1376 格：通過 508　fail 6　驗不了 2　未設定 860
```

五個閘門（`parse.coverage`、`parse.checks`、`pp.equations`、`extract.format`、
`retrieval.smoke`）172 份全部未設定。總表上它只是一堆 `-`。

⚠ **更糟的是 `parse` 與 `coverage` 每天都在跑**（`daily-check.sh`），量了、結果
寫進 `checks/`，**卻從不回寫體檢表**。所以不是「沒量」，是「量了但表上看不到」。

做法：`ledger.py summary` 加欄級統計，整欄 0 量測要明講；daily-check 跑完把
parse／coverage 的結果經**既有的 `record()` 單一入口**回寫。
⚠ `parse.checks` 的 WARN 只回寫 ERROR 層——WARN 佔 96%，直接進表會讓表跟著失去
鑑別力（見 B-2）。

### B-2 parse-check 的 WARN 沒有鑑別力（實測 96%）

```
$ ssh florian-dker '…/parse-check.py'
共 172 份： OK 5 ／ WARN 165 ／ ERROR 2      rc=1
```

判準是「空文字／空表格／空公式任一非空即 WARN」，而零星空 text 塊是 MinerU 對
這批論文的**常態產物**。ERROR 那層仍然準（歷史 2/2，今天這 2 份也各自對應到
真的碎字元）。

⚠ **不要直接把 WARN 關掉。** 先量：165 份的空塊數分布長什麼樣，門檻設在哪裡
會留下幾份。技能文件的「累積兩三份同型再改判準」在這裡同樣適用。

### B-3 測試跳過看不見

`run-tests.sh` 用 `pytest -q`（無 `-ra`），報告只有 `N passed, M skipped`。
`test_stack_matches_repo` 因此靜靜跳過好幾天——它是唯一守著「跑著的 compose 與
repo 一致」的測試，修好之後**立刻抓到真漂移**（部署那份的註解還寫著更早的
`acoustics_v2`）。

做法：加 `-ra`；再加一條「在 dker 上這幾條必須被執行」的斷言。

### B-4 compat 的斷言級「驗不了」在燈號上隱形

`compat-check.py` 的 `ok=None` 刻意不進離開碼（那是對的，驗不了不該擋），但
`latest.json` 只有整支檢查層級的 `unverified`。做法：把數量放進 `unverified`
附註（如 `compat: 2 項驗不了`），**不改離開碼**。

### 做完之後要能說出

```
每一項      改前長怎樣 → 改後長怎樣（附原文輸出）
反向驗證    刻意製造那個情境 → 真的亮燈了
沒動什麼    尤其 WARN 門檻若沒動，要說為什麼
```

## C. 兩個會反覆咬人的判準

**要回答的問題**：哪些判準會在 PO 的**正常操作**下製造假失敗或漏報？

**怎麼知道做完了**：兩個都有回歸測試，而且測試在修之前是紅的。

### C-1 無主 hard 失敗會殺掉無關的整批（兩天兩次）

```
2026-08-20 00:49  1 份陪葬（XVD6N97J，其實已 processed）
2026-08-21 01:22  10 份陪葬（HMJ6IDEG_03..12，其實都已 processed）
```

`hard_failing_documents()`（`scripts/intake.py:1009`）用「檔名是不是 `what` 的
子字串」分主，**分不到主就當整庫級**，然後 `verify_batch` 把整批標失敗。

⚠ **`ba87447` 只修了一個象限**（驗到一半才進來的新檔 → 名單改成量測後才算）。
第二次是另一個象限：**已被移出語料、但留有殘 bundle 的舊文件**。觸發條件是
「PO 在批次進行中移除或歸檔庫內文件」——那是正常操作。

做法：依斷言 ID 區分「文件層（A-10～A-16，`what` 都帶檔名）無主」與「真整庫層
（A-19／A-26 那種）」。前者另記庫級警報、**不動本批判定**。
⚠ 哪些算真整庫層要跟 PO 對過清單，不要自己定義。

### C-2 刪一份文件沒有「全部清掉」這條路

今天的實例：走「放回收件匣」＋「從收件匣刪除」，而重置**刻意保留解析成果**
（MinerU 要錢，這個設計是對的）。兩個動作各自正確，組合出一個沒有主人的解析包
→ A-13 無主紅燈 → 觸發 C-1 → 10 章陪葬。

做法：補一個「永久移除」動作，一次清乾淨（bundle、crops、ledger、知識庫紀錄）。
⚠ 順序有講究：先從知識庫刪、再清磁碟——反過來的話中途失敗會留下今天這種孤兒。

### 做完之後要能說出

```
C-1  回歸測試（修前紅）＋ 真整庫層的斷言清單（PO 確認過）
C-2  一個指令走完全部四處，且中途失敗不留孤兒
```
