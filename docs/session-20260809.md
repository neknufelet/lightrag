# 這一輪做了什麼

**52 個 commit**，橫跨三件事：把審核台修到不說謊、把語料從 6 篇推到 22 篇、
以及用受控比對量出「溫度」與「推論後端」對抽取品質的實際影響。

⚠ **這份報告裡標「未驗」的都是真的沒驗**，不要當結論用。

## 一、審核台：六個洞，全部是同一個病的變形

起點是 PO 在重抽時當場抓到的：**同一頁上「已處理 4」與「已進知識庫 5」並存**。

根因是同一件事被算了兩次：計數那半有過濾狀態、顯示那半沒有。而 2026-08-04
已經學過一次同樣的教訓，只補在計數上——**兩段程式碼相距 800 行，沒有東西會
發現它們對不上**。

修法不是補那一行，是**改成只有一個真相來源**：分節一律問知識庫，
「已處理」直接等於「已進知識庫」那一節的長度，兩個數字不可能再分岔。

然後在擴充語料時，連續浮出五個潛伏已久的洞：

| 洞 | 為什麼一直沒被發現 | commit |
|---|---|---|
| 排隊中被畫成正在跑 | 之前一次只能按一篇，最多 1 件在這狀態 | `4550ba1` |
| 重啟把排隊中的全判失敗 | 同上，1 件被殺看起來像單一意外 | `4550ba1` |
| 重啟拿「解析中」去問 LightRAG | 那個階段索引本來就沒看過它 —— **問錯對象** | `c8e9a9a` |
| soft 失敗的容忍**字串比對永遠不成立** | compat-check 從沒在這條路上回過 5，直到 A-32 上線 | `55a7fab` |
| 放行失敗不清收件區，**一件堵死全部** | 之前沒有連續 20 件排隊 | `55a7fab` |

**前兩個是我加「全部解析」放大的，後兩個是我加 A-32 引爆的。** 都不是新 bug，
是被新用法照出來的舊 bug。

另外補上 2026-08-08 早上就下的裁決 `4eacaea`（clean 的計畫自動放行），
當時註明「實作留待下一輪」，而我改了狀態機卻只做了另一半——被 PO 當場問出來。

**2017 那篇**：`decision=clean`、`reasons=[]`，只因為重抽拿 `inputs/` 當暫存區
就被判 failed，而 failed 是死路，唯一出口會刪掉 4.0MB 的解析成果。
新增 `failed → planned` 的重試之後**直接救回，沒有再付一次 MinerU**。

## 二、重抽驗收：三條規則，一勝一平一誤讀

```
節點總數   3,137 → 2,032   -35%
```

**這不是崩掉。** 掉的幾乎全是 person／organization（-745）、UNKNOWN（-297）、
content（-149），而 **concept 從 962 增加到 1,133** —— 而且是在多一份文件的
情況下。真正的知識變多了。

- **規則 1（參考文獻的作者機構）：793 → 48，-94%。** 四條規則裡最貴的洞補起來了。
- **規則 2a（位置標記）：96 → 28**，殘留全是小寫 `equation N`。規則已補
  「不分大小寫」（`a2616c1`），但**後來實測證明沒效**（見第五節）。
- **規則 3（不套標題大小寫）**：指標從 89 → 84 看似失敗，實際上目標達成了 ——
  基準裡的例子是 `Cantwell Wj` 這種被 Title Case 破壞的作者名，那類已隨規則 1
  消失。剩下的是**符號本身的大小寫**（`b_0` vs `B_0`），是另一個問題。

**參考文獻消音帶控制組驗收**：從 4 份文件各取一條參考文獻的原文字串去查索引，
命中 0；控制組（真正的正文）命中 1。**0 是真的 0，不是查詢壞掉。**
五篇論文共 262 條參考文獻，一條都沒進索引。

## 四、Modal：兩條路都走通，也都量了

### llama.cpp on A100：只快 2.1 倍，已拆

```
短輸入          並行 1 → 16：  72.6 →  187.1 tok/s   2.6 倍
真實抽取形狀    並行 1 → 16： 401.9 →  848.3 tok/s   2.1 倍
```

每槽 decode 從 72 掉到 13.7 —— MoE 的批次退化：不同序列的 token 挑到不同專家，
批次越大要讀的權重越接近整個 35B。淨賺約 2 倍，不值得，**已拆**。

### vLLM on H100：端到端 12 倍

```
本機（llama.cpp, MAX_ASYNC=2）   每篇約 6 分鐘
vLLM（H100, MAX_ASYNC=16）       3 篇 90～101 秒 = 每篇 30 秒
```

實測到的其他數字：

- **前綴快取命中率 61%** —— 那 1,200 token 的規則提示詞真的只算一次
- 16 個並行只用掉 **7.9% 的 KV**（45.93 GiB ≈ 81 萬 token）
- `max_model_len` 是單一請求的上限**不是預留** —— 這是與 llama.cpp
  （`-c ÷ --parallel` 零和）最本質的差別，所以開到 128k 不吃併發
- 冷啟動 470～562 秒（`torch.compile` 佔 94～163 秒）

⚠ **未驗**：編譯快取 Volume 對冷啟動的實際幫助沒量到（快取鍵隨啟動旗標變動，
兩次都在重填）。

## 五、受控比對：推翻了自己兩個猜測

同樣三篇論文、同樣的規則與解析成果，只變一個東西：

```
                     節點  泛用標籤  人/機構  大小寫組
A llama.cpp temp 1.0  612      11      33      14
C llama.cpp temp 0    673       8      37       9
D llama.cpp temp 0.2  637       0      36       9
E vLLM FP8  temp 0.2  684       7      47       8
F vLLM AWQ4 temp 0.2  680      10      51       9
B vLLM FP8  預設1.0   626       7      50      20
```

### 證實的

**① `person/organization` 的差異是真的**

```
llama.cpp   33、36、37    → 約 35
vLLM        47、50、51    → 約 49
```

三次對三次、範圍完全不重疊。vLLM 這條路穩定多抽四成的人名機構。

**② 大小寫變體是取樣溫度造成的，兩個後端都同意**

```
溫度 1.0   14（llama.cpp）、20（vLLM）
溫度 0.2    9（llama.cpp）、 8（vLLM）
溫度 0      9（llama.cpp）
```

這是整張表裡最紮實的結論。

**③ 抽取一直跑在 temperature 1.0**

llama.cpp 伺服器預設 1.0、LightRAG 的 `DEFAULT_TEMPERATURE` 也是 1.0，
兩邊都沒人壓下來。

⚠ 但 **LightRAG 官方 `env.example` 建議的是 0.9，而且刻意調高**：

> Increasing the temperature setting may help mitigate **infinite inference loops**
> during entity/relation extraction, particularly when using models with more
> limited capabilities, such as **Qwen3-30B**

點名的就是我們這個模型家族。我們三篇的溫度 0 沒有出現迴圈，但**間歇性的失敗
模式不能用 3 篇的樣本排除**。

### 被推翻的（我自己的猜測）

**① 「溫度 0.2 讓泛用標籤歸零」—— 那個 0 是離群值**

```
llama.cpp   11、8、0     ← 自己三次就跳這麼大
vLLM        7、7、10
```

兩邊範圍重疊。我看到 D 的 0 時說「規則 2a 達標了」，**講得太快**。

**② 「FP8 退步是因為均勻量化」—— AWQ 也沒有比較好**

AWQ 是 activation-aware（選擇性保精度，跟本機的 Unsloth Dynamic 同思路），
換上去之後泛用標籤 10、人名機構 51，**都比 FP8 更差一點**。
所以差異不在量化方式。

### 還沒排除的變因

`min_p`：llama.cpp 預設 0.05，vLLM 是 0.0（模型的 `generation_config.json`
沒指定這一項）。`top_k=20`／`top_p=0.95` 兩邊都有，已由 vLLM 的啟動 log 證實：

> Default vLLM sampling parameters have been overridden by the model's
> `generation_config.json`: `{'temperature': 1.0, 'top_k': 20, 'top_p': 0.95}`

在溫度 0.2 下分布已經很尖，`min_p` 大概解釋不了四成的差距，但**沒有實測**。

## 六、方法本身可能比數字更值錢

這一輪建立了一套**可重複的受控比對**：

```
六個隔離的 workspace（同一組 Postgres，靠 workspace 欄位分開）
共用的解析成果（work/parsed）—— 少一個變數，也不重複付 MinerU
共用的抽取規則與 LightRAG 映像 digest
一支比對腳本 /tmp/cmp5.sh
```

**換模型、換量化、換溫度都能用同一把尺量。** 下次 Qwen 3.8 出來，
直接開新 workspace 跑同樣三篇就有對照。

⚠ 隔離靠三樣，缺一不可（`deploy/trial-vllm/README.md` 記著）：
`WORKSPACE`、`HOST_PORT`、**`RAG_STORAGE_DIR`**。第三個最容易漏 ——
scan_spool 共用會讓一邊撿到另一邊的掃描工作，**而且不報錯**。

## 八、還沒做的（依價值排序）

### 能立刻做、而且換模型不會白做

1. **位置標記的確定性清除** —— 提示詞守不住已經實測三次。正規式
   `^(equation|eq\.|figure|fig\.|table|section) ?[\d.]+[a-z]?$` 加型別過濾，
   抽完掃一遍刪節點與關係。**不會誤傷**，沒有真實的聲學概念長這樣。
2. **標題頁作者單位的消音** —— 規則 1 的措辭已經涵蓋 `author/affiliation block`，
   **是模型沒遵守**。跟參考清單一樣往前挪一步，在抽取前就消掉那段文字。
   ⚠ 只能救「在標題頁與參考清單裡的」，散在正文的救不了。

### 要決定的

3. **溫度設多少** —— 0.2 的證據不如我昨晚說的強（那個 0 是離群值），
   但「1.0 太高」是三次都支持的。官方建議 0.9 且警告低溫有迴圈風險。
   **折衷值需要跑重複才敢定**。
4. **要不要用 vLLM** —— 12 倍速度 vs 多四成人名機構。我的看法是那些人名
   可以用第 2 項的消音清掉，值得；但**應該先做完 1、2 再重新比一次**。
5. **重抽** —— 圖譜混著兩代規則。溫度、規則清除、後端三件事應該在**同一次
   重抽**裡一起量，不要各抽一次。

### 審核台的欠帳

6. **每日檢查橫幅只顯示代號**（`compat_rc`），看不出是哪條斷言、更看不到
   A-32 的兩個雜湊。要開 JSON 才知道。
7. **300 份時的顯示會壞** —— 「已進知識庫」逐份列出、`/api/state` 每 3 秒
   吐出全部 job。建議：收件匣／等你看／失敗維持逐份（本來就該是個位數），
   處理中只顯示「正在跑的 + 排隊 N 件」，已進知識庫改成數字 + 最近 10 筆 + 搜尋。
8. **`scan_rc`、`tests_rc` 今早新紅**，還沒查。

### 策略

9. **Qwen 3.8 若近期發布**，上面 3～5 的決定會被它蓋掉。建議**設一個期限**
   （例如一週），到期沒出就用 3.6 做一次完整重抽，不要讓「等下一版」變成
   無限期拖延。
   ⚠ 我無法確認 3.8 的發布時程，我的資訊有時效。

## 九、這一輪我犯的錯

記下來因為它們都有同一個形狀：**看到一個數字就下結論，沒問它穩不穩**。

1. **把 11,744 tok/s 當成真的** —— 三輪測試用同一段原文，第三輪整個命中前一輪
   的 prompt cache。是 ADR-0002 的警告擋下來的（「A/B 一定要用沒跑過的題本」）。
2. **把 D 的「泛用標籤 0」當成規則達標** —— 單次結果，鄰居都不支持。
3. **說「vLLM 從完整分布取樣」** —— 錯的，它有讀模型的 `generation_config.json`。
4. **說「規則 1 沒涵蓋標題頁」** —— 錯的，原文寫著 `author/affiliation block`。
5. **憑三篇的量測要 PO 設 temperature 0** —— 官方文件明確警告低溫有迴圈風險，
   而且點名這個模型家族。**「有權威來源時不得自己重算」，我又犯了一次。**
6. **監控腳本挑清單第一件當「正在跑」** —— 跟我當天在審核台修掉的毛病一模一樣，
   於是誤判「卡住 22 分鐘」，實際跑的是另一份 1,477 項的教科書章節。
