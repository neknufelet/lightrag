# 設計：一個名字走全程

**狀態：草案，等 PO 裁決。** 2026-08-14 由 fable 產出，依據是同日的實測。
這份文件的用途是**就地批註** —— 你直接在段落底下寫你的意見，我在原處回。

---

## 一句話

**每份檔案在進門那一刻拿到一個永遠不變的身分，寫在檔名最前面。**
此後解析、圖譜、kbapi、Obsidian、Zotero 全部用這個身分對話，
「拿標題去猜」整個退役。

---

## 為什麼要做這件事

2026-08-14 一天之內，「用標題猜這兩個是不是同一篇」被以下每一種情形各打敗一次：

```
拆書        一本論文在 Zotero 是 1 筆、在知識庫是 7～9 個檔
縮寫        檔名 TD_DG vs 標題 time-domain discontinuous Galerkin，零個共同的詞
檔名截斷    尾巴被切掉
空白不一致  `2012 - Combined` 與 `2012 -Combined` 被當成兩部作品
標點黏字    `Preferences:Part 2` 變成 `PreferencesPart 2`，相似度差門檻 0.017
上下集      Part 1 與 Part 2 幾乎一樣，而庫裡只有 Part 2
短吃長      `M Room Acoustics`（兩個字）吸走四篇長標題的論文
前綴相同    `Low-frequency broadband absorber…` 開頭一樣的三篇被併成一篇
```

**每修好一種，下一批文件就長出新的一種。** 今天所有的補丁 —— 比對器、
`source-map.json`、`compat-check` A-38、Zotero Extra 裡的 `lightrag:` 與
`obsidian:` 註記 —— 全部是「第一步沒把身分釘死、事後回頭猜」的利息。

PO 說的五步流程（進來 → 解析 → 整理 → 抽取 → 檢查）**不動**。
這個設計只補一件事：**在第一步就把身分釘死。**

---

## 一、身分放哪裡

**放檔名最前面。**

```
<KEY>_<NN> <年份> - <標題尾巴>.pdf

APLAMD5P_03 2021 - Room acoustic modeling with the TD-DG method_CH3.pdf
L0000042_01 2019 - 某篇不在 Zotero 的技術報告.pdf
```

| 欄位 | 是什麼 |
|---|---|
| `KEY` | 8 碼。Zotero 來的用它的 item key 原文；不是的由進料台鑄 `L` + 7 位流水號 |
| `NN` | 兩位流水號。**只保證唯一與穩定，不承載章節號** |
| 尾巴 | 沿用現行的「年份 - 標題」。**可以被截斷，不准被修改** |

**命名權威只有一個：進料台。** 它今天就已經在做最終命名（同名加序號、回 201
告訴外掛實際檔名）。外掛改成上傳時附一個 `X-Zotero-Item-Key` 標頭，
進料台配 NN、組最終檔名。手動丟的檔案由進料台在認領時命名。

### 為什麼是檔名

檔名是**唯一已經天然流過每一站**的東西（實測的傳播鏈）：

```
進料台存檔
  → work/parsed/<檔名>.pdf.mineru_raw      解析快取的鍵
  → LightRAG 的 file_path                  Postgres 實查有此欄
  → 檢索回傳的 doc 欄位                     kbapi 取 basename
  → kbapi 圖片別名                          sha1(檔名) 前 6 碼
```

把身分放進檔名，等於**零新管線**就讓每一站自動攜帶它。

| 其他候選 | 為什麼輸 |
|---|---|
| sidecar 檔 | 收件夾收的是裸 PDF；要改上傳協定，而且每一站都得重新學會攜帶它 |
| LightRAG 的 metadata 欄 | 它在管線**最末端**才誕生 —— 解析快取、收件夾、kbapi 的 `/docs` 都看不到；而且重抽即重生 |

### 為什麼在最前面

> **2026-08-15 補：截斷者找到了，是 Zotero 自己。** 這一條原本是本設計唯一的
> 生死假設（「如果它其實截頭不截尾，本設計直接死」），現在有答案了。

檔名長度分佈量出來有一根柱子：

```
100–109 字   23 份
110 字       16 份  ┐
111 字       25 份  ┘ ← 牆
113–123 字   ~7 份
```

41 份卡在 110–111，而且全部斷在字中間（`chan`、`approximat`、`energ`、`w`、`Ac`）。
追下去：**Zotero 自己重新命名附件檔案時砍的**。它的附件實體檔名分佈：

```
110 字   8 個
111 字  15 個   ← 一模一樣的牆
121 字   2 個  ┐ 翻譯本：先砍到 110，**然後才接上** `_zh-TW_dual`
122 字   7 個  ┘
```

最後那兩行是鐵證：**砍完尾巴還能往後接東西，頭部完全沒被動過。**

所以那 41 個斷檔全部是「從 Zotero 的儲存資料夾直接拖出來丟進收件夾」的；
走外掛的檔案由我們自己命名（上限 180），不受這道牆影響。

**結論：截斷一律砍尾巴，身分放頭部是安全的。**
（原本以為是 105 字的牆、以為在我們自己的程式裡，兩個都不對，以實測為準改了。）

### 這不是新發明

現庫 316 份裡**已經有 89 份**在用 5 碼書碼前綴（`01405_5.5 The influence….pdf`，
Postgres 實查 `file_path ~ '^[0-9]{5}_'` → 89）。這個設計是把既存的局部做法
統一成全庫規則，並把碼換成跨系統都認得的 key。

### 代價（誠實列）

1. **檔名定案後終身不准改。** kbapi 的圖片別名與解析快取的鍵都是檔名，
   一改兩者皆斷。錯了就走「單篇刪除 ＋ 重進」（這條路 08-14 已實測，乾淨）。
2. **遷移日已發出去的圖片別名會斷一次。** 但斷的只有「別名 → 伺服器」的反查：
   Obsidian 筆記裡的圖是**下載進 vault 的本地複本**，不會破。
   遷移時產一張「舊別名 → 新別名」對照表存進 `records/`。

## 二、一本書在圖譜裡是幾份

**檔案是生命週期單位，作品是前綴。一本 20 章的書 = 20 份文件，共用同一個 8 碼前綴。**

- **為什麼不合併成 1 份**：單篇刪除已實測可用且乾淨 —— 那是整個系統最值錢的
  維修工具。合併成一份等於把「修一章」變成「重做一本書」。
- **作品層資訊怎麼取**：任何消費者用**檔名前 8 碼**分組即可，不需要查表。
  公式跨來源比對從「查 source-map」改成「取前綴」。
- **來源登記因此在結構上不可能再欠帳**：今天欠 57 份，是因為「登記」是一個
  獨立於進料的人工動作。改制後分組資訊是檔名的一部分，**進門即登記**。

### 一個誠實的殘餘

有一類資訊前綴表達不了：**「A 作品的某章與 B 作品是同一份文字」**
（學位論文第三章 ＝ 某篇期刊論文）。那是兩個不同的 Zotero 條目。

這類保留成一張很小的表（`verdicts/same-work.json`），量級是**幾筆**，
只在 PO 裁定時增長。這是 `source-map.json` 唯一活下來的部分 ——
從「259 筆逐檔登記、永遠在欠帳」縮成「幾筆作品級裁決、天生不會欠帳」。

## 三、送哪個附件（翻譯本怎麼辦）

**翻譯本永不入庫。**

理由：語料是英文、檢索以英文為準；`_dual` 對照版進解析器只會產生中英交錯的
垃圾。實測 155 筆雙 PDF 裡 **96 筆是標準 `PDF + PDF_ZHT`** —— 放進去就是
一百多篇被抽兩次、而且被公式比對當成獨立來源的**假發現製造機**。

### 決策瀑布（全在外掛裡）

```
1. 附件帶 kb tag           → 送它們，不問
2. 只有一個 PDF            → 送它，不問（6 筆屬此）
3. 排除翻譯樣式後只剩一件   → 預設勾它
4. 剩多件（拆章、全文＋章節、preprint＋正式版）→ 對話框列出，預設全勾非翻譯件
```

對話框每次送出都出現、**預設已經勾好**，你按一下 Enter。
**確認的同時外掛在被選附件蓋 `kb` tag** —— 同一筆之後再送、對帳，永不問第二次。

這正是你那 8 筆手工寫「送出的版本」想表達的意圖。接管它，給它機制。

翻譯排除樣式：`ZHT`、`zht`、`_zh-TW_dual`、`_zh-TW_translation`，
樣式表集中一處維護。

⚠ **既有 179 筆不回頭補 tag** —— 遷移走解析快取重抽，完全不回 Zotero 拿附件。
tag 只在未來的送出動作中自然累積。

## 四、不從 Zotero 來的檔案

**兩條路並存，都不擋，但只有一條是免手續的。**

| | |
|---|---|
| **正門（外掛）** | 一次可多選文獻送出。key 自動、命名自動、**零額外動作** |
| **後門（收件夾）** | 照收。沒有 key 的檔案停在既有的人工放行閘門前 |

後門的處理：審核台加一格「認領」。把這批檔案分好組（預設按檔名共同前綴），
每組做**一個動作** —— 選一筆 Zotero 文獻，或按「鑄本地編號」。
42 篇散論文那種批次，預設動作就是「全部各鑄一個」，一鍵放行、**流程永不卡死**。

**本地編號不是欠帳，是誠實標記「此物不在 Zotero」。**
事後要升級：同一份內容日後從外掛再送一次，內容雜湊會攔下並提示
「這份已存在，編號 L0000042 —— 要認領成 APLAMD5P 嗎」。
認領寫進目錄檔，**檔名不改**（改名禁令優先於編號美觀）。

### 你的成本結算

正門零動作；後門每批一次確認 —— 而且是在**你最知道答案的那一刻**（丟檔當下）問，
不是三個月後拿標題回來猜。

⚠ 你今天繞過外掛的原因之一是**它一次只送一個附件**（`sendOne` 只送
`getBestAttachment()`，程式實讀確認）。正門修好，後門的流量自然萎縮。

## 五、重抽：做，但三層成本完全不同

| 層 | 怎麼處理 | 成本 |
|---|---|---|
| **解析（MinerU）** | **搬家改名，不重跑** | **零額度。這保住了 09-04 到期的 token** |
| **修補資產** | 原封保留（∂ 那 71 處等都活在 `content_list.json` 裡，跟著搬） | 零 |
| **抽取（DeepSeek）** | 新 workspace 全部重跑 | 牆鐘約 **16–20 小時**；費用估**數十元人民幣**量級（未驗，估算） |

工期由實測外插：08-09 批 149 份約 8 小時、08-14 批 57 份約 3.4 小時、
單篇中位數 233 秒。

### 改名工具要動 bundle 內部的哪些地方

dker 逐檔 grep 實測，不是猜的：

```
要改   _manifest.json 的 source_filename_at_parse ＋ 指紋重蓋
要改   .parsed/blocks.jsonl meta 行的 document_name / doc_title
要改   drawings.json
要改   .parsed/ 內以檔名開頭的檔案本身
乾淨   content_list.json、full.md、layout.json、equations.json
```

⚠ 指紋重蓋**必須走 `pp/apply.py` 的 `restamp_manifest()`** —— 它是指紋的唯一
擁有者。08-13 那次「修補被 reindex 洗掉」的事故就是繞過它造成的。

### 為什麼不走「只改名不重抽」

改名要同步改遍 Postgres 13 張表裡所有帶 `file_path` 的列
（doc_status、chunks、entities、relations、三張向量表的 payload），
**漏一張就是新坑**。ADR-0006 拒絕改 workspace 名用的正是同一個論證。

藍綠重建把「手術」換成「重建 ＋ 驗收 ＋ 切換」，每一步都可驗、可退。

### 一個可能省掉九成時間的加速器（未驗）

ADR-0006 實測過「chunk 不動時抽取快取全命中，207 chunk 的重抽 45 秒走完」
（差 160 倍）。改名不改內容，chunk 文字理論上逐字相同。

batch 1 時實驗把 `lightrag_llm_cache` 的列複製到新 workspace ——
成了，整場遷移的抽取從 16 小時縮成幾十分鐘；不成，照付 16–20 小時，計畫不變。

### 分批與閘門

**batch 1（試金石）**：一本拆章書（走完整前綴鏈路）＋ 約 10 篇單篇，
**刻意收錄歷史踩雷樣本**（Part 1/Part 2 那對、被截斷的那篇、`M Room Acoustics`）。

**batch 1 的硬閘門，全過才有 batch 2**：

```
(a) 零 MinerU 呼叫 —— 證明改名後快取確實命中。這是整個遷移的前提
(b) parse-check ERROR 零新增
(c) extract-check 接地全過
(d) graph-shape 四數字與舊 workspace 同組文件相比在合理帶內
(e) eq-dup 用前綴分組重現已知的跨來源裁決
(f) retrieval smoke
```

全部是**既有的尺，不新造**。之後每晚一批（50–60 份），同套閘門，
ledger 三態記帳（pass / fail / unverifiable，沒跑的閘門不填 pass）。
179 部作品約**一週到十天**收完。

## 七、遷移路徑

**每一步結束時，舊庫都在原埠照常回答查詢。**

⚠ 回滾手段自始至終是「指回舊庫」，**刻意不依賴冷備還原** ——
考古確認「還原」這條路至今**沒有人走過**（repo 三處文件明寫還原未實測）。
未走過的路不能當安全網。

```
1. 凍結進料（收件夾照收、只是不處理；查詢不受影響）。建冷備還原點
2. 最後一役：產出 316 份 → key 對照表
   ★ 你的第一次出場：核一張 179 部作品的清單（作品、key、檔數）
3. 建新解析層：bundle 複製到 work/parsed-v3/、改內部引用、restamp。跑 parse-check 驗綠
   舊層一字未動
4. 起新 stack（compose 本來就支援同機第二 workspace）。磁碟實測剩 209G，綽綽有餘
5. batch 1 ＋ 硬閘門。過不了就修了重來，舊庫毫髮無傷
6. 每晚一批到收完
7. 切換
   ★ 你的第二次出場：核准。操作是停舊 stack、新 stack 改監聽正式埠重啟
   停機是一次容器重啟，秒級到分鐘級
   舊 stack 停而不刪，留 2–4 週當回滾點
8. 同一天：進料台新命名 ＋ 認領閘重啟、外掛新版發佈、退休名單執行、A-38′ 上線
```

**你在整個過程中只出現兩次。**

⚠ **期間的取捨**：凍結進料的一到兩週內，新丟的檔案查不到（排隊中）。
等不及的話順序可以倒過來先收急件 —— 批次順序沒有依賴關係。

## 八、這個設計會被什麼打敗

上面那張「比對被什麼打敗」的表，就是現行做法當初沒想到的東西。這個設計也會有：

1. **Zotero key 不是永恆的。** 合併重複條目、刪掉重建，key 就變，
   知識庫裡的前綴變成孤兒。A-38′ 會亮燈，但修復是人工裁決。
2. **一份內容屬於兩部作品。** 檔名只能蓋一個 key —— 這是硬選擇，
   靠 `same-work.json` 補。錯放的那一邊永遠要靠人發現。
3. **認領疲勞。** 一鍵確認久了會盲按。而錯的 key 比今天的錯猜**更黏** ——
   它會被燒進檔名、圖譜、引用。解毒劑是單篇刪除便宜，但前提是有人發現錯了。
4. **繞過進料台。** 直接把檔案放進 `work/parsed` 的人（包括未來的 agent），
   A-38′ 抓得到「名字沒前綴」，**抓不到「前綴蓋錯」**。
5. **運輸層改寫檔名。** samba／WebDAV／Synology 的 unicode 正規化可能動尾巴。
   前綴是純 ASCII、在頭部，抗性最高。但如果哪天某一層連前綴都動，設計傷到根。
6. ~~**那個沒被定位的截斷者。**~~ **2026-08-15 已解決** —— 是 Zotero 自己在
   重新命名附件時砍的，砍在 110–111 字，**一律砍尾巴**（翻譯本是先砍完再接
   後綴，證明頭部沒被動）。這一條從「生死問題」降級成「已知行為」。
7. **抽取非決定性。** 新圖譜不會與舊圖譜逐實體相同（除非快取搬移實驗成功）。
   切換日起，同一條查詢的答案會變。這是重建的本質，不是 bug，但要先講。
8. **翻譯排除樣式表仍然是一張「猜」的清單。** 第五種翻譯命名法出現時會勾錯。
