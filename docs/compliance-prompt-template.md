# 規則遵循度盤點的 prompt

**與 [audit-prompt-template.md](audit-prompt-template.md) 的差別**：

| | 探索式體檢 | 盤點式（本檔） |
|---|---|---|
| 事先知道要找什麼 | 不知道 | 知道，有清單 |
| 問的問題 | 哪裡會安靜壞掉而沒人知道 | 這條規則誰在守 |
| 找得到清單外的問題 | **會** | 不會 |
| 有明確的完成條件 | 沒有 | **有**（清單跑完） |
| 產出 | 問題清單 | 規則 × 執行者等級的表 |

兩種都要做。今天最有價值的三個發現全是探索式的（規則從來沒想過的地方），
但盤點式會逼出「這條規則寫了三個月，誰在守？沒有人」——那是探索式不會系統性去問的。

**這份的核心不是「有沒有遵守」，是「違反了會不會有人知道」。** 一條被遵守但沒有
執行者的規則，只是還沒被違反而已。

---

## 直接複製這一段

```
請盤點 <專案> 的規則遵循度。

## 這件事的重點

不是「有沒有遵守」，是「**違反了會不會有人知道**」。
一條目前被遵守、但沒有任何東西在守的規則，只是**還沒被違反**而已。

所以每一條規則你都要回答同一個問題：**誰會發現違反？** 並給等級：

  會擋下          有 hook／CI／pre-commit 會讓違反的動作失敗
  會印警告        有排程或檢查會跑出紅燈，而且紅燈有人看得到
  只在有人主動跑時才響   工具存在，但沒有東西會自動叫它
  每 session 載入 只適用「AI 行為規則」，且必須是 inline 進 context 的全文
  沒有人          ← 這個答案最重要，不要不好意思寫

⚠ **人的審查不算執行者。** PO 會看到、reviewer 會抓到——但那是系統外的最後一道。
  把它算進去，系統就會開始依賴一個「剛好會看到」的人，等於沒有守衛。

⚠ **「文件裡有寫」不算執行者。** 寫在 README／CLAUDE.md／規範文件裡而沒有東西
  在守，等級就是「沒有人」。這一條最常被誤判為「已經有規範了」。

⚠ **「只引用外部檔案」不算部署。** 被引用的檔不會自動進 AI 的 context。

## 要盤點的清單

### 第一部分：程式碼紀律（9 條）

  1. Read before write     改檔前先讀，禁止覆蓋未讀的內容
  2. No silent drops       重構時資料／欄位／邏輯不得無聲消失，刪除要明說
  3. Type hints            函式簽名要有型別註解，禁止裸 Any 當逃生門
  4. No print for logging  用 logging，不要拿 print 當 log
                           （⚠ CLI 工具的 print 是輸出不是 log，不要誤判）
  5. SOLID／單一職責       函式與類別只做一件事
  6. 明確的資源管理        file handle／DB 連線／thread 要用 with 或明確 close
  7. 路徑用 pathlib        不要用字串拼接路徑
  8. 合併前要有測試        新功能至少一個 smoke test
  9. 驗證再斷言            關於「跑著的系統」的陳述必須附驗證指令**與其原始輸出**

### 第二部分：制度紀律（這幾條最容易「有寫但沒人守」）

  10. 規則的執行者         每條規則本身都要答得出「誰會發現違反」
  11. 乾淨的 0 先當成量錯   量到 0／全數通過時先假設量錯；新檢查上線前要證明它會失敗
  12. 秘密不經由整包輸出    值不得進入會被記錄或轉貼的輸出；禁止先取出再遮蔽
  13. 檢查結果要帶版本      紅綠燈／報告要帶產生它的 commit，否則過期與現況長得一樣
  14. 跨元件的隱含前提要有斷言  B 依賴 A 的某個性質時，那個依賴要寫成可執行的斷言
  15. 文件不得寫死可量測的數字  份數／鍵數／容器數要換成量它的指令
  16. 提交紀律            做完即提交，禁止「done 但 uncommitted」長期累積

## 怎麼盤（重要：不要靠讀文件判斷）

**每一條都要去找那個執行者的實體**，找不到就是「沒有人」：

  會擋下     → 找得到 hook 設定檔／CI 設定／pre-commit 條目，而且**確認它有裝**
              （設定檔存在不代表裝了：`pre-commit install` 沒跑就是沒裝）
  會印警告   → 找得到排程單元（cron／systemd timer）**而且它是 enabled 的**
              ⚠ 實測過的坑：單元檔躺在 /etc 但 `systemctl list-timers` 裡沒有，
                看起來一切正常，實際沒有任何東西在跑
  只在有人跑 → 工具存在但沒有呼叫端。用 grep 確認它真的沒有被任何腳本呼叫

**對每一條「會擋下」或「會印警告」的，再問一次：它紅過嗎？**
拿一個已知會違反的輸入試一次。**只會回綠的檢查，跟沒有檢查在畫面上長得一樣。**
不敢試的話就降級成「宣稱有但未驗證」。

## 交付格式

### 主表

| # | 規則 | 目前遵守? | 誰會發現違反 | 證據 |
|---|---|---|---|---|
| 1 | Read before write | ? | 沒有人 | grep 不到任何檢查 |
| … | | | | |

「證據」欄要放**實際的檔案路徑與行號，或你跑過的指令與輸出**，不要放「應該有」。

### 三個數字

  a. 幾條的執行者是「沒有人」（連同百分比）
  b. 幾條宣稱有執行者、但你**沒有實際驗證它會紅**
  c. 幾條在文件裡寫著、但實際上沒有任何東西在守
     （這一類最危險：它會被當成「已經有規範了」）

### 最有價值的一節：配執行者的成本排序

對「沒有人」那幾條，各給一個**最便宜的執行者**提案，並排序：

  規則 → 提案（具體到可以直接做）→ 大約要多久 → 為什麼是這個等級

排序依據不是重要性，是 **「代價／擋掉的損害」**。
一條只要加三行 pre-commit 就能從「沒有人」變成「會擋下」的規則，
永遠排在需要寫一支新服務的前面。

## 不要做的事

- 不要改動任何東西。這一輪只盤點。
- 不要把「這個專案還很小所以不需要」當理由跳過——那是「什麼時候要做」的問題，
  不是「有沒有守」的問題，兩者分開答。
- 不要為了讓表好看而把「沒有人」寫成「靠 code review」。
- 盤完之後，**如果每一條都是「有人守」，先假設你盤錯了**。
  參考值：lightrag 2026-08-07 第一次盤點，173 條踩坑教訓裡 **51% 的執行者是「沒有人」**。
```

## 用之前

1. **先確認你要盤的是哪一版規則。** 上面第一部分那 9 條是 lightrag 專案上游
   `standards/BASELINE.md` 的核心規則；第二部分混了上游的非核心條文與 2026-08-08
   這一輪新提的三條。換專案時先確認它認的是哪一份。
2. **這份會產出很多「沒有人」，那是正常的。** 第一次盤點的價值就在於把那個數字
   量出來，而不是讓它好看。
3. **盤完不要立刻全部去修。** 用成本排序那一節挑最便宜的兩三條先做——
   一次修太多會讓每一條都做得不紮實，而做不紮實的執行者比沒有更糟
   （會誤擋、然後被關掉）。
