# 上游 BASELINE 畢業評估

**先講結論**：這一輪最重要的發現不是「上游少了什麼」，是**上游已經有兩條正是我
今天踩的，而我照樣踩了**。所以這份文件分三部分：已經有的、真的缺的、以及不該急著
升格的。

上游現況：`baseline_version: 2.0.0`，`rules_sha256: f2d0bcfa04c43fb3`。

---

## 一、上游已經有，而我違反了（**不需要新增條文**）

### 「規則的執行者（誰會發現違反）」（BASELINE.md:140，2.0.0 加入）

上游已經寫得比我想加的完整：

- 等級表：`會擋下` ＞ `會印警告` ＞ `只在有人主動跑時才響` ＞ `每 session 載入` ＞ `沒有人`
- **「新規則答『沒有人』者不得寫成條文」**，先進觀察區，配到執行者才升格
- **「人的審查不算執行者」** —— 那是系統外的最後一道，不是系統內的守衛
- 「能機器判定的規則以工具出貨（hook／檢查腳本），不佔 context」

⇒ PO 這一輪反覆問的「不是講而已，要怎麼具體避開或警告」，**上游早就是這個規定**。
我先前把規範寫成散文放進 review 文件，就是違反了它。

### 「量測紀律：乾淨的 0 要先當成量錯」（BASELINE.md:165，2.0.0 加入）

同樣已經完整，而且連對策都寫了：

- 「量測工具回報 0 時，**先假設量錯**，最常見成因是『驗的東西跟真正在跑的東西不是
  同一個』」
- 「**新檢查上線前要證明它會失敗**（拿已知會咬到的值試一次）」

⇒ 我今天四次全部命中這條，**而且每一次都是 0 或小數字**：

| 我量到的 | 實際 | 錯在哪 |
|---|---|---|
| `person／organization = 0` | **709 + 84** | 查向量表，型別在 `graph_nodes` |
| 參考文獻消音 `0.05%` | **8–23%** | 只數 `text`，內容在 `list_items` |
| `apply` 乾跑「消音 0」 | 19 | 統計那行只數了另一條規則 |
| `freshness rc=0` | **rc=2** | 管線後面的 `$?` 抓到 `tail` 的 |

**每一個 0 都看起來像「這件事不用做」**——這是這條規則值得補強的地方（見第四節）。

## 二、上游完全沒有，而我們有執行者了（**可以升格**）

用上游自己的判準：有執行者才升格，並註明等級。

### A. 秘密不得經由「整包輸出」離開系統

**等級：會擋下**（`scripts/guard-command.py` ＋ `.claude/settings.json` 的 PreToolUse hook）

上游 BASELINE 目前**完全沒有秘密相關條文**（grep `秘密|secret|金鑰|api.key` 零命中）。

擬議條文：

> 秘密的**值**不得進入任何會被記錄或轉貼的輸出。禁止「先取出整包再遮蔽」——
> 遮蔽樣式寫錯就全洩，而寫錯不會有訊息。
> 具體：不得整包傾印容器設定／環境變數／設定檔；取值只取指定的鍵；
> 比較兩個秘密是否相同用**雜湊**不用值。

血淚：2026-08-08 一天三次，而**正解早就寫在專案自己的 `cairn/secrets-handling.md`
裡**（「先取出再遮蔽的設計本身就是錯的」）。我讀過那份文件，然後用同一個錯的形狀
又做了兩次。⇒ **知道規則不等於套用規則**，這正是它需要執行者而不是條文的證明。

### B. 檢查結果必須帶上產生它的版本

**等級：會印警告**（`daily-check.sh` 寫入 `latest.json` 的 `commit`；審核台 `:9710` 顯示）

擬議條文：

> 任何會被人看到的檢查結果（紅綠燈、報告、量測輸出）必須帶上產生它的版本
> （commit 或等價識別）。沒有版本的話，「這條檢查後來被修好了」與「這個問題還在」
> 在畫面上長得一樣，讀者會照著一份舊碼的判斷去處置。

血淚：2026-08-08 加上這個欄位後，審核台立刻顯示「由 `73af65e` 產生」——而同一天
稍早，審核台回報 `commit: None` 正好暴露了**讀它的行程是舊的**（跑著 7 小時前的
`intake.py`）。這個欄位第一天就抓到了另一個問題。

### C. 跨元件的隱含前提必須有斷言

**等級：會印警告**（`compat-check` 的 A-29：兩個外部端點的金鑰各打一次 `/models`）

擬議條文：

> 當 B 的正確性依賴 A 的某個性質，而那個依賴沒有寫成斷言時，改 A 會讓 B 安靜失效。
> 這類依賴要嘛寫成可執行的斷言，要嘛消除（讓 B 不依賴 A）。
> 判準：問「這裡假設了什麼？那個假設變了的話，誰會知道？」

血淚：`pp/eyes.py:87` 的第二雙眼睛 fallback 沿用 `EMBEDDING_BINDING_API_KEY`，
前提是「embedding 用的就是 OpenAI 金鑰」。embedding 切成本機 BGE-M3 之後前提消失，
而**沒有任何東西會發現**——實測同一把金鑰打 OpenAI 回 401、打本機回 200，
但那個 401 要到**下次進料跑後處理時**才會浮出來。

## 三、真的缺，但**還不能升格**（執行者是「沒有人」）

照上游規矩，這三條先進本專案的觀察區（`docs/NEXT.md`），配到執行者才升格。
列在這裡是為了讓下一次評估時不必重新發現。

| 候選 | 為什麼還不能升 | 執行者長什麼樣才夠 |
|---|---|---|
| **有權威來源時不得自己重算** | 通用形式難以機器判定 | 需要「哪些問題有權威來源」的清單，逐條做成斷言 |
| **文件不得寫死可量測的數字** | 沒有檢查在守 | 一支掃描器：文件裡出現「N 個鍵／N 份／N 個容器」就要求附量它的指令 |
| **啟發式的結果不得直接當數字報** | 無法從程式碼判定「這是啟發式」 | 可能只能靠 review 清單，那就不算執行者 |

第一條的血淚最完整（2026-08-08 四次，全部答錯而且**看起來沒問題**）：

| 我重算的 | 權威來源怎麼說 | 後果 |
|---|---|---|
| 容器啟動時間 vs commit 時間 | `compose up --dry-run` | 四台答錯兩台，含一個**漏報** |
| `compose config --hash` vs 容器標籤 | 同上 | `config --hash` 不算 `env_file`，誤報 |
| 每段 chunk 約 600 token | LightRAG 的 tokenizer 說 1,818 | 錯 3 倍，結論相反 |
| 實體型別查向量表 | 型別在 `graph_nodes` | 回報 `person=0`，實際 709 |

⇒ 這一輪新增的五支工具（`graph-shape`／`extraction-profile`／`context-budget`／
`deploy-stack freshness`／`guard-command`）**全部是這條原則的實作**：問 compose、
問 tokenizer、問解析器、問 systemd。但那是本專案的實作，不是通用的執行者。

## 四、給既有條文補血淚（**不是新規則**）

「量測紀律：乾淨的 0」那一節建議補一句，把說服力加厚：

> 補充（lightrag 2026-08-08，一天四次）：這四次的共同形狀不只是「量錯」，是
> **量錯的方向都讓人想放棄**——`person = 0`、`消音 0.05%`、`乾跑消音 0`。
> 一個漂亮的 0 不只代表工具可能壞了，它還會讓人把一個真問題判定成不存在。
> ⇒ 所以對策不能只是「再驗一次」，要是「**找一個已知該被命中的例子，確認它真的
> 被命中**」——控制組比重跑更可靠。

`rules_sha256` 不變（非核心規則）。

## 五、動手時的注意事項

1. **只有 `standards` repo 那一份可以改**（BASELINE.md 第 18 行：各專案的 snapshot
   是唯讀凍結副本）。改完 bump `baseline_version`，`rules_sha256` **不用重算**——
   上面三條都是非核心規則。
2. **各專案的 snapshot 用顯式 sync 動作拉取**，不要手抄（本專案 CLAUDE.md 那個區塊
   標著「用程式抽出、不手抄」）。
3. 升格 A、B、C 之後，本專案 `docs/NEXT.md` 第 6 批那條「七條新通則上升」要跟著
   改成剩下的四條。
