<details>
<summary>修前 / 修後對照、根因、與你的批註</summary>

**修好之後的實測**

```
             修前          修後
單篇 naive   找不到    →   3,703 字
單篇 naive   1,257 字  →   4,685 字（原本被截斷）
單篇 naive   找不到    →   4,955 字
跨篇 naive   391 字    →   6,653 字（原本被截斷）
跨篇 mix     找不到    →   6,223 字
跨篇 mix     2,929 字  →   7,100 字（原本被截斷）

$ docker logs --since 12m lightrag-acoustics_v2 | grep -c "exceed_context_size_error"
0
$ docker logs --since 12m lightrag-acoustics_v2 | grep -c "truncated by token limit"
0
```

**原本的問題**：知識庫檢索到內容，卻回 `No relevant context found for the query.`。
真正發生的是組完 prompt 超過模型 context 上限、LLM 回 400，這個錯誤被轉成
「查無資料」呈現給使用者。**沒有任何紅燈會亮。** 這是〈乾淨的 0 要先當成量錯〉
那條畢業知識，長在對外的答案上。

```
$ docker logs --since 25m lightrag-acoustics_v2 | grep -iE "no relevant|error"
ERROR: query LLM func: Error code: 400 - {'error': {'code': 400,
       'message': 'request (33350 tokens) exceeds the available context size
       (32768 tokens), try increasing it', 'n_prompt_tokens': 33350, 'n_ctx': 32768}}
```
同一時段另外兩次：`32887`、`33175`，皆超過 `n_ctx: 32768`。

**根因是算術**：

```
$ docker inspect llama-qwen36-moe --format '{{join .Args " "}}'
... -c 131072 --parallel 4 ...
```
131072 ÷ 4 = **32,768**，那是每個 slot 分到的量。`.env.example:153` 自己就寫著
「n_slots = 4、n_ctx_slot = 32768」——但那個決定（SPEEDUP-2）是為**抽取**做的
效能測試，抽取的 prompt 是單一 chunk 很小；**查詢**要把整個檢索結果組進去就會超過。

> **你的批註（第一輪）**
> ```
> ## >> 除了限制token 數量,我們記憶體還有一點空間,如果再把總token加大一點可行嗎?
> 另外限制到28000左右的token會太少嗎 ,現在才13.1k的上下文. 128k 應該是理想吧?
> 或是要降低max sync的數量 犧牲一點性能換取品質？
> ```

**答**：先更正一個數字——**不是 13.1k，是 131k**。131,072 是四個 slot 的總和，
每個 slot 分到 32,768。

**加大總量不可行**，記憶體沒空間：

```
$ nvidia-smi --query-gpu=index,memory.total,memory.used,memory.free --format=csv
0, NVIDIA GeForce RTX 3060, 12288 MiB, 11093 MiB, 819 MiB
1, NVIDIA GeForce RTX 3060, 12288 MiB, 10311 MiB, 1601 MiB
```
兩張卡合計只剩 2.4 GB，而 131,072 的 KV cache 已經配下去了。

**只有兩條路**：

| 做法 | 查詢拿到的 context | 代價 | VRAM |
|---|---|---|---|
| (a) 設 `MAX_TOTAL_TOKENS` | 25k | 查詢少拿一點料 | 不變 |
| (b) `--parallel` 4 → 2 | 65k | 抽取吞吐 −22% | 不變 |

(b) 有連動：`--parallel` 降到 2 的話 `MAX_ASYNC` 也必須跟著降，
否則回到 `.env.example:144-148` 記的那場災難（4 個請求擠 2 個 slot、排隊、逾時）。

**為什麼最後設 25,000 而不是我一開始說的 28,000**：觀測到的 prompt 是 33,350，
而預設預算是 30,000，**代表系統提示與查詢本身另外吃掉約 3,350**。設 28,000 的話
prompt 會是 ~31,350，離 32,768 只剩 1,418 給答案——400 錯誤會消失但**截斷會繼續**。
`32,768 − 3,350 − 4,096（留給答案）≈ 25,300`，所以取 25,000。實測結果證明這個算對了。

> **你的批註（第二輪）**
> ```
> >> 2答 token 這邊就照你說的依序把max token 設定好跑 看結果 不理想再將parallel 4>2 看看
> rerank 我如果用dker 這台機器來架設可以嗎
> ```

**答**：已照做，結果如上——不需要動 parallel 了。rerank 那題回在第 3 條。

**還沒做的**：這個值與理由要寫進 `.env.example`，否則重建時會掉（工單 1）。

### 3. ◻ rerank 開著但沒有設模型 — **可以用 dker 自架，那台的卡完全閒置**

**結論先講**：dker 有一張 **RTX 2070 8GB，用量 1 MiB**，docker 的 nvidia runtime
也配好了。reranker 只吃 1–2 GB，空間綽綽有餘。

<details>
<summary>能接哪些、要設什麼、有什麼坑</summary>

> **你的批註**
> ```
> ## >> rerank 的用處大嗎, 我看他不是很貴,如果套用openrouter上的模型可行嗎
>    還是他其實非常消耗token
> ## >> 2答 ... rerank 我如果用dker 這台機器來架設可以嗎
> ```

**用處在這個專案特別大**，因為它正好接著第 1 條：我們剛把查詢空間壓到 25,000，
壓縮之後「這 25,000 裡放什麼」就變得比以前重要——rerank 正是決定這件事的東西。
現在是「撈 20 個全塞」，開了之後可以「撈 30 個、只留最相關的 8 個」。

**它不吃你的 32,768**。rerank 不是 LLM，是一個小模型，輸入「查詢＋候選段落」、
輸出分數，在另一個服務裡算。所以不會加重溢位。

**OpenRouter 不行**——它是 chat completions 的形狀，rerank 是不同的 API。

**dker 自架可行**：

```
$ nvidia-smi --query-gpu=index,name,memory.total,memory.used,memory.free --format=csv
0, NVIDIA GeForce RTX 2070 with Max-Q Design, 8192 MiB, 1 MiB, 7786 MiB
$ docker info | grep -iE "runtime|nvidia"
  cdi: nvidia.com/gpu=all
 Runtimes: nvidia runc io.containerd.runc.v2
```

（順帶：CLAUDE.md 說這台 `nvidia-smi` 是 driver/library mismatch，**那條已經過期**，
現在是好的。另開成第 24 條。）

**但有一個限制**：LightRAG 只認四種接法。

```
$ docker exec lightrag-acoustics_v2 python -c "import inspect, lightrag.api.config as c; ..."
choices=["null", "cohere", "jina", "aliyun"]
```

所以本地服務**必須講 Cohere 或 Jina 那個形狀的話**，再把 `RERANK_BINDING_HOST`
指過去。不是隨便一個 rerank 服務都能接。

**推薦順序**：

1. **llama.cpp**——你們已經在用。支援 reranker 的 GGUF，開 `--reranking` 之後有
   `/v1/rerank`，形狀是 Cohere 那一系。**不增加任何新技術**，同一套東西你們會維護。
2. **Infinity**（`michaelf34/infinity`）——專做 embedding 與 rerank，有現成 image，
   `/rerank` 是 Cohere 相容的。更專門，但多一個要維護的東西。
3. **TEI**（HuggingFace text-embeddings-inference）——也有 rerank 端點，
   但回應形狀我沒實際對過 `(未驗)`，可能要用 `generic_rerank_api` 調整。

**模型**：`BAAI/bge-reranker-v2-m3`（5.68 億參數、100+ 語言、**Apache 2.0**）是我會選的。
多語言對你們**特別重要**——你用中文問、論文是英文的，單語模型在這種情況會退步。
完整名單與授權比較見**第 25 條**。

**要設的項目**（共九個，核心四個）：

```
RERANK_BINDING           現在是 null，要改成 cohere 或 jina
RERANK_MODEL             模型名
RERANK_BINDING_HOST      指向 dker 上那個新服務
RERANK_BINDING_API_KEY   本地服務隨便給一個
（其餘：RERANK_BY_DEFAULT、RERANK_ENABLE_CHUNKING、RERANK_MAX_TOKENS_PER_DOC、
  RERANK_MAX_ASYNC、RERANK_TIMEOUT）
```

**一個坑**：`RERANK_MAX_TOKENS_PER_DOC` 預設 **480**，而你們的 chunk 比這個大很多——
直接開下去會把每個 chunk 砍掉一大半再評分，等於**用摘要在排序全文**。
要嘛調大這個值，要嘛開 `RERANK_ENABLE_CHUNKING`。
出事的樣子是「排序怪怪的但沒有錯誤訊息」，沒人會提醒你。

**本地跑的好處**：沒有按次計費、**沒有會過期的 token**——你們已經被 MinerU 那個
9/4 到期的綁著了，不必再多一個。

**現在的狀況**：每次查詢都印一行警告。

```
$ grep -E "^RERANK" /opt/stacks/lightrag/.env
RERANK_BINDING=null
WARNING: Rerank is enabled but no rerank model is configured.
```
不管走哪條路，**留著「開著但沒接」是最糟的**——下次真的出事時會被當成雜訊跳過。

| | 修溢位前 | 修完溢位、無 rerank | **加上 rerank** |
|---|---|---|---|
| 答案完整度 | 4 假「找不到」+ 7 截斷 + 1 完整 | 12/12 完整 | **12/12 完整** |
| chunk 重疊率 | 68–85%（不可信，量到的是 token 上限） | 65–88% | **26–67%** |

INFO: Successfully reranked: 20 chunks from 73 original chunks   ← mix
INFO: Successfully reranked: 20 chunks from 40 original chunks   ← mix
INFO: Successfully reranked: 20 chunks from 42 original chunks   ← mix

**naive 的候選池只有 20 個，rerank 無事可做（20 挑 20）。

少了 rerank，多出來的候選只是雜訊（於是 mix 看起來像 naive 的子集）；
有了 rerank，mix 才敢撈得更廣。**這兩件事單獨看都不明顯，合起來才成立。**

**答：是「同一份文章裡面的版面」，不是跨文件的 A3／A4。**

規則在 `scripts/pp/docctx.py:56-64`，它自己寫了理由：

```python
@cached_property
def page_size(self) -> tuple[float, float]:
    """PDF 點座標的頁面尺寸。要求所有頁一致 —— 尺寸混雜時 bbox 換算會錯，
    而且錯得很安靜（裁出來的圖看起來像張表，只是位置不對）。"""
    sizes = {tuple(p.get("page_size") or ()) for p in self.layout["pdf_info"]}
    if len(sizes) != 1:
        raise DocContextError(f"{self.doc_name}：頁面尺寸不一致 {sizes}")
```

**跨文件完全不管**——每份文件各自算各自的。A4 論文跟 A3 圖表集放一起沒問題。
擋的是**同一份 PDF 裡混了不同尺寸的頁**。

**會造成什麼不好的結果**：整份文件的圖表座標都是用「這一頁多大」換算的。
一份裡混兩種尺寸就會用錯的分母，**裁出來的圖會偏位**——而且不報錯，
你會拿到一張「看起來像張表、只是框歪了」的圖。

**這次是誤判**：2017 那篇的兩種尺寸是 `(594, 842)` 與 `(595, 842)`，
差 **1 個點**（約 0.35 公釐），那是排版軟體的捨入。

**做法**（工單 3）：判準從「集合大小必須是 1」改成「**最大與最小的差不超過 2 點**」。
2 點約 0.7 公釐，足以吸收捨入，又擋得住真正的 A4／A3 混頁（差 297 點以上）。
改 `docctx.py` 一個地方，所有文件立刻適用，2017 那篇自動通過。

**不進 SSOT**——PDF 解析的領域知識，換個專案就沒了。留在 `hard-rules.md`。

你講的坑很具體：同樣的檔案不同檔名丟進去，圖譜多一份重複實體，合併之後不可逆。
定時備份救不了——出事跟下次備份之間可能隔 6 小時，而且你不會知道要還原到哪個時間點。

**建議做法**：掛在**放行成功**這個事件上。`_run_admit` 走完（狀態變 `indexed`）
就觸發一次快照，命名帶上剛進來的文件名。這樣每份文件進庫前後各有一個明確的還原點，
「這篇是垃圾」的復原就變成「還原到收它之前」，而不是「還原到某個時間」。

順帶：`intake.py` 已經在擋一部分——同批不能有相同檔名、同一份候選不能重複解析、
內容雜湊會比對。**不同檔名同內容**是用 sha256 擋的（`_known_hashes`），
所以你說的那個坑現在應該擋得住 `(未驗,推測——沒實際丟兩個同內容不同名的檔試過)`。

<summary>踩到的兩個坑（都會安靜地錯，記下來）</summary>

**坑一：`--dtype` 預設是 float32，直接 CUDA OOM**

我原本估「兩個模型合計 2.5 GB，8 GB 綽綽有餘」——**那個估法是錯的**。
2.5 GB 是 float16 的**權重**，而 (a) 預設是 float32 要兩倍，
(b) 真正吃顯存的大宗是 **batch × 序列長度的中間張量**，不是權重。

```

GPU 0 has a total capacity of 7.60 GiB of which 644.38 MiB is free.
ERROR:    Application startup failed. Exiting.

容器因此進重啟迴圈。加上 `--dtype float16 --batch-size 8` 之後 45 秒 healthy，
實際用量 **2,610 MiB，剩 5,177 MiB**。

**fp16 會不會影響品質**：對編碼器模型，fp16 與 fp32 的分數差在小數點後第三、

不是悄悄變差。實測分數健康（見下）。
⚠ **不要跟 `--embedding-dtype` 搞混**——那個是把**輸出向量本身**量化成 int8，

⚠ **授權有矛盾，選之前一定要自己看模型卡**：查到的來源裡，Qwen3-**Reranker**
被列為 Apache 2.0，但 Qwen3-**Embedding** 有一處被列為「custom commercial」。
兩者說法不一致，**不要憑我這張表就決定**。BGE 那兩個沒有這個問題
（MIT 與 Apache 2.0，說法一致）。

**我的選擇：BGE-M3（embedding）＋ bge-reranker-v2-m3（rerank）**

理由三個：授權乾淨且一致、同一家同一代所以行為可預期、
**BGE-M3 明確支援跨語言檢索**——你中文問、論文英文，那正是它宣稱的能力。
兩個加起來約 2.5 GB，7.8 GB 的卡還剩 5 GB 以上。

**如果量出來輸給 OpenAI**：再往上換 Qwen3-Embedding-4B（量化），
那時候 GPU 還有空間。**但先量再換，不要一開始就上最大的**——
embedding 每次查詢都要跑，延遲會直接變成體感。

**真正的風險，而且現在測不出來**

你是**用中文問、論文是英文的**。跨語言檢索正是便宜的本地 embedding 最容易垮掉的地方，
而 `text-embedding-3-large` 在這件事上相當強。換過去**最可能退步的就是這個**。

**但我們現有的六道題全是英文**——所以**現在的測試量不到會壞的那件事**。
要換之前得先補幾道中文問英文論文的題目，否則換完看數字沒退步，
實際上你問中文的時候變差了，而沒有任何東西會告訴你。

**所以我的建議**

   換 embedding 的邊際成本接近零。分兩次做等於重跑兩次
4. 換完用同一組題（含中文題）比一次。退步就改回來，舊向量表還在

而一兩週後為了第 6、8 條還要再付一次。**同樣的錢做一次就好。**

### 其餘四項

<details>
<summary>MinerU 到期、A 節沒有執行者、藍桶 3–8 沒人守、2017</summary>

> **你的批註**

**1. 做成分頁**——贊成，跟第 20 條是同一件事（工單 12）。MinerU 到期日、各家餘額、
秘密的來源與狀態，全是「現在無人看管的外部依賴」。做成審核台的一個分頁就夠了，
不需要警報系統：**你每天都會打開審核台看紅綠燈，那就是最好的提醒位置。**

**2.「有做但沒有制衡」——你用的詞很準，這確實是最糟的一類。**
`rebuild-checklist.md` A 節那六條是：**檢查的函式寫好了（`oracle.mineru_options()`），
但沒有任何地方呼叫它**。所以它看起來像「有人管」，實際是零。
**這比「明知沒人管」更危險**——後者你會警覺，前者你會放心。

**怎麼處理，一句話**：**寫好的檢查沒有被呼叫，等於沒寫。**
規則應該是——任何檢查函式必須有一個排程或測試在呼叫它，否則不准算完成（工單 11）。
**這條該進 SSOT**：BASELINE 的「規則的執行者」那節現在只說「規則要有執行者」，
**沒說「執行者本身也要有人呼叫」**。

**3. 藍桶 3–8 沒有 lint／CI**。這六條（type hints、不用 print、SOLID、資源管理、
pathlib、測試）機器都判得出來，不該靠人記得。但**不建議現在架 CI**——
你們只有兩台機器、沒有 runner，架 CI 本身是新的維運負擔。
**更便宜**：其中五條 `ruff` 一支就能守，掛在**已經存在的 pre-commit** 上（工單 11）。
剩下「新功能要有測試」機器判不了，維持人工。**不新增機制、只在既有執行者上加規則。**

**4. 2017 那篇**：你的看法我在第 10 條回了，你也同意放寬容差。
