# 升級 v1.5.6 → v1.5.7

**2026-10-14 已升級並驗收**（compose `469f17a`，修正 `01f496a`）。升級後實跑：

    容器內 lightrag.__version__      1.5.7，healthy，restarts 0；啟動 log 無錯誤
    GET /documents                   405（確實刪了）
    審核台                           已進庫 472、外來 0、錯誤 None
    graph-shape --compare            68,279 → 68,279，四項全 +0
    retrieval-check                  與升級前逐行相同（120 chunks）
    compat-check                     紅燈 7 個，與升級前完全相同（A-36 hard 從 10/10 起就在，與升級無關）
    run-tests.sh                     三個入口全部通過

升級前的備份與基準在 `/data/backups/lightrag-pre-v157-20261014/`（pg_dump、rag_storage、graph-shape、compat 前後、retrieval 前後）。

⚠ 啟動時的 Security Warning（`WHITELIST_PATHS` 預設放行 `/api/*`）v1.5.6 就有，不是新的；埠只開在 Tailscale 位址上。要不要關另外決定。

**結論：只壞一處，三個呼叫點加兩個測試。其他我們碰得到的都沒變，資料庫不用搬。**

我們不是 LightRAG 的 source fork —— repo 只有 compose、我們的腳本、prompts。
所以「要修」指的是我們的腳本跟新版的接口對不上，不是合併衝突。

比對方法：下載兩版 release tarball 逐檔 diff，再對著我們實際用到的東西逐條查。
跑著的系統的部分在 dker 實打（輸出原文附在下面）。

## 壞掉的那一處：`GET /documents` 被刪

上游 PR #3788 `remove the deprecated GET /documents listing and get_docs_by_status`。
v1.5.6 `document_routes.py:6009` 有這條，v1.5.7 整個 `DocsStatusesResponse` 不見了。

我們用到它的地方：

- `scripts/intake.py:3691`（`_index_documents`）—— **最要緊**。問不到時被 `except` 接住、清單變空，
  `_foreign_documents` 會算出「不是這裡送進去的：0 份」。畫面說一切正常，其實沒數。（讀 code 推的，要等 v1.5.7 上去才能重現）
- `scripts/intake.py:1079` —— 錯誤字串會浮出來
- `scripts/pp/oracle.py:322` —— compat-check A-25 會落到「驗不了」
- `tests/test_intake.py:652`、`:745` —— 假資料還是舊形狀，會綠著騙人

## 修法（兩個替代接口 v1.5.6 就有，今天就能改、今天就能驗）

2026-10-14 在 dker 對跑著的 v1.5.6 實打：

    GET /documents               -> 200  {"statuses": {"processed": 472}}
    GET /documents/status_counts -> 200  {"status_counts": {"processed": 472, "all": 472}}
    POST /documents/paginated    -> 200  keys: documents / pagination / status_counts
      pagination: {page 1, page_size 10, total_count 472, total_pages 48}
      每份文件有 file_path

重量：`docker exec -i lightrag-<WORKSPACE> python -` 在容器內打 `localhost:$PORT`，帶 `X-API-Key`。

- `oracle.py` 只要份數 → 改打 `/documents/status_counts`
- `intake.py` 兩處要完整清單 → 改走 `POST /documents/paginated` 翻頁。page_size 上限 200
  （v1.5.7 `document_routes.py:1205`），472 份是 3 頁。`postprocess.py:974-981` 有現成的翻頁寫法

## 逐項比對沒變的

- `.env` 我們設的設定項目：**一個都沒被刪，預設值也沒變**（env.example 兩版比對，config.py 預設值比對）
- 資料庫：`PGTableGraphStorage` 還在；`pgtable_impl.py` 的建表語句**逐字相同 ⇒ 不用搬資料**
- `Dockerfile` 逐位元相同 —— 容器使用者、`/app/data` 路徑、啟動方式都沒動
- `__parsed__`／`archive_source` 行為相同；`addon_params.py` 逐位元相同；`PROMPT_DIR/entity_type/` 照舊
- 我們 docker exec 進去用的內部功能（`is_bundle_valid`、`MinerURawClient`、`default_addon_params`、
  `resolve_entity_extraction_prompt_profile`、`TiktokenTokenizer`）全在；MinerU client 公開介面逐字相同
- `OPENAI_LLM_EXTRA_BODY`（關 DeepSeek 思考）語意不變
- 我們打的其他接口逐條查過都在：`/documents/{paginated,scan,pipeline_status,delete_document,status_counts}`、
  `/query`、`/query/data`、`/query/stream`、12 條 `/graph*`、`/health`
- LLM 快取不會變冷：沒設 `USER_PROMPT_PREFIX` 時送出的文字跟舊版一模一樣（v1.5.7 `utils.py:408`）

## 順便知道

- 新的 `/assets/{hash}/{id}` 是網頁換 logo 用的，**不是圖片接口** —— kbapi 還得留著
- 新的 `EXTRACT_LLM_*`：抽取可以跟查詢用不同模型，正好是我們的形狀
- 安全修補 `GHSA-2wpj-ffvv-2pq8`：449 KB 的 Word 檔可以把記憶體吃到 1.1 GB。這是升級的實質理由
- 上游主線已經比 v1.5.7 多 679 個改動（2026-10-12 查），下一版會是大得多的跳躍
