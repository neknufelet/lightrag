# 進料分組 — 把改稿子從放行流程挪出來

**這份是「要做成什麼樣」的裁決，不是實作步驟。**

## 白話

現在一份文件從頭走到尾：改稿子、送進暫存區、請 LightRAG 讀、等它讀完。四件事黏在
同一段裡，而**改稿子不能在別人被讀的時候做**（`pp/apply.py` 直接拒絕：
「pipeline 忙碌中，拒絕改檔」）。於是只要有人在讀，別人的改稿就被擋住 ——
2026-08-09 實測開到 6 條，30 篇裡 3 篇因此掛掉，退回 1 條。

做法是**把流程切成幾段，全站同時只做一段**。PO 的原話畫成圖：

```
全部先解析（MinerU，6 條併行）
   ↓  這批都解析完
全部跑一次規格過濾
   ↓
   ├── 過了 ──→ 改稿 ──→ 待抽取
   └── 沒過 ──→ 等你看（放著，不擋別人）
   ↓  等整批都過完這一關
通過的一起開始抽（一次送、掃一次、一起等）
   ↓  抽完
剩下沒過的，PO 跟 agent 一起看
```

**「改稿」是 PO 的圖裡唯一沒畫出來的格子**，但它必須在那個位置：改稿是在改檔案、
抽取是在讀同一份檔案，讀到一半被改，讀進去的就是半舊半新。所以它得全部發生在
「開始抽」之前 —— 這個形狀剛好讓兩件事天然錯開。

改稿與抽取**永遠不重疊**。不是靠等、靠重試、靠運氣，是結構上不可能撞在一起。

## 三個已定的問題

PO 2026-08-09 裁決：

| 問題 | 決定 |
|---|---|
| 誰決定何時換段 | **系統自己輪替**。不加暫停開關，剩下的可以放著跑 |
| 一批多大 | **一批 mineru 完、一批開始抽**。批的邊界是進料那一批，不是某個數字 |
| 一批裡有人卡住 | **不等它們，剩下的先走**。看完之後併進下一輪 |
| 沒過的什麼時候處理 | **等整批抽完再改。** 你在畫面上按放行的時間點不用管 —— 閘門保證改稿只會在沒人抽取的時候動手，早按晚按都一樣 |

**沒過的那一堆不做新東西。** 審核台的「等你看」本來就在，而且已經按原因分堆
（`_render_pending_groups`，同一個原因併成一列標「N 份」）。這次要保證的只有一件事：
**它們不擋住別人。**

## 為什麼不做細粒度鎖

另一條路是不切段，把 `pp/apply.py` 那道鎖從「整個 LightRAG 閒不閒」改成「這一份的
PDF 不在暫存區、也不在它的處理清單裡」。理論上改稿與抽取可以完全同時跑。

**不做，兩個理由**：

1. 動到的是 `scripts/pp/`，`compat-check` A-19 守著它，要跑 canary、要重讀鐵則。
   而「逐份就安全」這個前提沒辦法在 coder 上驗證 —— 鐵則第 3 條說 LightRAG 的行為
   要問容器本人、不准推測。
2. **能搶回來的重疊時間本來就不多。** 抽取換成 DeepSeek 之後很快（2026-08-09 實測：
   6 篇 201 秒，對照本機 llama.cpp 每篇約 6 分鐘），所以「改稿時不准抽取」這個
   互斥的代價很小。用高風險換小收益不划算。

⚠ **2026-08-09 曾用錯的理由反對過它**：當時說「改稿的兩雙眼睛跟抽取搶同一張 GPU」。
那是照過時的機器表講的 —— 抽取在 DeepSeek、眼睛 A 在 OpenRouter、眼睛 B 在 OpenAI，
三個都是雲端，都不吃本機那張卡。**結論不變，理由換了。**

第三條路（只把 apply 挪到解析剛跑完那一刻）不夠：解析階段若與別份的抽取同時進行，
apply 一樣會撞。PO 自己指出的。

## 要改的

### 1. 狀態機加一格

```
planned → repairing → repaired → admitted → scanning → extracting → indexed
                      ~~~~~~~~ 新
```

`repaired` ＝ 稿子改好了、還沒送去讀。

**必須落成狀態，不能放在記憶體裡。** 服務重啟後要分得出「這份的稿子改過沒」——
重改一次會把 MinerU 的原文換成上一輪的修補結果（`pp/apply.py` 只記第一次原文的
那個 `setdefault`）。

`ACTIVE_STATUSES` 要加 `repaired`。`OWNED_STATUSES` **不加** —— 那一組問的是
「索引裡那一列該不該算在本站頭上」，而 `repaired` 還沒把檔案複製進暫存區。

### 2. `_run_admit` 拆兩半

現在一支做完 `repairing` 到 `indexed` 全部。拆成：

- **改稿**：只做 `apply`，成功轉 `repaired`
- **送讀**：複製進暫存區 → 掃描 → 等索引 → compat-check → 收尾

### 3. 新增單一的批次協調執行緒

**互斥不靠鎖，靠「兩個時段在同一個迴圈裡先後發生」。** 協調者只有一個，所以不需要
證明鎖的正確性。一輪長這樣：

1. **等**：有東西等改稿，而且解析佇列空、也沒有解析在跑
2. **改稿時段**：把當下等改稿的取一份快照，餵進改稿佇列，等它們全部落定
3. **抽取時段**：
   - 檢查暫存區有沒有外來的 PDF（`_inputs_blocked_reason`，判準不動）
   - 這一批 `repaired` 的全部複製進去
   - **只掃一次**
   - 一個輪詢迴圈同時盯所有份，每份自己的期限
4. 這一批全部落定 → 回到 1

改稿 worker 只在時段 2 被餵工作，時段 3 期間改稿佇列是空的。

### 4. 一批只掃一次

現在每份各自掃、各自輪詢。一批 30 份就是 30 個迴圈打同一個端點，而 `scan` 是掃
**整個目錄**，第一次就把大家都撿走了，後面 29 次只是在重試「pipeline 忙碌中」。

### 5. 每份自己的逾時

`INTAKE_INDEX_TIMEOUT` 預設 24 小時。一份走不完會把整輪拖住一天。改成單份逾時就
標失敗、移出這一輪，其餘照走 —— 這就是「不等卡住的」的落實。

### 6. 自動放行改接線

判乾淨的自動放行（裁決 `4eacaea`）保留，人工放行（`submit_admit`）也一樣，但兩者
都只把狀態推到「等改稿」，**不再自己排進佇列**。何時開工由協調者決定。

### 7. 併行數

| | 現在 | 之後 |
|---|---|---|
| 解析 | `INTAKE_PARSE_WORKERS`，6 | 不變 |
| 改稿 | 併在放行裡 | `INTAKE_REPAIR_WORKERS`，新，預設 6 |
| 送讀 | `INTAKE_ADMIT_WORKERS`，1 | **廢除** |

**`INTAKE_ADMIT_WORKERS` 會消失，這裡明講**（藍桶第 2 條）：一批一起送之後，
「同時幾份在跑」由 LightRAG 的 `MAX_PARALLEL_INSERT` 決定，本站這一側沒有對應的
旋鈕了。`INTAKE_IDLE_TIMEOUT` 保留但改變角色，見下。

### 8. 兩道舊守衛留著，但降級成保險

- `pp/apply.py` 的 `pipeline_idle`：**一個字都不改**。閘門對了就永遠踩不到它；
  哪天踩到了，代表閘門有 bug，那正是我們想聽到的聲音。
- `runner.apply` 開頭的「先等 pipeline 閒置」：留著，但它的角色從**緩解**變成
  **斷言**。協調者已經保證此刻沒人在抽取，所以它應該立刻回來；等不到就是閘門壞了，
  那時候失敗是對的。

## 測試

**要在它該壞的情境下實測，不是只看設定對不對。** 2026-08-09 那天兩個警報的 bug 都是
「正常狀態下是綠的」，只有製造出失效情境才看得見。

| 測什麼 | 怎麼證明它有效 |
|---|---|
| apply 全程沒有與抽取重疊 | 假 runner 在 apply 被呼叫的當下記錄「此刻有沒有 job 在 extracting」，斷言全程為否。**舊實作跑這個會紅** |
| 一批只掃一次 | 一批 N 份，`scan` 的呼叫次數 ＝ 1 |
| 一份卡住不擋整批 | 讓一份索引逾時 → 它 failed、其餘照樣 indexed |
| 停在「等你看」的不擋整輪 | 一份 novel 留在 planned → 該輪照走完 |
| 重啟後 `repaired` 不重跑 apply | 稿子改過的那份重啟後直接進送讀 |

既有 `tests/test_intake.py` 全部要過。

## 驗收

- 抽取時審核台「處理中」的「跑 N」真的大於 1
- 一整批 **0 件**因「pipeline 忙碌中，拒絕改檔」失敗
- `compat-check` hard 0、`canary` 相符
- 量前後吞吐（前值：PO 記的每份約 3.8 分鐘，含中斷）

## 沒驗的，動手前要知道

1. ~~一次送一整批進暫存區、只掃一次，LightRAG 會不會全部登記。~~
   **✅ 2026-08-10 在正式庫驗掉了**，見下一節。
2. **改稿 6 條併行會不會撞到 OpenRouter／OpenAI 的速率限制。** 沒量過。
   每一次 apply 內部自己還會開 3 條看表格（`postprocess.py` 的 `--workers` 預設 3）。
3. **一輪的起跑條件是「解析全空」。** 一次丟 200 篇的話，那 200 篇要全部解析完
   才會開始抽第一份。**現在不加上限**，真的要那樣用再說。

## 地基驗證（2026-08-10，正式庫）

**一次 scan 收下多份、當成同一批跑** —— 這是整個設計的地基。正式庫自己的 log：

```
INFO: Processing 5 document(s)
INFO: Extracting stage 1/5: 2014 - Acoustic coherent perfect absorbers.pdf
INFO: Extracting stage 2/5: 2012 - Subjective Preference of Modal Control Methods…
INFO: Extracting stage 3/5: 2018 - Coupled Resonators for Sound Trapping and Absorption.pdf
INFO: Extracting stage 4/5: 2017 - Rainbow-trapping absorbers…
INFO: Extracting stage 5/5: 2019 - Broadband low-frequency sound absorption…
```

五份交錯併行，不是一份跑完換下一份。容器裡的原始碼對得上（as-built，`/app/lightrag/pipeline.py`）：
`total_files = len(to_process_docs)` 把找到的全部收進同一批，
`Semaphore(self.max_parallel_insert)` 只卡併發 —— **超過的是排隊等，不是被丟掉**。

⚠ **不是引用試驗 stack 的數字。** 先前 LOG 記的「22 份 428 秒、六份同時跑」是在
已經刪掉的 `lightrag-ds*` 上量的，那組不能拿來證明正式庫。

## ⚠ 驗地基時撞到的：LightRAG 自己的清理是壞的

正式庫 log 裡 **92 次** `Invalid cross-device link`。看掛載才懂：

```
/data/lightrag/inputs      -> /app/data/inputs
/data/lightrag/work/parsed -> /app/data/inputs/acoustics_v2/__parsed__   ← 巢狀的第二個掛載
```

LightRAG 讀完一份會想把 PDF 從 `inputs/<ws>/` **搬進** `__parsed__/` 存查，但兩者是
不同掛載，`rename` 跨裝置失敗（Errno 18），每一份都失敗。

**資料沒掉**（`work/parsed` 本來就有我們自己放的那份，`library` 還有稽核備份）。
真正的後果是：**暫存區的清理只剩 intake 這一側在做。**

**這件事跟分組直接相關**：現在一次一份，清不掉最多卡一份。改成一次送 30 份之後，
只要清理漏掉幾份，**下一輪會被自己上一批的殘留擋住**（`_inputs_blocked_reason`），
而擋人的理由會是上一批的檔名 —— 2026-08-08 踩過同一個形狀（一件掛掉、後面 15 件
全部退回「等你看」）。

⇒ 實作時 `_release_inputs`／`_cleanup_admitted` 的失敗處理要當成一等公民，不是
邊角案例。**一批收尾時要斷言暫存區真的空了**，而不是假設每一份都清掉了。

## 不動的東西

- `pp/apply.py`、`pp/` 底下任何檔案 —— 所以不需要跑 canary
- `_inputs_blocked_reason` 的判準（「不得有我不認識的檔」）
- `scan` 遇 `pipeline_busy` 重試到收下的行為
- 兩雙眼睛、三隻眼、閘門那一整套
