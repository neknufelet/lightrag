# 拿去審別的專案的 prompt

下面整段可以直接複製貼上，把 `<專案>` 換成目標（例如 `aosr v2`）。

**為什麼要有這份**：體檢最容易失敗的方式不是漏看，是**看了、量了、然後得出錯的
結論**。2026-08-08 這一輪，我自己在一天內：秘密進輸出 3 次、離開碼抓錯地方 2 次、
自己重算而不問系統 4 次——**每一次算出來的數字都看起來沒問題**。所以這份 prompt 的
大半篇幅在講「怎麼確認你量對了」，而不是「要量什麼」。

---

## 直接複製這一段

```
請體檢 <專案>。目標不是列出所有問題，是找出「會安靜出錯而沒有人會知道」的地方。

## 你要遵守的紀律（比找到什麼更重要）

1. 【驗證再斷言】任何關於「跑著的系統」的陳述，必須附上你實際跑過的指令**與它的
   原始輸出**。沒跑過的一律標 `(未驗,推測)`，不得混進事實陳述。
   斷言與輸出不符時，**以輸出為準，改斷言**。

2. 【離開碼要抓對】`cmd | tail; echo $?` 抓到的是管線最後那支的離開碼，不是你要的。
   要離開碼就先存：`cmd > /tmp/out 2>&1; rc=$?; tail /tmp/out; echo "rc=$rc"`。

3. 【不要自己算，去問做決定的那一方】需要知道「系統會怎麼做」時，問那個做決定的
   東西，不要重新實作它的邏輯：
     容器要不要重建 → `docker compose up -d --dry-run`，不要自己比時間戳或雜湊
     伺服器開幾路   → 啟動 log，不要看設定檔
     這段多少 token → 該系統自己的 tokenizer，不要拿字元數除
   自己算的版本只能當交叉驗證，不能當答案。**它一定會跟真正的決策者漂移。**

4. 【0 和小數字先當成量錯】量到「0 個命中」「0.05%」「全數通過」時，**先假設你量
   錯了**。最常見的成因是「你量的欄位不是內容實際存在的欄位」，或「你查的表不是
   資料實際存放的表」。
   **危險在於 0 看起來像「這件事不用做」** —— 它會讓你把一個真問題判成不存在。
   驗證方法：找一個你已知該被命中的例子，確認它真的被命中。

5. 【啟發式可以用來找，不能用來報】用關鍵字密度、命名樣式那類方法圈出候選，可以；
   把圈出來的數量當結論報出去，不行。要報數字，先用權威訊號（解析器給的結構、
   資料庫的型別欄位）覆驗。

6. 【秘密不得經由「整包輸出」離開】
     ✘ `docker inspect --format '{{join .Config.Cmd " "}}'`（命令列上的金鑰會一起出來）
     ✘ `env`、`printenv` 不帶鍵名、`cat .env`、`source .env`
     ✘ 先取出整包再用 sed/grep 遮蔽 —— 遮蔽樣式寫錯就全洩
     ✔ 只取要的那一格；只取指定的鍵；比較兩個秘密是否相同用**雜湊**不用值

7. 【每個發現都要能講出「誰會發現違反」】等級由強到弱：
     會擋下 ＞ 會印警告 ＞ 只在有人主動跑時才響 ＞ 每 session 載入 ＞ **沒有人**
   **人的審查不算執行者**（那是系統外的最後一道，不是系統內的守衛）。
   如果一條規則已經寫在文件裡但等級是「沒有人」，那不是「已經有規範」，
   而是「**有一條沒有人在守的規範**」——那要當成發現報出來。

## 要找什麼

按「安靜程度」排序，越安靜越優先：

A. **改了 A 讓 B 安靜失效的相依。** 找那種「B 的正確性依賴 A 的某個性質，而那個
   依賴沒有寫成斷言」的地方。典型：fallback 沿用另一個元件的設定、預設值在不同
   路徑不一樣、兩處各寫一份同義判準。
   問法：「這裡假設了什麼？那個假設變了的話，誰會知道？」

B. **文件與實際不符。** 特別是每個 session 都會載入的檔（CLAUDE.md 那類）——
   它錯的成本每次都要付。重點看寫死的數字（份數、鍵數、容器數、費用）：
   **數字會過期，指令不會。**

C. **重建會掉的東西。** 比對「範本／文件說的」與「實際跑著的」。範本不是文件，
   是重建時真的會被執行的東西；它過期等於系統會被還原成舊版。

D. **寫好卻沒有人呼叫的檢查。** 找 `def check`／`verify`／`assert` 之類的東西，
   確認它們真的在某條路徑上被呼叫。**寫好的檢查沒被呼叫，等於沒寫。**

E. **只會回綠的檢查。** 對每一條既有檢查問：「它紅過嗎？拿什麼輸入會讓它紅？」
   答不出來的就當成沒有檢查。

F. **不可再生／唯一副本。** 哪些東西掉了就回不來？它們有沒有被當成可再生的東西
   對待（例如被某個清理流程刪掉）？

## 怎麼交

每個發現寫成四段，缺一不可：

  現象      你實際看到什麼（附指令與原始輸出）
  為什麼壞  它會怎麼安靜地出錯，以及誰會受害
  誰會發現  用上面那個等級表；答「沒有人」要明講
  怎麼修    可以直接照抄的指令或改動，不是「建議加強」

最後給我：

  1. 一張表：發現 × 嚴重度 × 誰會發現違反（現況）
  2. **你自己在這次體檢中犯的錯**——量錯的、猜錯的、後來被自己推翻的。
     這一項不得省略。體檢報告如果只有別人的問題，通常代表體檢做得不夠深。
  3. 你**沒有驗**的部分，明確列出來

## 不要做的事

- 不要為了湊數量而報「建議加強型別註解」這類沒有具體損害的東西。
- 不要在沒有量測的情況下說「這裡可能有效能問題」。
- 不要改動任何東西。這一輪只看不動；要動什麼先列出來讓我決定。
- 不要把「我讀了程式碼所以我知道」當成驗證。讀碼是推測，跑起來才是事實。
```

## 用之前先確認三件事

貼給 agent 之前，你自己先確認，否則它會在錯的前提上跑一整輪：

1. **它有沒有辦法真的跑起來那個系統。** 不能跑就只能讀碼，而讀碼的結論一律是推測。
   lightrag 這邊是靠「coder 上刻意沒有 `.env`」讓這件事在物理上分得開。
2. **它知不知道哪些是「別人的東西不要碰」。** 同一台機器上有別的專案時，這條要明講。
3. **有沒有一個「現在是好的」的基準。** 沒有基準的話，它報的每個數字都無從判斷是
   本來就這樣還是壞了。

## 這份 prompt 的來歷

這些判準不是想出來的，是 2026-08-08 那一輪收尾**踩出來的**：

| 紀律 | 那天發生的事 |
|---|---|
| 離開碼要抓對 | 兩次把 `rc=2` 報成 `rc=0`，漏掉真紅燈 |
| 不要自己算 | 四次，每次算出來的都看起來沒問題 |
| 0 先當成量錯 | `person=0`（實際 709）、`消音 0.05%`（實際 8–23%） |
| 啟發式不能當數字報 | 年份密度估參考文獻 40%，實際 10% |
| 秘密不整包輸出 | 三次外洩，而正解早就寫在專案文件裡 |
| 誰會發現違反 | 173 條踩坑教訓裡，51% 的執行者是「沒有人」 |
