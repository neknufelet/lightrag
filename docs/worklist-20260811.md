# 三塊工單（2026-08-11）

PO 指定：**檢索品質 → 內容錯誤 → 檢查有洞**，三塊跑完給結果與修正。

## 為什麼是這個順序

檢索品質排第一**不是因為它最急，是因為它的答案會改變另外兩張票的做法**。
整庫 259 份全部是 DeepSeek 抽的，而它抽出的關係比舊模型少約三成 —— 如果檢索
真的因此變差，結論會是「重抽」，那麼內容錯誤那張票的修正（改解析結果 + 重建
索引）就要跟重抽一起做，先做等於白做一輪。

⚠ **量與判可以並行，改不行。** 改動都會碰同一個知識庫，而且要 PO 拍板。

## A. 檢索品質 — 現在問問題會拿到什麼品質的答案

**要回答的問題**：整庫換成 DeepSeek 抽取之後，查得準不準？中文問英文論文
還差多少？同一題重跑會不會跳？

**怎麼知道做完了**：拿到一張逐題分數表，而且**帶著雜訊帶** —— 單次結果不算數。

### 已經知道的坑

- ⚠ **單次結果不可信**。`retrieval-score.py` 的檔頭寫著：同一題同一端點重跑
  三次拿到 0.7624／0.8507／0.8279，**單題重跑的落差比整組平均的差距大一個
  量級**。成因是 `mode=mix` 先用 LLM 抽關鍵詞，而查詢端溫度沒壓住時每次都不同。
- 查詢端溫度 2026-08-09 已經釘住（0.2、關思考），**但正式庫沒重測過**。
  所以第一件事是量「同條件的雜訊帶」，先確認它真的收斂了。
- ⚠ 只有一個知識庫。`retrieval-score.py` 是 A／B 比較用的，兩邊都指同一個
  端口就是在量重現性 —— 那正好是第一個要回答的問題。
- 題本 `tests/retrieval-questions.json` 是五組中英配對，**配對是刻意的**：
  不配對只能給一個總平均，看不出是哪類問題掉最兇。
- ⚠ 這組分數**不能跟 `cairn/retrieval-tuning.md` 的歷史數字比**。題目換過、
  語料清空重建過，母體不是同一個。

### 做完之後要能說出

```
雜訊帶       同條件重跑的落差有多大（收斂了沒）
逐題分數     哪幾題差、差在中文還是內容
中英落差     還是 63–86% 嗎
結論         要不要重抽
```

## B. 內容錯誤 — 已知在庫裡的錯，而且都能免費修

**要回答的問題**：那 62 處符號誤讀，哪幾種可以換、哪幾種不能？

**怎麼知道做完了**：每一種符號變體都有一個帶理由的裁定，`scan-partial` 的
漂移歸零。

### 已經知道的坑

- ⚠⚠ **不能整批換。** `latex_fix` 的測試記著兩條血淚：
  - `\hat{c}` 全母體 9 處裡有 **3 處是真的遞迴係數 ĉ_n**，換掉會毀資料
  - **t 檢定的 σ̂ 是樣本標準差**，改成 ∂ 就是毀資料
  ⇒ 要**逐種看上下文**才能決定哪幾種進白名單。
- `scan-partial.py --details` 會逐處印出上下文，那就是判斷的材料。
- 判準本身是「上下同形」：`∂p/∂z` 誤讀後分子分母會變成同一個 token，
  而真的 c̄、ρ̄ 不會長成 `c̄x / c̄y`。**看到上下同形就幾乎確定是 ∂。**
- 改法是改 `content_list.json`（走 `_pp_original_*`，可還原）+ `reindex`，
  **不用重抽、不花錢**。
- 另外兩塊碎字元（2012 CH8 第 23 頁、C Equivalent 第 64 頁，各約 100 多字元）
  現有規則抓不到：它們是 `text` 型別、有內容、不是 header/footer。要加一條
  「碎字元」偵測。⚠ 旁邊的表格都抽得很好，那兩塊沒有值得救的內容。

## C. 檢查有洞 — 出事的時候你不會知道

**要回答的問題**：八個閘門裡有幾個真的在寫？沒寫的那些要怎麼接？

**怎麼知道做完了**：體檢表印得出總表，而且每一格的值都來自真的跑過的檢查。

### 已經知道的坑

- 🔴 **體檢表現在是停用狀態。** 2026-08-11 實跑：

  ```
  acoustics_v2　**已停用**：體檢表與現役母體脫節，拒絕輸出總表。
    現役文件 259 份，其中 4 張體檢表的文件已不存在
  ```

  它拒絕輸出是對的 —— 那些幽靈文件貢獻了絕大部分的「通過」，照印會顯示一個
  漂亮的高通過數而現役文件其實幾乎一格都沒驗。**先跑 `archive-ledger.py --move`。**

- 閘門有 **八個**不是六個（`ledger.py` 的 `GATES`）：

  ```
  parse.coverage   parse.checks
  pp.preflight     pp.tables      pp.equations
  extract.grounding  extract.format
  retrieval.smoke
  ```

  現在自動寫得起來的只有 `pp.preflight` 與 `pp.tables`（計畫一判完就寫）。
  ⚠ NEXT.md 寫「六格」是錯的，順手修掉。

- **沒跑過的閘門填 `pass` 就是說謊** —— 這條不准為了讓總表好看而破例。
- `coverage-check`／`parse-check` 已經在每日排程跑了，只差把結果接進表。
- `extract-check` 全庫要一個多小時，**還沒決定掛哪裡**。

## 分工：哪些交給 workflow，哪些不交

| | 交給 workflow | 為什麼 |
|---|---|---|
| 量 | ✅ | 三塊互不相干，並行不會互相踩 |
| 判 | ✅ | 逐個符號變體看上下文，正是可以分頭做的事 |
| **改** | ❌ | 都碰同一個知識庫，而且要 PO 拍板 |

⚠ **workflow 一律唯讀。** 它產出的是「發現什麼 + 建議怎麼修」，不動任何檔案、
不改任何索引。改由人接手，照 TDD 走，動索引之前先問 PO。
