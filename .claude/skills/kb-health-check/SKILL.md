# 知識庫體檢：紅燈是真是假

## 這份流程存在的理由

2026-08-10 對 257 份文件跑完六隻尺，逐份查證最可疑的四份，**四份全是量測工具
自己的問題**。整個知識庫只有兩塊 100 多字元的雜訊要清。

如果沒有人做那四次查證，會發生的是：13 個紅燈掛在那裡，沒有人知道哪個是真的，
然後所有人開始無視它們。**而查證一次要半小時，重複查證的成本才是真正的浪費**
——`pp/findings.py` 的檔頭寫著「同一個查證做過兩次了，沒有這個機制還會有第三次」。

**所以這份流程的產出不是「修好了」，是「查過了，結論記下來了」。**

## 不可違反的四條

1. **難看的數字要先當成量錯。** 鐵則第 7 條說「乾淨的 0 要先當成量錯」，
   **它的鏡像同樣成立**：79% 的漏字率、88% 的 WARN，第一個假設都該是量測本身壞了。
   2026-08-10 四次查證，四次都是這個答案。

2. **先看對照源可不可信，再看被驗的東西。** 每一隻尺都有一個「證人」。
   證人自己壞掉時，判定會指向**被驗的東西**，而且看起來完全合理。
   最快的判準：**抽取出來的詞數大於對照源的詞數 → 證人涵蓋不了它，比對不成立。**

3. **查過的結論要記進 `tests/verified-findings.json`。** 不是寫進 LOG（會被時間
   淹沒）、不是寫進 CLAUDE.md（太重）。記在那裡，工具下次超標時會**自己印出來**。
   ⚠ 每筆要帶 `at_verification`（當時的數字）：現值偏離超過 50% 時工具會改說
   「已查證但數字已變動」——**過期的結論比沒有結論更危險**，它會讓人跳過該做的查證。

4. **不要為了讓數字好看而動文件。** 2026-08-10 想過三種：OCR 重做、換 MinerU 的
   vlm 模式、整頁 VLM 重新辨識。**三種都不該做**，理由見下方「不要做的事」。

## 六隻尺的準度（2026-08-10 實測，257 份）

| 尺 | 工具 | 叫了幾次 | 準度 |
|---|---|---|---|
| `parse.coverage` | `coverage-check.py` | 13（5%） | **查 4 次全錯** |
| `parse.checks` WARN | `parse-check.py` | 225（88%） | 沒有鑑別力 |
| `parse.checks` ERROR | 同上 | **2（0.8%）** | **2/2 全對** |
| `pp.preflight` | intake 自帶 | — | 直接可信 |
| `pp.tables` | intake 自帶 | — | 直接可信 |
| `extract.grounding` | `extract-check.py` | 接不到 0 | 全綠 |
| `extract.format` | 同上 | 符號型 8.7% | 已知現象，有查證紀錄 |

**`retrieval.smoke` 不在逐份的表上** —— `retrieval-check.py` 只有 `--query`，
它是整庫層級的量測，放每日檢查。

**`pp.equations`（`eq-check.py`）要打 VLM，花錢。** 沒有 PO 明確指示不要跑。

## 怎麼判斷一個紅燈是真是假

### 第一步：看對照源的規模

```bash
# coverage-check 的 JSON 裡直接有
pdf_words   vs   content_words
```

**`content_words > pdf_words` → 假訊號**，證人讀不全。2026-08-10 的三份都是這樣：

```
2023   證人 397  vs 抽取 2500   （差 6 倍）
2026   證人 903  vs 抽取 1429
1979   證人 2359 vs 抽取 2748
```

### 第二步：看缺詞長什麼樣

```
碎片        usti、essi、etri、bilit     → 字型／浮水印被讀成片段，假的
重複字母    dddd、nnjj、mmmmmm          → 數學字型沒有編碼，假的
黏在一起    roomacoustics、methodfor    → 掃描件文字層沒有詞邊界，假的
冠詞        the 缺 336 次               → 冠詞不可能被漏掉，量錯了
實詞散落    slit、folded、absorption    → 要往下查，可能是真的
```

### 第三步：逐頁字元數（最有用的一招）

```python
# 每頁的 text + table_body 字元數，某頁遠低於中位數就是它
```

比詞頻比對可靠得多：不呼叫模型、不需要對照源、不會被壞掉的文字層騙，
而且**直接指出去看第幾頁**。

⚠ **最後一頁空白通常不是問題** —— 那是參考文獻，而 `reference_section` 本來
就會把它消音。2026-08-10 四份裡有三份的最後一頁是空的，全部無害。

### 第四步：真的可疑就並排看

```bash
pdftotext -f <頁> -l <頁> <pdf> -    # 原文那一頁
# 對照 content_list.json 裡同一頁的項目
```

2026-08-10 的 2024 那份就是這樣破的：`pdftotext` 把雙欄版面的同一段話**重複輸出
且第二次被打散**，MinerU 只寫一次，於是被算成「缺少」。

## 三類處置

| 類別 | 做什麼 |
|---|---|
| **假訊號** | 記進 `verified-findings.json`，下次自動閉嘴 |
| **真的壞但局部** | 只補那一塊。碎字元且旁邊有完整表格 → **消音**（鐵則 2，可還原可查帳，零成本） |
| **真的壞且整份** | 退回重解析。⚠ 2026-08-10 一份都沒遇到 |

## 不要做的事

- **不要換 MinerU 的 vlm 模式。** 2026-08-01 同檔實測（`.env.example` 有記）：
  vlm 有 16/57 個表格區域完全空白、表格內容量只有 pipeline 的一半，
  而且**真實掉字兩者都約等於零**。
- **不要對整頁做 VLM OCR。** `MINERU_IS_OCR=true` 已經在跑，MinerU 從來沒讀那個
  壞掉的文字層 —— 它把頁面當圖看、自己認一遍。再做一次不會更好。
- **不要為了紅燈重新解析。** 鐵則第 8 條：重解析同一份 PDF，MinerU 對表格的辨識
  不可重現。拿一個好結果去賭一個不確定的結果。
- **不要讓這些尺擋放行。** 2026-08-10 的數字：若第 1、2 隻是擋的，257 份會只剩
  30 份進得去，而擋錯的佔絕大多數。**只警告，不停**（PO 裁決）。

## 常用指令

```bash
# 三隻不花錢的尺（唯讀）
python3 scripts/coverage-check.py --json          # 全庫，約 10 分鐘
python3 scripts/parse-check.py                    # 全庫，快
python3 scripts/parse-check.py --doc X --details  # 看 mangled 的實際內容
python3 scripts/extract-check.py --json           # 全庫，約 1 小時

# 體檢表
python3 scripts/ledger.py summary --problems
python3 scripts/ledger.py show 'C Equivalent'
```

⚠ 全庫跑要背景跑，而且**`pgrep -f` 會匹配到自己那條 ssh 指令** ——
2026-08-10 因此兩次誤判「還在跑」。用 `ps -eo cmd | awk '/scripts.xxx/ && !/awk/'`。
